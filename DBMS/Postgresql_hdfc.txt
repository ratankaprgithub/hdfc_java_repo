-------------

Problems with Flat Files:
-------------------------

1. Data Redundancy: 

--Same data gets repeated multiple times.

2. Data Inconsistency:

--One file containts "Ravi Kumar" whereas another file contains "Ravi K"

3. Data Retrieval:

--Finding one customer among lakhs of records becomes difficult.

4. Poor Security

--Anyone can modify the file.

5. Difficult Maintenance

--Updating thousands of files becomes difficult.

6. Data Integrity Issues

--No guarantee that correct data is entered.

Example:

Age = -50

--Flat files cannot effectively prevent such invalid data.


To overcome the limitations of Flat Files: 


--To overcome the above limitations DBMS softwares are introduced.

Types of Data Models:
--------------------

There are three major data models are there:

1. Hierarchical Model

2. Network Model

3. Relational Model



Hierarchical Model:
------------------

--In Hierarchical Model, data is organized in a tree-like structure.

--Here one root element will be there and for one root there can be multiple childs elements.

--This model is also called as parent-child hierarchical model.

Example:

	College
     [name|address]   
	    |
	Department
       [dno|name]
            |
--------------------------------
|				|
Course			      Student
[cno|name|duration]	     [sno|name|address]
   |
Faculty
[id|name] 


The biggest limitation of this model is: 

Not all data naturally follows a parent-child relationship.

Example:

Suppose:

Student
Course

A student can enroll in multiple courses.

A course can have multiple students.

--This relationship cannot be represented efficiently using a simple hierarchy.


2. Network Model:
-----------------

--In Network Model, entities are represented as nodes and connected through relationships.

--Here we gets a graph like structure.

Example:

Student
 /   \
/     \
Java  Spring
 \    /
  \  /
 Teacher


Limitations:

1. Not suitable for large amounts of data and relationships.

2. Complex to design

3. Complex to maintain

--This completely changed the database world.

--In this model, data is stored in the form of 2-dimentional tables.

Why Is It Called Relational?

--Because tables can be related to each other.

DBMS Architecture:
==================

ANSI (American National Standards Institute) proposed a Three-Level Architecture for DBMS.

This architecture is also known as:

ANSI/SPARC Architecture


Objective of DBMS Architecture:
---------------------------------

The main objective of DBMS Architecture is:

--To separate the user's view of data from the way data is physically stored.

Benefits:

Data Abstraction
Security
Flexibility
Data Independence


Three Levels of DBMS Architecture:
----------------------------------

1. External Level
2. Conceptual Level
3. Internal Level


External Level
     ↑
Conceptual Level
     ↑
Internal Level




1. Conceptual Level:
--------------------

--The Conceptual Level provides the logical view of the entire database.

--It is the most important level for Database Developers.

It describes:

What data should be stored
Data Types
Constraints
Relationships
Business Rules

It does NOT describe:

--How data is physically stored

Example:

CREATE TABLE employee
(
emp_id INT PRIMARY KEY,
name VARCHAR(100) NOT NULL,
salary NUMERIC(10,2)
);

The above definition specifies:

Data Type
Primary Key
NOT NULL Constraint

--Therefore it belongs to the Conceptual Level.

Relationship Example:

CREATE TABLE department
(
dept_id INT PRIMARY KEY
);

CREATE TABLE employee
(
emp_id INT PRIMARY KEY,
dept_id INT REFERENCES department(dept_id)
);

--The Foreign Key relationship is also part of the Conceptual Level.


2. External Level:
------------------

--The External Level provides customized views of data to different groups of users.

Purpose:

Security
Restricted Access
Simplified Data Access

Example:

--Suppose we have the following table:

Item

item_no
item_name
price
quantity

Customer View:

item_name
price

Manager View:

item_name
price
quantity

Different users can access different portions of the same data.

Example using SQL View:

CREATE VIEW customer_view AS
SELECT item_name, price
FROM item;


--The customer can access only the view instead of the complete table.

Important Point:

External Level is mainly used for:

Security
Controlled Data Access
User-Specific Views


3. Internal Level:
------------------

--The Internal Level describes how data is physically stored inside the database.

--It is the lowest level of the architecture.

It includes:

Storage Files
Data Pages
Disk Blocks
Index Structures
Storage Allocation

Managed By:

Database Engine
DBA

Example:

When we create:

CREATE TABLE employee(
emp_id INT,
name VARCHAR(100)
);


--The developer only sees the table.

Internally PostgreSQL decides:

Which file stores the table
Which page stores the data
Which block stores the page

--These decisions belong to the Internal Level.

Important Point:

--The Internal Level focuses on physical storage optimization.




Data Independence:
------------------

--It means, Changes at one level should not affect higher levels.

--There are two types of Data Independence based on the 3-level ANSI/SPARC architecture:

1. Logical Data Independence
2. Physical Data Independence



1. Logical Data Independence:
-----------------------------

--Changes in the Conceptual Level should not affect the External Level.

Example:

employee table:

id
name
salary

Later:

ALTER TABLE employee ADD COLUMN email VARCHAR(100);

Even after adding the new column:

Customer View:

id
name
salary

--continues to work without modification.

This property is called: Logical Data Independence

Benefit:

--Changes in the database design should not require changes in user views.



2. Physical Data Independence:
------------------------------

--Changes in the Internal Level should not affect the Conceptual Level.

Example:

The DBA may:

Move data files
Reorganize storage
Rebuild indexes
Change storage locations

Despite these changes:

CREATE TABLE employee
(
emp_id INT,
name VARCHAR(100)
);

--remains unchanged.

--Application code also remains unchanged.

This property is called: Physical Data Independence

Benefit:

--Storage-related changes do not impact database design or application logic.



Introduction to PostgreSQL:
==========================

--PostgreSQL (pronounced as Post-Gres-Q-L) is an open-source Relational Database Management System (RDBMS) software used to store, manage, and retrieve data efficiently.

--It follows the Relational Model proposed by Dr. E. F. Codd and stores data in the form of related tables.


History of PostgreSQL:
---------------------

--PostgreSQL originated from the POSTGRES project at:

University of California, Berkeley

The project was led by: Michael Stonebraker

--Over time, PostgreSQL evolved into one of the most powerful open-source databases.



Why PostgreSQL is Popular?

Because it provides:

Reliability
Security
Performance
Scalability
Open Source

--without licensing costs.


Major Features of PostgreSQL:
-----------------------------

1. Open Source:

--Free to use.

--No license cost.

Example:

PostgreSQL = Free

Oracle = Paid (mostly enterprise environments)

2. ACID Compliance:

--PostgreSQL follows ACID properties.

A → Atomicity
C → Consistency
I → Isolation
D → Durability

--This ensures safe transactions.

3. Supports Large Databases:

Can handle:

Millions of Records
Billions of Records
Terabytes of Data


4. Strong Security

Supports:

Users
Roles
Privileges
Authentication


5. Supports Advanced SQL:

--PostgreSQL provides:

Joins

Window Functions
CTEs
Transactions


6. Cross Platform:

Works on:

Windows
Linux
macOS



7. Extensible

Supports:

Custom Functions

Note: PostgreSQL is an RDBMS, but it also supports several NoSQL capabilities through:

1. Numeric Data Types:

--Used for storing numbers.

-32,768 to 32,767

age SMALLINT

INTEGER (INT): Most commonly used numeric type.
-------------

Range:

-2,147,483,648

to

or
emp_id INT

BIGINT: Used for very large numbers.
-------

Example:

mobile_no BIGINT


NUMERIC: Used when precision is important.
--------

Syntax:

NUMERIC(precision, scale)

Where:

precision = total digits

scale = digits after decimal

Example:

salary NUMERIC(10,2)

FLOAT vs NUMERIC:
-----------------

NUMERIC → Exact
FLOAT   → Approximate

--For financial applications:

Always prefer NUMERIC

Variable length string.

--------

UUID = Universally Unique Identifier

Globally Unique
Hard to Guess
Good for Distributed Systems

8-4-4-4-12 hexadecimal characters

SQL Fundamentals & SQL Categories:
==================================

What is SQL?
------------

SQL stands for:

	Structured Query Language

--SQL is a standard language used to communicate with Relational Databases.


Using SQL we can:

Create Databases
Create Tables
Store Data
Retrieve Data
Update Data
Delete Data
Manage Security
Control Transactions


SQL commands are divided into five categories:

1. DDL: Data Definition Language
2. DML: Data Manipulation Language
3. DQL: (DRL) Data Query Language
4. DCL: Data Control Language
5. TCL: Transaction Control Language


1. DDL (Data Definition Language):
-----------------------------------

--DDL commands are used to define and modify database structures.

These commands work on:

Database
Table
Schema
Constraints


Common DDL Commands:

CREATE
ALTER
DROP
TRUNCATE
RENAME


CREATE:
-------

--Used to create database objects.

Create Database:

	CREATE DATABASE training_db;

Create Table:

CREATE TABLE employee
(
    emp_id INT,
    emp_name VARCHAR(100)
);



ALTER:
-----

--Used to modify existing structures.

Add New Column:

	ALTER TABLE employee ADD COLUMN salary NUMERIC(10,2);


DROP:
-----

--Used to permanently remove objects.

Drop Table:

	DROP TABLE employee;

TRUNCATE:
----------

--Removes all rows but keeps table structure.

	TRUNCATE TABLE employee;




2. DML (Data Manipulation Language)
------------------------------------

--DML commands manipulate the data stored inside tables.

Common DML Commands:

INSERT
UPDATE
DELETE



INSERT:
--------

--Used to add data.

Example1: Inserting all the columns

	INSERT INTO employee VALUES(101,'Ravi');

Example2: Inserting specific columns values


	INSERT INTO employee(name) VALUES('Ravi');



UPDATE:
------

--Used to modify existing data.

	UPDATE employee SET emp_name='Amit' WHERE emp_id=101;



DELETE:
-------

--Used to remove records.

	DELETE FROM employee WHERE emp_id=101;

Important Rule:

When using GROUP BY:

--Every column in the SELECT clause that is not inside an aggregate function must be present in the GROUP BY clause.

Example:

Correct:

SELECT address, salary, MAX(salary)
FROM employee
GROUP BY address, salary;


Incorrect:

SELECT address, salary, MAX(salary)
FROM employee
GROUP BY address;



How Group By works:
-------------------

--Aggregate (group) functions such as SUM(), AVG(), COUNT(), MAX(), and MIN() operate on multiple rows and return a single value.

For example:

SELECT SUM(salary) FROM employee;

Output: 365000

--Here the database calculates the total salary of all employees and returns a single value.


Problem Without GROUP BY:
------------------------

Suppose we write:

SELECT address, SUM(salary)
FROM employee;

PostgreSQL will generate an error:

ERROR: column "employee.address" must appear in the
GROUP BY clause or be used in an aggregate function


--The aggregate function SUM(salary) returns only one value for the entire table.

--But address contains multiple values:

Delhi
Mumbai
Delhi
Chennai
Delhi
Mumbai

--Now PostgreSQL cannot determine which address should be displayed along with the single salary total.

--Therefore, a normal column cannot be used together with a group function unless the data is grouped properly.

Solution: GROUP BY Clause

--To calculate salary totals for each address separately, use:

SELECT address, SUM(salary)
FROM employee
GROUP BY address;


Output:

 address |    sum
---------+-----------
 Mumbai  | 110000.00
 Delhi   | 175000.00
 Chennai |  80000.00



When the following query is executed:

SELECT address, SUM(salary)
FROM employee
GROUP BY address;

PostgreSQL performs the following steps:

Step 1: Read the GROUP BY Column

address

Step 2: Create Logical Groups:

Group 1 → Delhi
Group 2 → Mumbai
Group 3 → Chennai


Step 3: Place Rows into Corresponding Groups

Delhi Group:

emp_id	emp_name	salary
101	Ravi	        50000
103	Neha	        70000
105	Rahul	        55000

Mumbai Group:

emp_id	emp_name	salary
102	Amit	        60000
106	Ankit	        50000

Chennai Group:

emp_id	emp_name	salary
104	Priya	        80000


Step 4: Apply Aggregate Function on Each Group

Delhi   → 50000 + 70000 + 55000 = 175000

Mumbai  → 60000 + 50000 = 110000

Chennai → 80000


Step 5: Create Temporary Result Set

address	sum
Delhi	175000
Mumbai	110000
Chennai	80000

--Finally, PostgreSQL returns this result to the user.


Important Point:

--Normal query execution works row by row.

Example:

SELECT emp_name, salary FROM employee;

--The database processes one row at a time.


--But aggregate functions work on an entire group of rows.

Example:

SELECT SUM(salary) FROM employee;

--The database must read all salary values before producing the result.

--Because of this difference, normal columns and aggregate functions cannot be mixed directly.

--To establish a relationship between them, we use the GROUP BY clause.



HAVING Clause:
-------------

--The HAVING clause is used to filter groups created by the GROUP BY clause.

--Just as the WHERE clause filters individual rows, the HAVING clause filters groups after grouping has been performed.

WHERE  ->  Filters rows

HAVING ->  Filters groups


--The WHERE clause is executed before GROUP BY.

--The HAVING clause is executed after GROUP BY.

--Therefore, if we want to apply a condition on grouped data or on aggregate function results, we must use the HAVING clause.



Syntax:

SELECT column_name, aggregate_function(column_name)
FROM table_name
GROUP BY column_name
HAVING condition;



Example 1: Display Number of Employees in Each Address

FROM employee
GROUP BY address;

1. CROSS JOIN:
--------------

--A Cross Join returns all possible combinations of rows from both tables.

--It does not require any matching condition.

Syntax:

SELECT *
FROM employee
CROSS JOIN department;

Formula:

Total Rows = Rows in Table1 × Rows in Table2

In our data:

Employee Rows   = 8
Department Rows = 5

Result:

8 × 5 = 40 rows

Use Cases:

--Rarely used in real projects.

Used mainly for:

Generating combinations
Testing
Matrix reports



2. INNER JOIN:
-------------

An Inner Join returns only the rows that have matching values in both tables.

--INNER JOIN is the most frequently used join in real-world applications.

Syntax:

SELECT columns
FROM table1
INNER JOIN table2
ON condition;

-------------------

A FULL OUTER JOIN returns:

All rows from Left Table
+
All rows from Right Table

Matched rows are combined.

Unmatched rows are filled with NULL values.

       d.dept_name
FROM employee e

          | Admin



Employee     Department

[ ALL ]  +  [ ALL ]

Important Point:

The result contains:

All matched records
Unmatched employees
Unmatched departments


Summary:

INNER JOIN: Only Matching

LEFT JOIN: Keep Everything From Left

RIGHT JOIN: Keep Everything From Right

FULL OUTER JOIN: Keep Everything From Both

Constraints & Data Integrity:
=============================

--Suppose we create an employee table:

CREATE TABLE employee(
    emp_id INT,
    emp_name VARCHAR(100),
    salary NUMERIC(10,2)
);

--Without constraints PostgreSQL allows:

INSERT INTO employee
VALUES(NULL,NULL,-5000);

Technically the data gets inserted.


But:

Employee ID is missing
Employee Name is missing
Salary cannot be negative

This is called: Bad Data

To prevent bad or invalid data, databases use: Constraints


Constraint:
----------

--A Constraint is a rule applied on a column or table to enforce data integrity.

Constraint = Restriction/Rule

--that controls what data can be inserted, updated, or deleted.

Types of Constraints:

1. NOT NULL
2. UNIQUE
3. CHECK
4. PRIMARY KEY
5. FOREIGN KEY
6. DEFAULT



Constraints can be defined in two ways:

1. Column-Level Constraint
2. Table-Level Constraint


Column-Level Constraints:

--These constraints are written immediately after the column definition.

Syntax:

column_name datatype constraint

Example:

CREATE TABLE employee
(
    emp_id INT PRIMARY KEY,
    emp_name VARCHAR(20) NOT NULL,
    salary NUMERIC(10,2) CHECK(salary > 0)
);


Table-Level Constraint:

--These constraints are written after all column definitions.

CREATE TABLE employee(
    emp_id INT,
    salary NUMERIC(10,2),
    CHECK(salary > 0)
);


Which Constraints Can Be Applied at Which Level:
------------------------------------------------

| Constraint            | Column Level    | Table Level |
| --------------------- | --------------- | ----------- |
| NOT NULL              | Yes             |  No         |
| DEFAULT               | Yes             |  No         |
| CHECK                 | Yes             |  Yes        |
| UNIQUE                | Yes             | Yes         |
| PRIMARY KEY           | Yes             | Yes         |
| FOREIGN KEY           | Generally No*   | Yes         |
| Composite Primary Key | No              | Yes         |
| Composite Unique Key  | No              | Yes         |




1. NOT NULL Constraint:
-----------------------

--Prevents NULL values.

Example

CREATE TABLE employee(
    emp_id INT,
    emp_name VARCHAR(100) NOT NULL
);


INSERT INTO employee
VALUES(102,NULL);

Error.


Real-Time Examples

Usually:

Employee Name
Customer Name
Policy Number
Email

--should not be NULL.

Multiple NOT NULL Columns:


CREATE TABLE employee(
    emp_id INT NOT NULL,
    emp_name VARCHAR(100) NOT NULL,
    email VARCHAR(255) NOT NULL
);



2. UNIQUE Constraint:
---------------------

--Ensures no duplicate values exist.

Example:

CREATE TABLE employee(
    emp_id INT,
    email VARCHAR(255) UNIQUE
);



INSERT INTO employee
VALUES(101,'ravi@gmail.com');

INSERT INTO employee
VALUES(102,'ravi@gmail.com');

Error: Duplicate email not allowed.


Real-Time Examples:

Email
Mobile Number
PAN Number
Passport Number

--often use UNIQUE constraints.


Note: PostgreSQL allows multiple NULL values in a UNIQUE column.

Example:

INSERT INTO employee(email)
VALUES(NULL);

INSERT INTO employee(email)
VALUES(NULL);

Valid.


Composite UNIQUE:

--Multiple columns together can be unique.

Example:

CREATE TABLE enrollment(
    student_id INT,
    student_name VARCHAR(20),
    course_id INT,
    UNIQUE(student_id, course_id)
);


--Same student cannot enroll in same course twice.


3. CHECK Constraint:
--------------------

--CHECK validates data using a condition.

Example

--Salary must be positive.


CREATE TABLE employee(
    emp_id INT,
    salary NUMERIC(10,2) CHECK(salary > 0)
);



Real-Time Examples:

Age Validation:

	CHECK(age >= 18)

	CHECK(rating BETWEEN 1 AND 5)

	CHECK(gender IN ('M','F'))

Premium Amount:

	CHECK(premium > 0)


Example:

CREATE TABLE customer(
    age INT CHECK(age >= 18),
    rating INT CHECK(rating BETWEEN 1 AND 5)
);




4. PRIMARY KEY Constraint:
---------------------------

--Primary Key uniquely identifies each row.

Example:

CREATE TABLE employee(
    emp_id INT PRIMARY KEY,
    emp_name VARCHAR(100)
);



Primary Key Rules:

Must Be Unique
Cannot Be NULL
Only One Primary Key Per Table



Composite Primary Key:

--Some time we need to combine more than one columns to uniquely identify a record.

--We create the Composite PK at table level.

CREATE TABLE enrollment(
    student_id INT,
    course_id INT,
    PRIMARY KEY(student_id,course_id)
);


Here combination of student_id and course_id should not be duplicate.



5. FOREIGN KEY Constraint:
---------------------------

--A Foreign Key (FK) is a constraint used to establish a relationship between two tables and enforce Referential Integrity.

--It ensures that a value entered in the child table must already exist in the parent table.


Referential Integrity means:

--A child record cannot reference a non-existing parent record.

Example:

Parent Table:

CREATE TABLE department
(
    dept_id INT PRIMARY KEY,
    dept_name VARCHAR(20)
);


Child Table:

CREATE TABLE employee
(
    emp_id INT PRIMARY KEY,
    emp_name VARCHAR(20),
    dept_id INT,

    FOREIGN KEY(dept_id)
    REFERENCES department(dept_id)
);


Valid Insert:

INSERT INTO department VALUES
(10,'HR');

INSERT INTO employee VALUES
(101,'Ravi',10);


Invalid Insert:

INSERT INTO employee VALUES
(102,'Amit',99);

Error: violates foreign key constraint

--Because department 99 does not exist in the parent table.




Foreign Key Actions (Cascade Options):
---------------------

--By default, if a parent table record is referenced by a child table through a foreign key, the database does not allow the parent record to be deleted or its referenced key value to be updated.

--This restriction is enforced to maintain Referential Integrity and prevent orphan records.

--To allow such operations automatically, we can use cascade options such as:

   ON DELETE CASCADE
   ON UPDATE CASCADE

-- These options instruct the database to automatically propagate the changes to the related child records.

--When a parent row is UPDATED or DELETED, PostgreSQL can automatically perform actions on related child rows.




1. ON DELETE CASCADE

--If a parent record is deleted, all related child records are automatically deleted.

Example:

CREATE TABLE employee
(
    emp_id INT PRIMARY KEY,
    emp_name VARCHAR(20),
    dept_id INT,

    FOREIGN KEY(dept_id)
    REFERENCES department(dept_id)
    ON DELETE CASCADE
);

Example:


department:

10  HR
20  IT

employee:

101 Ravi 10
102 Neha 10
103 Amit 20

Delete Parent:

DELETE FROM department WHERE dept_id = 10;

Result: Deleted

department

20 IT

employee

103 Amit 20

Employees belonging to department 10 are automatically deleted.



2. ON UPDATE CASCADE:


--If a parent key value changes, related child records are automatically updated.

Example
CREATE TABLE employee
(
    emp_id INT PRIMARY KEY,
    emp_name VARCHAR(20),
    dept_id INT,

    FOREIGN KEY(dept_id)
    REFERENCES department(dept_id)
    ON UPDATE CASCADE
);


Example:

department:

10 HR

employee:

101 Ravi 10
102 Neha 10

Update Parent Key:

UPDATE department
SET dept_id = 1001
WHERE dept_id = 10;


Result: Employee table data also will be updated.

department

100 HR

employee

101 Ravi 1001
102 Neha 1001

--Child records are automatically updated.


3. ON DELETE SET NULL

--When the parent row is deleted, the foreign key column in child records becomes NULL.

Example:

FOREIGN KEY(dept_id)
REFERENCES department(dept_id)
ON DELETE SET NULL


Result:

Before Delete:

101 Ravi 10
102 Neha 10


Delete Department 10:

DELETE FROM department
WHERE dept_id = 10;

After Delete:

101 Ravi NULL
102 Neha NULL


Complete Example:


CREATE TABLE employee
(
    emp_id INT PRIMARY KEY,
    emp_name VARCHAR(20),
    dept_id INT,

    FOREIGN KEY(dept_id)
    REFERENCES department(dept_id)
    ON DELETE SET NULL
    ON UPDATE CASCADE
);

----------------------

--The DEFAULT constraint is used to assign a default value to a column when no value is provided during an INSERT operation.

--If the user does not specify a value for that column, the database automatically inserts the default value.


Example:

Relationships among tables:
===========================


--In a Relational Database Management System (RDBMS), data is generally stored in multiple related tables rather than a single large table.

--To establish a connection between related data stored in different tables, we use Relationships.

--A relationship is typically established using:

Primary Key (PK)
        +
Foreign Key (FK)


Relationships help in:

Reducing data redundancy
Maintaining data consistency
Enforcing referential integrity
Improving database design



What is a Relationship?
-----------------------

--A relationship is an association between two or more tables that allows related data to be linked together.

Example:


Employee Table
      |
      | dept_id
      |
      V
Department Table

--Here, employees are associated with departments through the dept_id column.


Types of Relationships
----------------------

--There are three major types of relationships:

1. One-to-One (1:1)

2. One-to-Many (1:M)

3. Many-to-Many (M:N)


1. One-to-One Relationship (1:1)
--------------------------------

--In a One-to-One relationship, one record from Table A is associated with only one record from Table B, and vice versa.

One Person      ↔      One Passport

One User        ↔      One User Profile

One Citizen     ↔      One Aadhaar Card

One Person      ↔      One Driving Licence

One Husband     ↔      One Wife


Implementation:

Generally, a One-to-One relationship is implemented by:

Creating a Foreign Key
Applying a UNIQUE constraint on the Foreign Key

--This ensures that a parent record can be referenced only once.


Example:

CREATE TABLE person
(

    person_name VARCHAR(30),
    address VARCHAR(50)

(

    rto VARCHAR(30),

    person_id INT UNIQUE,

    FOREIGN KEY(person_id)
    REFERENCES person(person_id)
);

Subqueries: (Nested Query)
==========================

--A Subquery is a query written inside another SQL query.

A subquery is also known as:

Nested Query
Inner Query
Child Query

The main query is called:

Outer Query
Main Query
Parent Query


Syntax:

SELECT column_name
FROM table_name
WHERE column_name operator
(
    SELECT column_name
    FROM table_name
);


Execution Flow:

1. First the Inner Query (Subquery) executes.

2. The result produced by the Subquery is passed to the Outer Query.

3. The Outer Query uses that result and produces the final output.





Example Employee Table:

CREATE TABLE employee
(
    emp_id INT PRIMARY KEY,
    emp_name VARCHAR(20),
    salary NUMERIC(10,2),
    dept_id INT
);


INSERT INTO employee VALUES
(101,'Ravi',50000,10),
(102,'Amit',60000,20),
(103,'Neha',70000,20),
(104,'Priya',80000,30),
(105,'Rahul',55000,10);



--Sometimes we need the result of one query as input to another query.

Example

Display employees whose salary is greater than the average salary.

First find:

SELECT AVG(salary)
FROM employee;

Suppose result:

63000

Then:

SELECT *
FROM employee
WHERE salary > 63000;

--Instead of executing two separate queries, we can combine them using a Subquery.

Example:

SELECT *
FROM employee
WHERE salary >
(
    SELECT AVG(salary)
    FROM employee
);



Execution:

Step 1

SELECT AVG(salary)
FROM employee;

Result:

63000

Step 2

SELECT *
FROM employee
WHERE salary > 63000;

Result:

Neha
Priya


Types of Subqueries:
--------------------

--Subqueries are commonly classified as:

1. Single Row Subquery (Scalar Subquery)

2. Multiple Row Subquery (Multirow single column)

3. Multiple Column Subquery

4. Correlated Subquery


1. Single Row Subquery: Scalar Subquery
----------------------

--A subquery that returns:

Exactly One Row
Exactly One Column



--here mostly same column name which is in the where clause of parent query will be there inside the child query select clause.



Example1: 


Write a Query to find out the employee details who is working in 'IT' detaparment:


SELECT * 
FROM employee 
WHERE dept_id=(select dept_id from department where dept_name='IT');



Note: This query works only if department name 'IT'
returns exactly one row.

Otherwise Oracle/PostgreSQL may throw an error
that the subquery returned more than one row.




Example 2

--Display employees earning more than the average salary.

SELECT *
FROM employee
WHERE salary >
(
    SELECT AVG(salary)
    FROM employee
);

Subquery returns:

63000

Only one value.

Hence: Single Row Subquery


Example 2

Display employees working in the same department as Ravi.

SELECT *
FROM employee
WHERE dept_id =
(
    SELECT dept_id
    FROM employee
    WHERE emp_name = 'Ravi'
);

Subquery returns:

10

Outer query becomes:

SELECT *
FROM employee
WHERE dept_id = 10;


Example3: 


Find employee having highest salary.

SELECT *
FROM employee
WHERE salary =
(
    SELECT MAX(salary)
    FROM employee
);





Operators Used:

--Single Row Subqueries generally use:

=
>
<
>=
<=
<>



2. Multiple Row Subquery
------------------------

--A subquery that returns more than one row.

Example

Suppose we have a department table.

CREATE TABLE department
(
    dept_id INT PRIMARY KEY,
    dept_name VARCHAR(20)
);


INSERT INTO department VALUES
(10,'HR'),
(20,'IT'),
(30,'Finance');


Requirement:

Display employees working in HR or IT departments.


SELECT *
FROM employee
WHERE dept_id IN
(
    SELECT dept_id
    FROM department
    WHERE dept_name IN ('HR','IT')
);


Subquery returns:

10
20

Multiple rows.

Hence: Multiple Row Subquery

Operators Used:

IN
ANY
ALL
EXISTS
NOT EXISTS


IN Operator
-----------

--Used when the subquery returns multiple values.

Example:

SELECT *
FROM employee
WHERE dept_id IN
(
    SELECT dept_id
    FROM department
);

Equivalent to:

WHERE dept_id IN (10,20,30)



ANY Operator
------------

--Condition should be true for at least one value returned by the subquery.

Example

Display employees whose salary is greater than ANY salary of employees in department 10.


SELECT *
FROM employee
WHERE salary > ANY
(
    SELECT salary
    FROM employee
    WHERE dept_id = 10
);

Suppose:

Dept 10 salaries

50000
55000

Condition becomes:

salary > 50000
OR
salary > 55000


Condition must be true for at least one value returned by the subquery.

Example:

salary > ANY (50000,55000)

Equivalent to:

salary > MIN(50000,55000)

Result:

salary > 50000




ALL Operator
------------

--Condition should be true for all values returned by the subquery.

Example
SELECT *
FROM employee
WHERE salary > ALL
(
    SELECT salary
    FROM employee
    WHERE dept_id = 10
);

Suppose:

50000
55000

Condition becomes:

salary > 50000
AND
salary > 55000

Effectively:

salary > ALL (50000,55000)

Equivalent to:

salary > MAX(50000,55000)

Result:

salary > 55000




EXISTS Operator
---------------

--Checks whether the subquery returns at least one row.

Returns:

TRUE  -> if rows exist

FALSE -> if no rows exist

Example

Display departments having employees.

SELECT *
FROM department d
WHERE EXISTS
(
    SELECT 1
    FROM employee e
    WHERE e.dept_id = d.dept_id
);




Here we often see:

SELECT 1

inside EXISTS.

Example:

EXISTS
(
    SELECT 1
    FROM employee
)

Reason:

EXISTS only checks row existence.

Actual column values are irrelevant.


Note: EXISTS stops searching as soon as it finds the first matching row.



NOT EXISTS
----------

Opposite of EXISTS.

Example

Display departments having no employees.

SELECT *
FROM department d
WHERE NOT EXISTS
(
    SELECT 1
    FROM employee e
    WHERE e.dept_id = d.dept_id
);

4. Correlated Subquery:
------------------------

--A Correlated Subquery depends on the Outer Query.

--Unlike normal subqueries, it executes once for each row processed by the outer query.

--A subquery that references columns from the outer query and executes once for each row processed by the outer query.

--A Correlated Subquery depends on values coming from the outer query, 
therefore it cannot be executed independently..


In Normal subquery the inner query execute first then it gives value to the outer query.

Whereas in corelated subquery the the outer query will execute first and its value is given to the inner query for record of the outer query.

Common trick: If child query is using the alias of parent query then 99% chances are there it is a corelated subquery.


Example:

Normal Subquery:


SELECT * 
FROM employee 
WHERE salary > (
 
SELECT AVG(salary) 
FROM employee 

);


Runs independently.

Execution Flow:

1. Execute Child Query
2. Get Result
3. Pass Result to Parent Query
4. Execute Parent Query



Correlated Subquery:

--Uses values from outer query.

SELECT *
FROM employee e
WHERE salary >
(
    SELECT AVG(salary)
    FROM employee
    WHERE dept_id = e.dept_id
);


Notice:

e.dept_id

comes from outer query.

Therefore: Correlated Subquery



--A Correlated Subquery depends on values coming from the Outer Query.

--The Outer Query processes one row at a time and passes values to the Inner Query.

--The Inner Query executes repeatedly, once for each row processed by the Outer Query.

--A Correlated Subquery cannot be executed independently because it references columns from the Outer Query.

Execution Flow:

1. Parent Query picks a row
2. Parent Query passes value(s) to Child Query
3. Child Query executes using those value(s)
4. Result is returned to Parent Query
5. Repeat for the next row



Example

Display employees earning more than the average salary of their own department.

SELECT *
FROM employee e1
WHERE salary >
(
    SELECT AVG(salary)
    FROM employee e2
    WHERE e2.dept_id = e1.dept_id
);






Execution:

For Ravi:

Find average salary of Dept 10
Compare Ravi's salary

For Amit:

Find average salary of Dept 20
Compare Amit's salary

For Neha:

Find average salary of Dept 20
Compare Neha's salary

--The subquery executes repeatedly.



Difference Between Normal and Correlated Subquery:
-------------------------------------------------

| Normal Subquery      | Correlated Subquery    |
| -------------------- | ---------------------- |
| Executes once        | Executes for each row  |
| Independent          | Depends on outer query |
| Faster               | Usually slower         |
| Easier to understand | More complex           |



Subquery vs Join:
-----------------

Subquery
SELECT *
FROM employee
WHERE dept_id =
(
    SELECT dept_id
    FROM department
    WHERE dept_name = 'IT'
);


Join


SELECT e.*
FROM employee e
INNER JOIN department d
ON e.dept_id = d.dept_id
WHERE d.dept_name = 'IT';


Both may produce the same result.

General Rule:

If data is coming from multiple tables
      ↓
Prefer JOIN

If you need a value/result from one query
to be used by another query
      ↓
Subquery is often more readable



A Subquery can be used in:

1. SELECT clause
2. FROM clause
3. WHERE clause
4. HAVING clause
5. DML Statements (INSERT, UPDATE, DELETE)


1. Subquery in SELECT Clause:


SELECT emp_name,
       salary,
       (SELECT AVG(salary) FROM employee) AS avg_salary
FROM employee;


2. Subquery in FROM Clause:

SELECT *
FROM
(
    SELECT *
    FROM employee
    WHERE salary > 50000
) x;

Here the subquery acts as a temporary table (derived table / inline view).


3. Subquery in WHERE Clause:

SELECT *
FROM employee
WHERE salary >
(
    SELECT AVG(salary)
    FROM employee
);

--Most common usage.


4. Subquery in HAVING Clause:

SELECT dept_id,
       SUM(salary)
FROM employee
GROUP BY dept_id
HAVING SUM(salary) >
(
    SELECT AVG(salary)
    FROM employee
);

Delete employees belonging to HR department

    SELECT dept_id
