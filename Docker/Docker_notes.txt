Introduction to Docker and Containerization:
============================================


Imagine you have built a Spring Boot Microservices application.


The project contains:

API Gateway
User Service
Product Service
PostgreSQL
JWT Authentication

--Everything works perfectly on your laptop.

--You commit the code and share it with another developer.

The next day he calls and says:

	The project is not running.

You ask:

	What error are you getting?

He replies:

	Java version issue.

You fix it.

Then he says:

	Now PostgreSQL connection is failing.

You fix it.

Then:
	Port 8080 is already in use.

You fix it.

Then:
	JWT secret key is missing.

You fix it again.

Finally you become frustrated and say:

	But it was working on my machine!


--This situation is one of the most common problems in software development.



The Biggest Problem in Software Development:
--------------------------------------------

For many years developers faced a common challenge:

	Works on My Machine Problem

The application worked perfectly on the developer's system but failed on:

- QA Server
- Testing Server
- Staging Server
- Production Server


Why Does This Happen?
---------------------

Because an application does not run alone.

A Spring Boot application depends on many things.

Example:

Application
Java Runtime
Maven
PostgreSQL Driver
Operating System
Environment Variables
Configuration Files
Network Settings

If any one of them changes:

	Application may fail.


Real World Analogy:
-------------------

Imagine a chef prepares a special recipe.

	The recipe works perfectly in his kitchen.

Now he goes to another kitchen.

Problems begin:

Different Gas Stove
Different Utensils
Different Ingredients
Different Temperature

--The same recipe may produce a different result.

--The software world had exactly the same problem.


Traditional Deployment Process:
--------------------------------

Before Docker, deploying software was a long and painful process.



Example:

Developer Machine:

Windows 11
Java 21
Maven 3.9
PostgreSQL 16

--Application works.

Testing Server:

Linux
Java 17
No Maven
PostgreSQL 14

--Application fails.

Production Server:

Different OS
Different Java Version
Different Configuration

--Application fails again.


How Companies Solved This Before Docker?:
-----------------------------------------

The most common solution was:
Virtual Machines (VMs)


--A Virtual Machine behaves like a complete computer running inside another computer.

Example:

Physical Machine
        |
        |
        +---- Virtual Machine 1
        |          Ubuntu
        |          Java
        |          Spring Boot App
        |
        +---- Virtual Machine 2
                   Windows Server
                   SQL Server
                   .NET Application


Each VM contains:

Operating System
Libraries
Runtime
Application


--and behaves like an independent computer.

--It is considered as hardware level virtualization.


Benefits of Virtual Machines:
-----------------------------

Virtual Machines solved many important problems.


They provided:

Isolation:

	Applications remain separated from each other.

Security:

	Each VM has its own environment.

Dedicated Operating System:

	Different operating systems can run on the same hardware.

Environment Consistency:

	The same VM can run across multiple servers.




Problems with Virtual Machines:
-------------------------------

Although VMs were useful, they had serious limitations.


Problem 1: Large Size

Each VM contains:

Application
+
Libraries
+
Complete Operating System

Example:

Ubuntu OS = 2 GB
Java Runtime = 300 MB
Application = 100 MB

	Total ≈ 2.4 GB

--for a single VM


Problem 2: High RAM Consumption

--Each VM requires dedicated memory.

Example:

VM 1 = 2 GB RAM
VM 2 = 2 GB RAM
VM 3 = 4 GB RAM

--A single server could quickly run out of memory.


Problem 3: Slow Startup

--Starting a VM is similar to booting an actual computer.

Like, 

Power On
Boot Loader
Kernel Loading
Services Starting
Application Starting

Typical startup:

30 Seconds
1 Minute
2 Minutes
Sometimes even longer.

--For modern cloud applications this is too slow.



Real World Analogy:
-------------------

Suppose you want to transport a television.

Virtual Machine Approach:

You transport:

Television
Room
Furniture
Walls
Entire House

--Very heavy.

Better Approach

You transport only:

Television
Remote
Power Cable

--Much lighter.

This idea eventually led to containers.


Virtualization:
===============

Hardware level virtualization

--Virtualization is a technology that allows multiple operating systems to run on a single physical machine.



Instead of purchasing:

1 Server
1 Operating System
1 Application

we can run:

1 Physical Server
Many Operating Systems
Many Applications

--simultaneously.



Example:

Physical Server
      |
      |
      +---- Ubuntu VM
      |
      +---- Windows VM
      |
      +---- CentOS VM

--All running simultaneously.



Real World Analogy:
------------------

Imagine you own a large apartment building.

--Instead of giving the entire building to one family, you divide it into:

Flat 101
Flat 102
Flat 103
Flat 104

Each family feels:
This flat belongs only to us.

--Even though all flats share the same building.

Computers work in a similar way.

--One physical server can be divided into multiple independent virtual environments.


This concept is called:
Virtualization


Why Was Virtualization Invented?
--------------------------------

--Earlier companies purchased powerful servers.

Example:

CPU     : 64 Cores
RAM     : 128 GB
Storage : 2 TB

--But a single application might use:

CPU  : 5%

--Remaining resources were wasted.

Solution:

Instead of:

1 Server
      |
1 Application


Engineers created:

1 Server
      |
Many Virtual Machines
      |
Many Applications


--Now the same hardware could be shared efficiently.



What is a Virtual Machine (VM)?:
--------------------------------

--A Virtual Machine (VM) is a software-based computer that behaves like a real physical computer.

A VM has its own:

Kernal
Drivers
Operating System
CPU Allocation
RAM Allocation
Storage
Network Configuration


--To the user, a VM looks exactly like a real computer.

--That's why VM's are heavy weight.

--Where as in the the Docker, multiple containers uses a single linux kernel.



Example

Suppose your laptop has:

Windows 11
16 GB RAM
512 GB SSD

You install:

Oracle VirtualBox(One type of Hypervisor) 

Now you create:

Ubuntu VM (Ubuntu OS inside the VM)

and allocate:
RAM   : 4 GB

Inside the Ubuntu OS you can install:

Java
Maven
PostgreSQL
Spring Boot

Ubuntu VM behaves like an entirely separate computer.



Virtualization Architecture:
-----------------------------

Applications
    |

    |

Hypervisor:
===========

--A Hypervisor is a software layer responsible for creating, running, and managing multiple Virtual Machines.

--Without a hypervisor, VMs cannot exist.

Simple Definition:

	Hypervisor = VM Manager

--It sits between the hardware and virtual machines and controls all VM resources.


Responsibilities of a Hypervisor
---------------------------------

--The Hypervisor performs many important tasks.

like,

Create VMs
Allocate CPU
Allocate RAM
Allocate Storage
Start VM
Stop VM
Delete VM

--Hypervisor Keeps VMs isolated from each other

--Failure of one VM usually does not affect another VM



Real World Analogy:
------------------

Suppose a hotel has:

	100 Rooms

Guests arrive every day.

Hotel Manager decides:

Room Allocation
Check-In
Check-Out
Room Management

Similarly:

	Hypervisor

--manages all Virtual Machines.




Types of Hypervisors
=====================

Hypervisors are divided into two categories:


1. Type-1 Hypervisor (Bare Metal)
2. Type-2 Hypervisor (Hosted)


Type-1 Hypervisor (Bare Metal Hypervisor):
-----------------------------------------

A Type-1 Hypervisor runs directly on the physical hardware without requiring a host operating system.

--No Host Operating System is required.


Architecture:


 Applications
      |
Guest Operating System
      |
-------------------
 Virtual Machine
-------------------
      |
Type-1 Hypervisor
      |
Physical Hardware



Notice:

	No Host OS

--exists between Hypervisor and Hardware.



Examples:

VMware ESXi:

	Most popular enterprise hypervisor.

Microsoft Hyper-V:

	Widely used in Windows Server environments.

Xen Hypervisor:

	Used by many cloud providers.

KVM (Kernel-based Virtual Machine):

	Commonly used in Linux-based cloud environments.


Advantages:

High Performance:

	No extra operating system layer.

Better Resource Utilization:

	Direct access to hardware.

Better Security:

	Smaller attack surface.

Scalability:

	Can run hundreds of VMs efficiently.


Real World Example:

--AWS EC2, Azure VM, GCP, Large cloud providers uses Type-1 Hypervisors extensively.



Type-2 Hypervisor (Hosted Hypervisor):
---------------------------------------

--A Type-2 Hypervisor runs on top of an existing operating system.

--The host operating system must be installed first.


Architecture:


 Applications
      |
Guest Operating System
      |
-------------------
 Virtual Machine
-------------------
      |
Type-2 Hypervisor (virtual box)
      |
Host Operating System
      |
Physical Hardware


Notice:
	Host Operating System is present between Hypervisor and Hardware.


--This additional layer introduces some performance overhead.


Examples:

Oracle VirtualBox

	Free and commonly used for learning.

VMware Workstation

	Popular desktop virtualization software.

VMware Fusion

	For macOS systems.

Parallels Desktop
	
	Used on Mac machines.





Example

Your laptop:
Windows 11 (Host OS)

Install:
VirtualBox

Create:
VM1

Install:
 Ubunto (Guest OS) on this VM1


--This is Type-2 Virtualization.

What is Containerization?
-------------------------

Containerization is a technology that packages:

Application
+
Libraries
+
Dependencies
+
Runtime
+
Configuration

into a single portable unit called:
Container



What is a Container?
---------------------

--A Container is a lightweight package that contains everything required to run an application.

Example:

Spring Boot Application
Java Runtime
Required Libraries
Configuration

--All packed together.

--Because containers share the host OS kernel, 
they do not require a separate operating system for every application.


Container Architecture:
-----------------------

     |        |
  Runtime   Runtime
     |       |
Container   Container
     |        |
-------------------------------
     Container Engine (Docker)
--------------------------------
     |       |
  Host OS Kernel
       |
    Hardware


Containers share the host kernel.
No Guest OS required.


Why Containers Are Faster?:
---------------------------

Operating System
Kernel
System Services

They simply start the application.

--Much faster than VMs.

Understanding Image Layers:
---------------------------

Most students imagine:


Image = Single File

	Wrong.

Docker Images are made of:
	
	Layers


Real World Analogy:
------------------

Imagine a Burger.

Top Bun
Cheese
Patty
Vegetables
Bottom Bun

--The burger is composed of layers.

Docker Image is similar.



Example:

FROM ubuntu

RUN apt update

RUN apt install openjdk-21-jdk

COPY app.jar app.jar

--Docker creates multiple layers.


Layer Structure:

Layer 4 -> app.jar

Layer 3 -> Java Installation

Layer 2 -> apt update

Layer 1 -> Ubuntu

Together they form:

	Docker Image


Why Layers?
------------

Because layers provide:

Reuse
Caching
Performance
Storage Optimization

Example

Suppose you have:

FROM ubuntu

RUN apt update

RUN apt install java

--Build image.

Now change only:

	COPY app.jar app.jar

Docker will reuse:

Ubuntu Layer
apt update Layer
Java Layer

and rebuild only:

	Application Layer

--This makes builds much faster.



Image Tags:
-----------

Every image has:

Repository
Tag

Example

	docker pull nginx:latest

Repository:
	nginx

Tag:
	latest

Another example:

	docker pull postgres:16

Repository:
	postgres

Tag:
	16


Tags identify versions.

Example

Java Images:

openjdk:17
openjdk:21
openjdk:24

--Each represents a different version.


The Biggest Myth: latest Tag

Many beginners think:

	latest = newest version

--Not always true.


latest

simply means:

	Default Tag

--assigned by image maintainer.


Best Practice:

Avoid:
	FROM postgres:latest

Prefer:
	FROM postgres:16

or
	FROM postgres:17

Reason:

--Future updates may break application compatibility.


Listing Local Images:

	docker images

Downloading Images

	docker pull nginx
	
	docker pull postgres:16

	docker pull mongo:7


Remove Image:

	docker rmi nginx

Remove Specific Version:

	docker rmi postgres:16

Docker Containers:
==================


--A Docker Container is a running instance of a Docker Image.

--A Docker Image is only a blueprint/template, whereas a Container is the actual running application created from that image.

Example:

Docker Image

    nginx
      |
      |
   docker run
      |
      v
Nginx Container

Command:

	docker run nginx



Important Point:

--A Container is not a complete Virtual Machine.

--It does not contain its own complete Guest Operating System.

--Instead, containers share the underlying OS kernel.

Therefore Containers are:

Lightweight
Fast
Portable
Isolated



VM vs Container:
----------------

Virtual Machine:

Application
    |
Libraries
    |
Guest OS
    |
Hypervisor
    |
Hardware

Each VM has its own:

Operating System
Kernel
Drivers
Libraries
Application

--Therefore VMs are comparatively heavyweight.


Container:

Application
    |
Libraries / Dependencies
    |
Docker Engine
    |
Host OS Kernel
    |
Hardware

--Containers do not require a separate Guest OS.

Therefore:

Less RAM
Less Storage
Faster Startup
Lower Resource Usage


Container Isolation:

--Every container runs in an isolated environment.

For example:

Container 1
Spring Boot
Java 21

Container 2
NodeJS
Node 22

Container 3
PostgreSQL

--They can all run on the same machine without interfering with each other.



Container Has a Main Process:
-----------------------------

--Normally, a container runs around one main application process.

Examples:

Nginx Container

Main Process:
	nginx

PostgreSQL Container

Main Process:
	postgres


Spring Boot Container

Main Process:
	java -jar app.jar



Important:

If the main process stops
        ↓
Container stops



What Does docker run Actually Do?
-----------------------------------

Example:

	docker run nginx


Internally:

1. Docker checks whether nginx image exists locally

2. If image is missing:
       Docker pulls it from Docker Hub

3. Docker creates a new container

4. Docker creates an isolated filesystem/network

5. Docker starts the image's configured command

6. Application starts running

So:

	docker run

basically performs:


Create Container
       +
Start Container

----------------------

--A container normally moves through the following states:

Created

   v

   v
Stopped

   v
Removed

We may also :

Restart
Pause
Unpause

a container.

	docker stop <container-id>

	docker stop abc123

	docker ps

	docker ps -a

5. Start an Existing Container:

--A stopped container does not need to be recreated.

Use:
	docker start <container-id>

Example:
	docker start abc123

--The same container starts again.


docker run vs docker start:
----------------------------

	docker run nginx

means:
Create NEW Container
+
Start It


	docker start abc123

6. Restart Container:


	docker restart <container-id>

Example:

	docker restart abc123

--Equivalent conceptually to:

Stop

7. Remove Container:

--Stopping a container does not delete it.

To permanently remove it:

	docker rm <container-id>

Example:
	docker rm abc123

--Normally, container should be stopped before removing it.


Important Concept:

--Deleting a Container does not delete its Image.



Detached Mode:
--------------


Normally:

	docker run nginx

--attaches the container output to the current terminal.

--For server applications, we normally run containers in the background.

Use:

	docker run -d nginx

Here:

	-d = Detached Mode

Meaning:
Run Container
      +
Run in Background

Example:
docker run -d nginx

Docker returns:
	Container ID

Check:
	docker ps

Real-World Example:

--For a Spring Boot backend, we normally do not want the terminal permanently attached.

So instead of:

	docker run user-service

we normally use:
	
	docker run -d user-service

Container Naming:
-----------------

--Docker automatically gives each container a random name.

Instead, we can provide our own name.

Syntax:
	docker run --name <container-name> <image>

Example:

	docker run --name my-nginx nginx

Now instead of container ID, we can use:

	my-nginx

Example:

	docker stop my-nginx

	docker start my-nginx

	docker logs my-nginx

	docker rm my-nginx

--This is much easier than remembering Container IDs.

Port Mapping in Docker:
=======================


Until now we have learned:

Docker Image
      |
docker run
      |
      v
Container

--Suppose we start an Nginx container:

	docker run nginx

Container starts successfully.

Check:
	docker ps

Output:
CONTAINER ID    IMAGE     STATUS
abc123          nginx     Up 2 minutes

Everything looks fine.

The Problem:

Now open browser:

	http://localhost

Will it work?
NO

Why?

Because Docker containers run inside an isolated environment.


Real-World Analogy:
------------------

--Imagine your application is inside a house.

House
 |
 +-- Nginx Server

--The house door is closed.

--People outside cannot access the server.

To allow access:

House
 |
Door Open
 |
Nginx Server

--Similarly, Docker containers keep their ports private by default.


What is a Port?

--A Port is a communication endpoint used by applications.

Examples:

80     → HTTP (nginx)
3306   → MySQL
5432   → PostgreSQL
27017  → MongoDB
8080   → Spring Boot


When Spring Boot starts:

	mvn spring-boot:run


it usually listens on:

	localhost:8080

Container Network Isolation:


Suppose we start nginx:

	docker run nginx

Inside container:

Container
 |
 +-- Nginx
 |
 +-- Port 80

	Port 80 exists inside the container.
But:

Laptop
 |
 +-- Browser

--cannot directly access that container port.


Solution: Port Mapping


Docker provides:

	-p

option.

Syntax:

	docker run -p HOST_PORT:CONTAINER_PORT IMAGE

Example:

	docker run -p 8080:80 nginx

Meaning:

Host Port → 8080

Container Port  → 80

Example 1: Nginx

Run:

	docker run -d -p 8080:80 nginx

Check:
	docker ps

Output:

PORTS

0.0.0.0:8080->80/tcp

Open browser:

	http://localhost:8080

You should see:
	Welcome to nginx


Another example:

	docker run -p 9090:80 nginx

Now access:

	http://localhost:9090

Notice:
	Container still uses Port 80

Only Host Port changed

Real-World Analogy:

--Suppose a hotel room contains a telephone.

Room 101
Phone Number 80

--Visitors outside cannot directly call Room 101.

Reception provides a public number:

Reception Number 8080
      |
      v
Room 101

--Port Mapping works similarly.

Suppose we create image:

Until now we have been using ready-made images:

-------------------------------

--Suppose we have a Spring Boot application.


Project:

├── src
├── pom.xml
└── target

	Run Application

	Repeat Again

	Repeat Again

This leads to:

--Works on my machine problem


--A Dockerfile is a text file that contains step-by-step instructions for building a Docker Image.

Official Definition:

--A Dockerfile is a text document that contains all commands required to assemble an image.

Building Our First Spring Boot Docker Image:
--------------------------------------------

Step1:

Build our Product Service:

	mvn clean package

After successful build:

product-service
├── src
├── pom.xml
├── Dockerfile
└── target
      |
      +-- product-service-0.0.1-SNAPSHOT.jar



Step2:

Create Dockerfile inside the root of our product-service application


FROM amazoncorretto:21

WORKDIR /app

COPY target/product-service-0.0.1-SNAPSHOT.jar app.jar

EXPOSE 8082

CMD ["java","-jar","app.jar"]




Here,

FROM amazoncorretto:21 → Uses Java 21 runtime.
WORKDIR /app → Sets /app as the working directory inside the container.
COPY → Copies the Spring Boot JAR into the container.
EXPOSE 8082 → Documents that the application is expected to use port 8082.
CMD → Starts the Spring Boot application.

Note:

--The actual application port is determined by server.port in application.yml.

--If server.port=8082, the application will run on 8082 inside the container, regardless of the EXPOSE value.

--EXPOSE is only metadata/documentation and does not force the application to run on that port.

--To access the application from outside the container, use port mapping while running the container.

Example:

	docker run -p 8082:8082 product-service:v1

Step 4: Running the Product Service Container
--------------------------------------------

	docker run -p 8082:8082 product-service:v1



Note: since our product-service uses the configuration of application.yml file as:

server:
  port: 8082

spring:
  application:
    name: product-service

  datasource:
    url: jdbc:postgresql://localhost:5432/productdb
    username: postgres
    password: root

  jpa:
    hibernate:
      ddl-auto: update

    show-sql: true



--Here localhost:5432 will be considered as the network inside the container, where postgres is not installed.


To solve this problem we have 2 options:


1. To use the host OS installed postgress change this property as:



docker run -d -p 8082:8082 -e SPRING_DATASOURCE_URL=jdbc:postgresql://host.docker.internal:5432/productdb product-service:v1


Assigning the container name:

	docker run -d --name product-service -p 8082:8082 -e SPRING_DATASOURCE_URL=jdbc:postgresql://host.docker.internal:5432/productdb -e SPRING_DATASOURCE_USERNAME=postgres -e SPRING_DATASOURCE_PASSWORD=root product-service:v1




--Using -e or --env we configure the environment variables and can override any properties inside our application.properties or .yml file like:

spring.datasource.username=admin
spring.datasource.password=admin123
spring.datasource.url=jdbc:postgresql://localhost:5432/productdb

jwt.secret=my-secret-key

server.port=8080

--we can externalize configuration.


Docker Syntax

	docker run -e KEY=VALUE IMAGE

Example:

docker run -e SPRING_DATASOURCE_USERNAME=postgres -e SPRING_DATASOURCE_PASSWORD=root product-service:v1



2. For real microservices deployments, it's usually better to run PostgreSQL in Docker as well and use:

	jdbc:postgresql://postgres-db:5432/productdb

Docker Networks (Container communication)
===========================================

Docker Compose automatically creates an internal network.

--Containers inside the same network can communicate using:

	Container Name
or
	Service Name

--instead of IP addresses.


Compose Example:
----------------

services:

  postgres-db:
    image: postgres:16
    container_name: postgres-db

  product-service:
    image: product-service:v1
    container_name: product-service


--Docker automatically creates:

    Compose Network

Example:

product-service
        |
        |
        |
   postgres-db

--Both containers join the same network.


--As a result, Product Service can connect to PostgreSQL using:

	jdbc:postgresql://postgres-db:5432/mydb

Here:

- postgres-db = service/container name
- 5432 = PostgreSQL port
- mydb = database name

--Docker's internal DNS automatically resolves:

    postgres-db

to the IP address of the PostgreSQL container.

Therefore, there is no need to use:

- localhost
- host.docker.internal
- Container IP addresses

--when both services are running inside the same Docker Compose application.


Internal DNS
------------

--Docker provides an internal DNS server.

Think:

Google DNS

8.8.8.8

--but running inside the Docker network.


When Product Service requests:

	postgres-db

--Docker DNS automatically resolves it to the IP address of the PostgreSQL container.

Example:

postgres-db
      ↓
172.20.0.2

--automatically.

--The actual IP address may change whenever containers are recreated, but the service name remains the same.

--This allows containers to communicate using service/container names instead of IP addresses.




Visual Representation
---------------------

Without Docker DNS:

product-service
      |
      |
172.20.0.2

--Need to know the exact container IP address.

With Docker DNS:

product-service
      |
      |
postgres-db

--Much easier and more reliable.




Recommended JDBC URL:

    jdbc:postgresql://postgres-db:5432/mydb

where:

- postgres-db = PostgreSQL service/container name
- 5432 = PostgreSQL port
- mydb = Database name

Docker Volumes
==============


--By default, all PostgreSQL data is stored inside the container.


Problem:
--------

postgres-db container
        |
        |
        +---- Database Files


If the container is deleted:

    docker rm -f postgres-db

--all database data will be lost.


Solution:
---------

Use Docker Volumes.

--A Docker Volume stores data outside the container and allows data to survive container deletion.


Without Volume
--------------

postgres-db Container
        |
        |
        +---- productdb

Delete Container
        |
        v
Database Lost 


With Volume
-----------

postgres-db Container
        |
        |
        +---- productdb
                |
                |
                v
        postgres-data (Volume)

Delete Container
        |
        v
Volume Still Exists

Database Preserved 


Step 1: Create a Named Volume

	docker volume create postgres-data

Verify:

	docker volume ls

Step 2: Start PostgreSQL container with Volume

docker run -d \
--name postgres-db \
-p 5432:5432 \
-v postgres-data:/var/lib/postgresql/data \
-e POSTGRES_USER=admin \
-e POSTGRES_PASSWORD=admin123 \
-e POSTGRES_DB=mydb \
postgres:16

Explanation

	-v postgres-data:/var/lib/postgresql/data

Maps:

Docker Volume

postgres-data
       |
       |
       v
/var/lib/postgresql/data

(PostgreSQL Data Directory)

--All database files are stored in the volume.



Step 3: Create Some Data

--Connect to PostgreSQL and create:


CREATE TABLE users(
    id SERIAL PRIMARY KEY,
    name VARCHAR(100)
);

INSERT INTO users(name)
VALUES ('Ratan');


Step 4: Delete Container

	docker rm -f postgres-db


Container is deleted.

Volume remains:

	docker volume ls

postgres-data

--still exists.


Step 5: Recreate PostgreSQL Container


docker run -d \
--name postgres-db \
-p 5432:5432 \
-v postgres-data:/var/lib/postgresql/data \
-e POSTGRES_USER=admin \
-e POSTGRES_PASSWORD=admin123 \
-e POSTGRES_DB=mydb \
postgres:16

--PostgreSQL automatically loads existing data from the volume.

Verify:

	SELECT * FROM users;

Output:

 id | name
----+-------
 1  | Ratan

--Data is preserved.

Option 2: Export and Share as TAR Files:
-----------------------------------------

Useful for classroom training or offline sharing.


Save Image

docker save -o user-service-v1.tar user-service:v1

docker save -o product-service-v1.tar product-service:v1

docker save -o api-gateway-v1.tar api-gateway:v1

--Share the .tar files via:

- Google Drive
- OneDrive
- USB Drive
- Company Share Drive

Team Member Loads Image

docker load -i user-service-v1.tar

docker load -i product-service-v1.tar

docker load -i api-gateway-v1.tar
