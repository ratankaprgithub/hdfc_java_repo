Spring Security:
================


What is Security?

Imagine you have developed a banking application.

The application contains:

Customer account details
Transaction history
Credit card information
Loan information
Personal user details

--If anyone can access this information without permission, the entire application becomes useless.

Therefore:

--Security is the process of protecting the data, resources, and business logic of an application from unauthorized access.



Real-Life Example:
-------------------

Consider an ATM Machine.

--The ATM does not allow everyone to withdraw money.

Before performing any operation, it verifies:

Who are you?
Are you allowed to access this account?
How much money can you withdraw?

--Similarly, software applications also need security mechanisms.

Important Security Principles:
------------------------------

--A good security system follows some fundamental principles.

Principle 1: Trust Nothing

--Never assume a request is valid.

--Every request should be verified.

--Every input should be validated.

Examples:

Assume client data is correct.

Validate:

Email format
Phone number
Password strength
JWT Token
User Role


Principle 2: Least Privilege

--Give users only the permissions they need.

Example:

Admin

Can:

Create Users
Delete Users
Update Users

Customer

Can:

View Profile
Update Profile

Cannot:

Delete Users
Access Admin Panel

--This minimizes security risks.



Principle 3: Complete Mediation

--Every request must pass through a central security checkpoint.

Think of an airport.

Before boarding:

ID Verification
Luggage Check
Security Scan

--Similarly, every application request should pass through security filters.


Principle 4: Defense in Depth

--Never depend on a single security layer.

Use multiple layers.

Examples:

Network Layer

	Firewall

Transport Layer

	HTTPS
	SSL/TLS

Application Layer

	Authentication
	Authorization

Database Layer

	Access Controls


Principle 5: Economy of Mechanism

Keep security simple.

--Complex security systems become difficult to maintain and may introduce vulnerabilities.


Principle 6: Open Design

--Security should not depend on hiding implementation details.

--A secure design should remain secure even when people know how it works.


Different Types of Application Security:
========================================

--Modern applications use multiple security mechanisms.

1. Firewall Security

--Blocks unauthorized access to servers.

Example:

--Only employees inside the company network can access an internal HR application.


2. HTTPS Security

--Encrypts communication between client and server.

Without HTTPS:

username=admin
password=1234

--can be intercepted.

With HTTPS:

--Data becomes encrypted during transmission.


3. SSL/TLS Certificates

--Used by HTTPS to establish secure communication.


4. Authentication

--Verifies identity.

Example:

Username + Password


5. Authorization

--Determines permissions.

Example:

--Admin can delete records.

--Customer cannot delete records.

"Who are you?"

	HTTP Status = 401 Unauthorized



2. Authorization:

Question:

"What are you allowed to do?"

--Authorization happens after authentication.


Examples:


| User     | Permission          |
| -------- | ------------------- |
| Admin    | Read, Write, Delete |
| Manager  | Read, Write         |

Authentication vs Authorization:
--------------------------------

| Authentication        | Authorization                |
| --------------------- | ---------------------------- |
| Verifies Identity     | Verifies Permissions         |
| Who are you?          | What can you do?             |
| Happens First         | Happens After Authentication |
| Returns 401 if failed | Returns 403 if failed        |
| Example: Login        | Example: Access Admin Page   |

What Happens Internally?
------------------------

Suppose a user provides the following credentials:

Username : admin
Password : 1234


Step 1: Combine Username and Password

--The client combines the username and password using a colon (:).

	admin:1234


Step 2: Encode Using Base64

--The combined string is converted into Base64 format.

admin:1234
↓
YWRtaW46MTIzNA==

--Base64 is an encoding mechanism, not an encryption mechanism.

Step 3: Add Credentials to HTTP Request Header

--The encoded value is sent inside the Authorization header.

	Authorization: Basic YWRtaW46MTIzNA==



Step 4: Request Sent to Server

--The complete HTTP request may look like:

GET /employees/hello  HTTP/1.1
Host: localhost:8080

Authorization: Basic YWRtaW46MTIzNA==


Step 5: Spring Security Validates Credentials

--When the request reaches the server:

1. Spring Security reads the Authorization header.

2. It extracts the Base64 encoded value.

3. It decodes it back to:

	admin:1234

4. It separates the username and password.

5. It validates the credentials using the configured authentication mechanism (InMemoryUserDetailsManager, Database, LDAP, etc.).

--If the credentials are valid:

	Authentication Successful

Otherwise:

	401 Unauthorized


Calling Secured APIs from React, Angular, Mobile Apps, or Other Clients:
------------------------------------------------------------------------

--When a frontend application (React, Angular, Vue.js), a mobile application, Postman, or any external client
 wants to access a Spring Security protected API, it must send the credentials in the Authorization header.

Example:

	Authorization: Basic YWRtaW46MTIzNA==

In general:

	Authorization: Basic base64(username:password)


Example in JavaScript:
----------------------

const username = "admin";
const password = "1234";

const credentials = btoa(username + ":" + password);

fetch("http://localhost:8080/employees/hello", {
    headers: {
        Authorization: `Basic ${credentials}`
    }
}); 




Important Note About Basic Authentication:
-----------------------------------------

Many beginners think:

Base64 = Encryption

This is wrong.

--Base64 is only encoding.

--Anyone can decode it.

--Base64 is an encoding mechanism. It is completely reversible and does not provide security. 
It is used only to represent data in a transport-friendly format.

Example:

YWRtaW46MTIzNA==

can be decoded back to:

admin:1234

--Therefore Basic Authentication should generally be used with:

	HTTPS

--to protect credentials during transmission.

Configuring Multiple username and passwords:
--------------------------------------------

--Until now, we have used a single user configured inside:

application.properties file:

spring.security.user.name=admin
spring.security.user.password=1234

--However, real-world applications typically contain multiple users, where each user may have different roles and permissions.

--Spring Security provides the InMemoryUserDetailsManager implementation which allows us to maintain multiple users directly in memory.


InMemoryUserDetailsManager:
---------------------------

--It is an implementation of the UserDetailsService interface that stores user information in memory (RAM).

It allows us to:

Create multiple users.
Assign different roles or authorities.
Authenticate users without using a database.
Quickly test and learn Spring Security concepts.

This approach is commonly used for:

Learning Spring Security
Proof of Concept (POC)
Testing APIs
Internal applications

--In production applications, user details are usually loaded from a database using a custom UserDetailsService.


Example:

--Create a class named AppConfig.java inside the com.hdfc.config package and annotate it with @Configuration.



package com.hdfc.config;

import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.security.core.userdetails.User;
import org.springframework.security.core.userdetails.UserDetails;
import org.springframework.security.crypto.bcrypt.BCryptPasswordEncoder;
import org.springframework.security.crypto.password.PasswordEncoder;
import org.springframework.security.provisioning.InMemoryUserDetailsManager;

@Configuration
public class AppConfig {

	
	
	@Bean 
	InMemoryUserDetailsManager userDetailsService(PasswordEncoder passwordEncoder) {
		
		UserDetails admin= User.builder()
					.username("admin")
					.password(passwordEncoder.encode("1234"))
					.authorities("ROLE_ADMIN")
					.build();
		
		UserDetails user= User.builder()
				.username("user")
				.password(passwordEncoder.encode("1234"))
				 .authorities("ROLE_USER")
				.build();

		return new InMemoryUserDetailsManager(admin,user);
		
	}

	
	
	@Bean
	PasswordEncoder passwordEncoder() {
		return new  BCryptPasswordEncoder();
	}
	
	
}



Understanding the Above Configuration:
--------------------------------------

Step 1: Create a PasswordEncoder Bean


@Bean
PasswordEncoder passwordEncoder() {
    return new BCryptPasswordEncoder();
}

--The BCryptPasswordEncoder is used to hash passwords before storing them.

Instead of storing:

1234

--Spring Security stores a BCrypt hash similar to:

$2a$10$Q9X0Q6....

--This makes passwords much more secure.


Step 2: Create UserDetails Objects:

UserDetails admin = User.builder()
        .username("admin")
        .password(passwordEncoder.encode("1234"))
        .authorities("ROLE_ADMIN")
        .build();

This creates a user with:

Username : admin
Password : 1234
Authority : ROLE_ADMIN

Similarly:

UserDetails user = User.builder()
        .username("user")
        .password(passwordEncoder.encode("1234"))
        .authorities("ROLE_USER")
        .build();

creates a normal user.


Step 3: Register Users Inside InMemoryUserDetailsManager


	return new InMemoryUserDetailsManager(admin, user);


--Spring Security stores both users in memory and uses them during authentication.


Note: Internally, the passwords are stored as BCrypt hashes, not as plain text.



Advantages of InMemoryUserDetailsManager:
-----------------------------------------

Easy to configure
No database required
Suitable for demos and testing
Supports multiple users
Supports roles and authorities

Limitations:
------------

User data is lost when the application stops.
Not suitable for production systems.
Users cannot be managed dynamically.
Does not persist data in a database.




***Note: Once a custom UserDetailsService implementation (such as InMemoryUserDetailsManager) is configured as a Spring Bean, 
Spring Boot's default user configuration using 

spring.security.user.name 
and 
spring.security.user.password 

inside application.properties file will be disabled. 

--Authentication will be performed only against the users configured inside the custom InMemoryUserDetailsManager.

CORS Filter:
-------------

CORS stands for:

	Cross-Origin Resource Sharing

Example

Frontend:

	http://localhost:3000

Backend:

	http://localhost:8080

--Different ports mean different origins.

--Browser blocks the request unless the server explicitly allows it.

The CorsFilter decides:

Allow
or
Reject

--cross-origin requests.


CSRF Filter:
------------

CSRF stands for:

	Cross-Site Request Forgery

What Problem Does It Solve?

Suppose:

User logged into bank.com

Browser contains:

	JSESSIONID

--A malicious website tricks the browser into sending a request to:

bank.com/transferMoney

--The browser automatically sends the session cookie.

The bank thinks:

Valid Session
Valid User

--and may execute the operation.

This attack is called:

CSRF Attack


Protection:

--Spring Security automatically enables CSRF protection for state-changing requests such as:

POST
PUT
PATCH
DELETE

--If the CSRF token is missing:

	403 Forbidden


Generally we Disable CSRF in REST APIs:

You'll often see:

	http.csrf(csrf -> csrf.disable());

because:

--REST APIs are usually stateless.
--Authentication is often done using JWT tokens.
--Session-based CSRF attacks are less relevant.

We'll study CSRF in detail later.

Why So Many Components?
-----------------------

Many beginners ask:

Why doesn't Spring Security simply check username and password directly?

--Because Spring Security supports multiple authentication mechanisms:

Username & Password
LDAP Authentication
OAuth2
JWT Authentication
SSO Authentication
Custom Authentication

--To support all these mechanisms, Spring Security follows the:

Separation of Responsibilities

principle.

--Each component has a specific job.


1. User Sends Login Request

--When a user tries to log in, they send their credentials (username and password) to the Spring Boot application.

POST /login

{
   "username":"ratan",
   "password":"1234"
}

The request first enters:

Spring Security Filter Chain



2. UsernamePasswordAuthenticationFilter

--Inside the Security Filter Chain, there is a filter called:

	UsernamePasswordAuthenticationFilter

This filter is responsible for:

--Extracting username and password from the incoming request
--Creating an "Authentication" object
--Passing that object to AuthenticationManager for authentication





3. Creating Authentication(I) Object

The UsernamePasswordAuthenticationFilter filter creates an object of:

	UsernamePasswordAuthenticationToken

which is an implementation class of the Authentication interface.

Authentication authentication = new UsernamePasswordAuthenticationToken(username,password);


State before authentication

Principal  = Username
Credentials = Password
Authenticated = false
Authorities = null

At this point:

The user is NOT authenticated yet.



4. Calling AuthenticationManager

After creating the Authentication object, the filter calls:

Authentication authenticate(Authentication authentication);

Example:

authenticationManager.authenticate(authentication);



5. AuthenticationManager

AuthenticationManager is an interface.

public interface AuthenticationManager {

    Authentication authenticate(Authentication authentication);
}

Default implementation:

ProviderManager class

--This class will act like a dispatcher..

Its responsibility is:

Receive Authentication object
Find suitable AuthenticationProvider
Delegate authentication work



--Spring Security supports different authentication mechanisms.

Examples:

DaoAuthenticationProvider
LdapAuthenticationProvider
JwtAuthenticationProvider
CustomAuthenticationProvider

--Each provider knows how to authenticate users using a specific mechanism.


6. AuthenticationProvider

--ProviderManager checks the available AuthenticationProviders.

AuthenticationProvider

Common providers are:

DaoAuthenticationProvider
LdapAuthenticationProvider
JwtAuthenticationProvider
CustomAuthenticationProvider

--Default provider used for username/password authentication:

DaoAuthenticationProvider

--You can also create your own provider:

}

Authority and Role:
===================

--Spring Security supports two authorization concepts:

1. Authority
2. Role




1. Authority
-------------

--An Authority represents a specific permission or privilege granted to a user.

Examples:

READ_EMPLOYEE
WRITE_EMPLOYEE
DELETE_EMPLOYEE
CREATE_ORDER
VIEW_REPORTS

--In Spring Security, authorities are represented by the GrantedAuthority interface.


Example:

		UserDetails user= User.builder()
				.username("user")
				.password(passwordEncoder.encode("1234"))
				.authorities("READ_EMPLOYEE", "WRITE_EMPLOYEE")
				.build();


Here the user has two authorities:

READ_EMPLOYEE
WRITE_EMPLOYEE



2. Role:
--------

--A Role is a collection/group of authorities.

Examples:

ADMIN
MANAGER
USER

Typically:

ADMIN
 ├── READ_EMPLOYEE
 ├── WRITE_EMPLOYEE
 └── DELETE_EMPLOYEE

USER
 └── READ_EMPLOYEE


Role indicates:

	Who the user is

Authority indicates:

	What the user can do



Special Behavior of Roles in Spring Security:
---------------------------------------------

When you write:

	.hasRole("ADMIN")

Spring automatically converts it to:

	.hasAuthority("ROLE_ADMIN")

Notice the prefix:

ROLE_

--Spring treats roles as authorities with the prefix ROLE_


Example:

		UserDetails user= User.builder()
				.username("admin")
				.password(passwordEncoder.encode("1234"))
				.roles("ADMIN")
				.build();

Internally Spring stores:

ROLE_ADMIN

as an authority.



hasRole() vs hasAuthority():
----------------------------

Using Role:


.requestMatchers("/employees")
.hasRole("ADMIN")

Spring checks:

ROLE_ADMIN


Using Authority:

.requestMatchers("/employees")
.hasAuthority("ROLE_ADMIN")

--This performs the same authorization check.



Fine-Grained Access with Authorities
-------------------------------------

--Roles are often too broad.

Example:

Instead of:

ADMIN
MANAGER
HR

we can define specific permissions.



.requestMatchers(HttpMethod.GET, "/employees")
.hasAuthority("READ_EMPLOYEE")

.requestMatchers(HttpMethod.POST, "/employees")
.hasAuthority("CREATE_EMPLOYEE")

.requestMatchers(HttpMethod.DELETE, "/employees/**")
.hasAuthority("DELETE_EMPLOYEE")

--Now access depends on permissions rather than job titles.

package com.hdfc.controller;

import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.security.authentication.AuthenticationManager;
import org.springframework.security.authentication.UsernamePasswordAuthenticationToken;
import org.springframework.security.core.Authentication;
import org.springframework.security.core.context.SecurityContext;
import org.springframework.security.core.context.SecurityContextHolder;
import org.springframework.security.web.context.HttpSessionSecurityContextRepository;
import org.springframework.web.bind.annotation.PostMapping;
import org.springframework.web.bind.annotation.RequestBody;
import org.springframework.web.bind.annotation.RestController;

import com.hdfc.dto.LoginDTOBean;

import jakarta.servlet.http.HttpServletRequest;
import jakarta.servlet.http.HttpSession;

@RestController
public class LoginController {

    private  AuthenticationManager authenticationManager;

    LoginController(AuthenticationManager authenticationManager) {
        this.authenticationManager = authenticationManager;
    }

    @PostMapping("/signIn")
    public String loginHandler(@RequestBody LoginDTOBean loginBean, HttpServletRequest req) {

    	Authentication unAuth = new UsernamePasswordAuthenticationToken(loginBean.getUsername(), loginBean.getPassword());
    	
        Authentication auth = authenticationManager
					.authenticate(unAuth);

        if(auth.isAuthenticated()) {

            SecurityContext sc = SecurityContextHolder.getContext();

            sc.setAuthentication(auth);

            HttpSession session = req.getSession(true);

            session.setAttribute(HttpSessionSecurityContextRepository.SPRING_SECURITY_CONTEXT_KEY, sc);

            return "Authentication Successful";
        }

        return "Authentication Failed";
    }

}

PasswordEncoder & BCrypt Deep Dive:
===================================

Why Do We Need Password Encoding?

--Suppose we store user information in a database.



User Table:

| Username | Password   |
| -------- | ---------- |
| admin    | 1234       |
| ratan    | welcome123 |
| john     | password   |




Problem

If a hacker gains access to the database:

Username   Password
------------------
admin      1234
ratan      welcome123
john       password

all passwords become immediately visible.

This is a major security risk.

Real World Rule:

--Never Store Passwords in Plain Text

Instead store: Hashed password.


What is Hashing?
-----------------

--Hashing converts data into a fixed-length string.

Example:

1234
↓
A1B2C3D4E5F6...

--The important property:

Input
  |
  v
Hash Function
  |
  v
Hash Value



One-Way Process:
----------------

--Hashing is designed to be:

One Way

Meaning:

Password
   |
   v
 Hash

--is possible.

But:

 Hash
   |
   v
Original Password


--is practically impossible.


Hashing vs Encryption:
-----------------------

Students often confuse these concepts.

Encryption:


Original Data
      |
      v
Encryption Key
      |
      v
Encrypted Data

--Can be reversed.

Encrypted Data
       |
       v
Decryption Key
       |
       v
Original Data


Example:

Hello
↓
X7P2K8L9
↓
Hello

--using the decryption key.


Hashing:

Password
     |
     v
Hash Function
     |
     v
Hash Value

--Cannot be reversed.

--No decryption key exists.




Q/- Why are passwords hashed instead of encrypted?

--Because applications never need to recover the original password.

--They only need to verify whether the entered password is correct.


PasswordEncoder Interface:
--------------------------

--Spring Security provides:

	PasswordEncoder interface.

Methods:

public interface PasswordEncoder {

    String encode(CharSequence rawPassword);

    boolean matches(
            CharSequence rawPassword,
            String encodedPassword
    );

}


Responsibilities

1. encode()

Used during:

	User Registration

2. matches()

Used during:

	User Login


BCryptPasswordEncoder:
----------------------

--Most commonly used PasswordEncoder implementation.

	BCryptPasswordEncoder


Creating Bean:
--------------

@Bean
PasswordEncoder passwordEncoder() {

    return new BCryptPasswordEncoder();

}


BCrypt provides:

Strong Hashing
Automatic Salt Generation
Protection against Rainbow Table Attacks
Industry Standard



Encoding Passwords:
--------------------

Example:

String encodedPassword = passwordEncoder.encode("1234");

Output:

$2a$10$O4s9hF8YjT....


Important Observation

Run again:

passwordEncoder.encode("1234");

Output:

$2a$10$L8xT7Ks9Ab....


Same Password, Different Hash

Input: 1234

Output 1:

$2a$10$AAA....

Output 2:

$2a$10$BBB....

Output 3:

$2a$10$CCC....


--Because BCrypt automatically generates a:

Salt

for every password.


--Salt is a random value added to the password before hashing.


Without Salt:

1234
↓
HASH_ABC

Another user:

1234
↓
HASH_ABC

--Same password → Same hash.


With Salt:

1234 + RandomSalt1
↓
HASH_XYZ

1234 + RandomSalt2
↓
HASH_PQR

--Different hashes are generated.


Why Salt Is Important?

Suppose:

100 users

have:

1234

as their password.

Without salt:

All 100 users
        |
        v
  Same Hash

--A hacker immediately knows many users share the same password.


With salt:

User1 -> Hash A
User2 -> Hash B
User3 -> Hash C

--Even though the password is identical.
