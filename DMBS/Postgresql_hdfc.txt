Problems with Flat Files:
-------------------------

1. Data Redundancy: 

--Same data gets repeated multiple times.

2. Data Inconsistency:

--One file containts "Ravi Kumar" whereas another file contains "Ravi K"

3. Data Retrieval:

--Finding one customer among lakhs of records becomes difficult.

4. Poor Security

--Anyone can modify the file.

5. Difficult Maintenance

--Updating thousands of files becomes difficult.

6. Data Integrity Issues

--No guarantee that correct data is entered.

Example:

Age = -50

--Flat files cannot effectively prevent such invalid data.


To overcome the limitations of Flat Files: 


--To overcome the above limitations DBMS softwares are introduced.

Types of Data Models:
--------------------

There are three major data models are there:

1. Hierarchical Model

2. Network Model

3. Relational Model



Hierarchical Model:
------------------

--In Hierarchical Model, data is organized in a tree-like structure.

--Here one root element will be there and for one root there can be multiple childs elements.

--This model is also called as parent-child hierarchical model.

Example:

	College
     [name|address]   
	    |
	Department
       [dno|name]
            |
--------------------------------
|				|
Course			      Student
[cno|name|duration]	     [sno|name|address]
   |
Faculty
[id|name] 


The biggest limitation of this model is: 

Not all data naturally follows a parent-child relationship.

Example:

Suppose:

Student
Course

A student can enroll in multiple courses.

A course can have multiple students.

--This relationship cannot be represented efficiently using a simple hierarchy.


2. Network Model:
-----------------

--In Network Model, entities are represented as nodes and connected through relationships.

--Here we gets a graph like structure.

Example:

Student
 /   \
/     \
Java  Spring
 \    /
  \  /
 Teacher


Limitations:

1. Not suitable for large amounts of data and relationships.

2. Complex to design

3. Complex to maintain

DBMS Architecture:
==================

ANSI (American National Standards Institute) proposed a Three-Level Architecture for DBMS.

This architecture is also known as:

ANSI/SPARC Architecture


Objective of DBMS Architecture:
---------------------------------

The main objective of DBMS Architecture is:

--To separate the user's view of data from the way data is physically stored.

Benefits:

Data Abstraction
Security
Flexibility
Data Independence


Three Levels of DBMS Architecture:
----------------------------------

1. External Level
2. Conceptual Level
3. Internal Level


External Level
     ↑
Conceptual Level
     ↑
Internal Level




1. Conceptual Level:
--------------------

--The Conceptual Level provides the logical view of the entire database.

--It is the most important level for Database Developers.

It describes:

What data should be stored
Data Types
Constraints
Relationships
Business Rules

It does NOT describe:

--How data is physically stored

Example:

CREATE TABLE employee
(
emp_id INT PRIMARY KEY,
name VARCHAR(100) NOT NULL,
salary NUMERIC(10,2)
);

The above definition specifies:

Data Type
Primary Key
NOT NULL Constraint

--Therefore it belongs to the Conceptual Level.

Relationship Example:

CREATE TABLE department
(
dept_id INT PRIMARY KEY
);

CREATE TABLE employee
(
emp_id INT PRIMARY KEY,
dept_id INT REFERENCES department(dept_id)
);

--The Foreign Key relationship is also part of the Conceptual Level.


2. External Level:
------------------

--The External Level provides customized views of data to different groups of users.

Purpose:

Security
Restricted Access
Simplified Data Access

Example:

--Suppose we have the following table:

Item

item_no
item_name
price
quantity

Customer View:

item_name
price

Manager View:

item_name
price
quantity

Different users can access different portions of the same data.

Example using SQL View:

CREATE VIEW customer_view AS
SELECT item_name, price
FROM item;


--The customer can access only the view instead of the complete table.

Important Point:

External Level is mainly used for:

Security
Controlled Data Access
User-Specific Views


3. Internal Level:
------------------

--The Internal Level describes how data is physically stored inside the database.

--It is the lowest level of the architecture.

It includes:

Storage Files
Data Pages
Disk Blocks
Index Structures
Storage Allocation

Managed By:

Database Engine
DBA

Example:

When we create:

CREATE TABLE employee(
emp_id INT,
name VARCHAR(100)
);


--The developer only sees the table.

Internally PostgreSQL decides:

Which file stores the table
Which page stores the data
Which block stores the page

--These decisions belong to the Internal Level.

Important Point:

--The Internal Level focuses on physical storage optimization.




Data Independence:
------------------

--It means, Changes at one level should not affect higher levels.

--There are two types of Data Independence based on the 3-level ANSI/SPARC architecture:

1. Logical Data Independence
2. Physical Data Independence



1. Logical Data Independence:
-----------------------------

--Changes in the Conceptual Level should not affect the External Level.

Example:

employee table:

id
name
salary

Later:

ALTER TABLE employee ADD COLUMN email VARCHAR(100);

Even after adding the new column:

Customer View:

id
name
salary

--continues to work without modification.

This property is called: Logical Data Independence

Benefit:

--Changes in the database design should not require changes in user views.



2. Physical Data Independence:
------------------------------

--Changes in the Internal Level should not affect the Conceptual Level.

Example:

The DBA may:

Move data files
Reorganize storage
Rebuild indexes
Change storage locations

Despite these changes:

CREATE TABLE employee
(
emp_id INT,
name VARCHAR(100)
);

--remains unchanged.

--Application code also remains unchanged.

This property is called: Physical Data Independence

Benefit:

--Storage-related changes do not impact database design or application logic.



Introduction to PostgreSQL:
==========================

--PostgreSQL (pronounced as Post-Gres-Q-L) is an open-source Relational Database Management System (RDBMS) software used to store, manage, and retrieve data efficiently.

--It follows the Relational Model proposed by Dr. E. F. Codd and stores data in the form of related tables.


History of PostgreSQL:
---------------------

--PostgreSQL originated from the POSTGRES project at:

University of California, Berkeley

The project was led by: Michael Stonebraker

--Over time, PostgreSQL evolved into one of the most powerful open-source databases.



Why PostgreSQL is Popular?

Because it provides:

Reliability
Security
Performance
Scalability
Open Source

--without licensing costs.

-----------------------------

1. Open Source:

--Free to use.

--No license cost.

Example:

PostgreSQL = Free

2. ACID Compliance:

--PostgreSQL follows ACID properties.

A → Atomicity
C → Consistency

D → Durability

--This ensures safe transactions.

3. Supports Large Databases:

Can handle:

Millions of Records

Terabytes of Data


4. Strong Security

Supports:

Users

5. Supports Advanced SQL:

--PostgreSQL provides:

Transactions


6. Cross Platform:

Works on:

7. Extensible

Supports:

Custom Functions

precision = total digits

-----------------

NUMERIC → Exact
FLOAT   → Approximate

Always prefer NUMERIC

SQL Fundamentals & SQL Categories:
==================================

What is SQL?
------------

SQL stands for:

	Structured Query Language

--SQL is a standard language used to communicate with Relational Databases.


Using SQL we can:

Create Databases
Create Tables
Store Data
Retrieve Data
Update Data
Delete Data
Manage Security
Control Transactions


SQL commands are divided into five categories:

1. DDL: Data Definition Language
2. DML: Data Manipulation Language
3. DQL: (DRL) Data Query Language
4. DCL: Data Control Language
5. TCL: Transaction Control Language


1. DDL (Data Definition Language):
-----------------------------------

--DDL commands are used to define and modify database structures.

These commands work on:

Database
Table
Schema
Constraints


Common DDL Commands:

CREATE
ALTER
DROP
TRUNCATE
RENAME


CREATE:
-------

--Used to create database objects.

Create Database:

	CREATE DATABASE training_db;

Create Table:

CREATE TABLE employee
(
    emp_id INT,
    emp_name VARCHAR(100)
);



ALTER:
-----

--Used to modify existing structures.

Add New Column:

	ALTER TABLE employee ADD COLUMN salary NUMERIC(10,2);


DROP:
-----

--Used to permanently remove objects.

Drop Table:

	DROP TABLE employee;

TRUNCATE:
----------

--Removes all rows but keeps table structure.

	TRUNCATE TABLE employee;




2. DML (Data Manipulation Language)
------------------------------------

--DML commands manipulate the data stored inside tables.

Common DML Commands:

INSERT
UPDATE
DELETE



INSERT:
--------

--Used to add data.

Example1: Inserting all the columns

	INSERT INTO employee VALUES(101,'Ravi');

Example2: Inserting specific columns values


	INSERT INTO employee(name) VALUES('Ravi');



UPDATE:
------

--Used to modify existing data.

	UPDATE employee SET emp_name='Amit' WHERE emp_id=101;



DELETE:
-------

--Used to remove records.

	DELETE FROM employee WHERE emp_id=101;

	DELETE FROM employee; //Delete all the records



3. DQL (Data Query Language):
-------------------------------

--Used to retrieve data from database tables.

Main Command: SELECT

Retrieve All Records:

	SELECT * FROM employee;


Retrieve Specific Columns:

	SELECT emp_id, emp_name FROM employee;

Retrieve records based on condition: Using where clause.

	SELECT * FROM employee where address = 'delhi';



4. DCL (Data Control Language)
------------------------------

--DCL commands control access and permissions.

Used by:

DBA (Database Administrators)

Common Commands:

GRANT
REVOKE


Provides permissions.

Example:

	GRANT SELECT ON employee TO user1;

Removes permissions.

Example:

	REVOKE SELECT ON employee FROM user1;


5. TCL (Transaction Control Language)
--------------------------------------

--TCL commands control database transactions.

--A transaction is a group of SQL statements executed as a single unit.


Real Time Example

Bank Transfer:

Withdraw 1000
Deposit 1000

Both operations should succeed together.

Common TCL Commands:

BEGIN
COMMIT
ROLLBACK
SAVEPOINT

Consider the following table:

CREATE TABLE employee
(
    emp_id INT,
    name VARCHAR(100),
    salary NUMERIC(10,2),
    address VARCHAR(50)
);


where clause:
============

--Used to filter the records based on condition:

Example:

Employees with salary above 60000

	SELECT * FROM employee WHERE salary > 60000;


Comparison Operators:
--------------------

| Operator | Meaning            |
| -------- | ------------------ |
| =        | Equal              |
| >        | Greater Than       |
| <        | Less Than          |
| >=       | Greater Than Equal |
| <=       | Less Than Equal    |
| <>       | Not Equal          |


Multiple Conditions:
-------------------

1. AND

--Both conditions must be true.

	SELECT * FROM employee WHERE address='delhi' AND salary > 50000;


2. OR

	SELECT * FROM employee WHERE address='delhi' OR salary > 50000;


3. NOT

Reverse condition.

SELECT * FROM employee WHERE NOT address='delhi';


4. IN Operator

--Used when checking multiple values.

Instead of:

WHERE address='delhi' OR address='mumbai' OR address='chennai'

Use:

	SELECT * FROM employee WHERE address IN ('delhi','mumbai','chennai');


5. BETWEEN Operator

--Used for ranges.

	SELECT * FROM employee WHERE salary BETWEEN 50000 AND 70000;


6. LIKE Operator

--Used for pattern matching.

Names starting with R

	SELECT * FROM employee WHERE name LIKE 'R%';

Names ending with a

	SELECT * FROM employee WHERE name LIKE '%a';

Wildcards:
----------

% -> Any number of characters
_ -> Single character





7. NULL Check

--Retrieve employees whose address is NULL

	SELECT * FROM employee WHERE address IS NULL;

Not NULL

	SELECT * FROM employee WHERE address IS NOT NULL;



8. ORDER BY Clause:

--Used to sort results.

Ascending Order

(Default)

	SELECT * FROM employee ORDER BY salary;


Equivalent to:

	SELECT * FROM employee ORDER BY salary ASC;


Descending Order:

	SELECT * FROM employee ORDER BY salary DESC;


Multiple Columns Sorting:
-------------------------

SELECT * FROM employee ORDER BY address, salary DESC;

First sort by:

address

Then within each address:

salary DESC


9. LIMIT Clause

--Used to restrict the number of rows returned.


Retrieve first 3 rows.

SELECT * FROM employee LIMIT 3;

Example:

Highest Salary Employee

	SELECT * FROM employee ORDER BY salary DESC LIMIT 1;


10. OFFSET Clause

--Used to skip rows before returning results.


Example:

SELECT * FROM employee OFFSET 2;

Skips:

Row 1
Row 2

--Returns remaining rows.


11. LIMIT + OFFSET

--Very important for pagination.

Example

	SELECT * FROM employee LIMIT 2 OFFSET 2;

Meaning:

Skip first 2 rows
Return next 2 rows



Real Time Example (Pagination):
--------------------------------

Page Size: 2 records 


Page 1:

	SELECT * FROM employee LIMIT 2 OFFSET 0;

Page 2:

	SELECT * FROM employee LIMIT 2 OFFSET 2;

Page 3:

	SELECT * FROM employee LIMIT 2 OFFSET 4;

This concept is heavily used in:

Spring Data JPA Pagination
Pageable
PageRequest

-------------------------

	SELECT * FROM employee WHERE salary > 50000 ORDER BY salary DESC LIMIT 3;
