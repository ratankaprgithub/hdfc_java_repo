
 

Web Application Architecture:
============================


--A Web Application is a software application that runs on a server and is accessed through a web browser.

Examples:

Gmail
Facebook
Instagram
Amazon
Flipkart
Internet Banking Portal
HDFC Employee Portal

--Instead of installing software on every user's machine, users simply open a browser and access the application.


Browser ---> Server ---> Database

Browser <--- Server <--- Database



Browser sends Request.

Server processes Request.

Database stores data.

Server sends Response.

Browser displays Response.



Client-Server Architecture:
--------------------------

--Web Applications follow Client-Server Architecture.


Client:
--------

--Client requests services.

Examples:

Chrome Browser
Firefox
Mobile App
Angular Application
React Application


Server:
-------

--Server provides services.
--The backend application deployed inside the server


Examples:

Spring Boot Application
ASP.NET Application
NodeJS Application



Types of Web Applications:
==========================

--Web applications are broadly classified into two categories:

1. Server-Side Rendered (SSR) Applications
2. REST API Based Applications (Client-Side Applications)




Type 1: Server Side Rendered Applications:
------------------------------------------

--In this architecture, both data processing and UI generation happen on the server.

--The server receives the request, processes the business logic, generates the complete HTML page, and sends it back to the browser.

--The browser's (Client) responsibility is mainly to display the HTML received from the server.


Technologies:

JSP
Servlet
Thymeleaf
Freemarker
PHP



Flow:

	   Http Request
Browser------------------------>Web server(contains application logic + HTML page generated)
      <------------------------
	   Http Response



--Server generates HTML.

--Browser simply displays it.

--Here, Client receives ready-made HTML.


Response Example:

<html>
<body>
    <h1>Welcome To HDFC Life</h1>
</body>
</html>


--Generated by server.


Real Life Analogy:
------------------


--Imagine a customer visiting a restaurant.

Customer places an order.
Kitchen prepares the complete meal.
Food is served fully prepared.
Customer simply consumes it.

Similarly,

--Server prepares Data + View
--Browser simply displays it



Advantages:

Easy to develop for small applications
Less JavaScript required
Suitable for traditional business applications


Limitations:

UI and backend are tightly coupled
Difficult to support multiple clients (Web, Mobile, Tablet)
Page reload occurs frequently
Reusability is limited


Typical Examples:


Banking Portals
Internal Company Portals
Government Websites
Employee Management Systems



Type 2: REST API Based Applications:
-------------------------------------

--This is the most commonly used architecture in modern enterprise applications.


In this approach:

--Backend only provides data.

--Frontend is responsible for generating the user interface.

The backend exposes REST APIs that return data in JSON or XML format instead of Generating the full fledge HTML (view).

--Multiple clients can consume the same APIs.




Frontend Technologies:

React
Angular
Vue.js
Android Applications
iOS Applications



Backend Technologies:

Spring Boot
NodeJS (ExpressJS)
ASP.NET
Django



Architecture:

React
     \
      \
       Spring Boot REST API
      /
     /
Mobile App/ Other backend Apps


--A single backend can serve multiple frontend applications.



Response Example:

--Instead of HTML, the server returns JSON data:


{
  "id":101,
  "name":"Raj",
  "salary":50000
}



--The frontend decides how this data should be displayed.



For example:

React may show it in a table.
Mobile app may show it in a card layout.
Another system may consume it for further processing.




Real Life Analogy:
-----------------

--Consider a restaurant that only provides packaged food.

--The restaurant does not decide where or how you consume it.

You can:

Eat it at home
Eat it in a hotel
Use it to prepare another dish

Similarly:

--Backend provides only data.
--Different clients decide how to use or display that data.




Advantages:

Frontend and backend are completely independent
Same APIs can be reused by multiple applications
Better scalability
Easier maintenance
Excellent mobile support
Faster and richer user experience



Limitations:

Requires separate frontend development
More technologies to learn
Initial setup is slightly complex








Comparison:
-----------

| Feature             | Server-Side Rendered (JSP/Thymeleaf) | REST API Based          |
| ------------------- | ------------------------------------ | ----------------------- |
| UI Generation       | Server                               | Frontend                |

| Frontend Dependency | Coupled with Backend                 | Independent             |

| Page Refresh        | Frequent                             | Minimal                 |
| Suitable For        | Traditional Web Apps                 | Enterprise Applications |



--Today, most enterprise applications follow the following architecture:


React + Spring Boot Rest API

or

or

Mobile App + Spring Boot Rest API



Note: Internally, Spring Boot uses the Spring MVC module to build web applications.

Therefore, using Spring Boot we can develop both types of web applications:

1. Server-Side Rendered Applications

--Where Spring MVC generates dynamic HTML pages using technologies such as:

JSP

--In this approach, the server generates the complete HTML page and sends it to the browser.



2. REST API Based Applications

--Where Spring MVC exposes REST endpoints and returns JSON/XML data.

--In this approach, the backend provides only data and the frontend is responsible for generating the user interface.


Conclusion:

--Spring Boot can be used for:

Traditional Web Applications (JSP, Thymeleaf, Freemarker)
RESTful Web Services
Microservices
Backend APIs for Web and Mobile Applications


--The choice depends on the project requirements, but in modern enterprise applications, Spring Boot is predominantly used for developing REST APIs and Microservices, while frontend applications are developed separately using technologies such as React, Angular, or Mobile Apps.




Layered Architecture in Spring Boot Applications:
=================================================


--Almost every business application performs the following three major activities:


1. Data Management

--The application needs to store, retrieve, update, and delete business data from a database.

Examples:

Customer information
Employee records
Insurance policy details
Transaction details

--The logic responsible for interacting with the database is called Data Access Logic.

2. Business Processing

--The application must process data according to business rules defined by the organization.

Examples:

Calculating insurance premiums
Validating loan eligibility
Processing salary calculations
Applying discounts and taxes

--The logic responsible for implementing these business rules is called Business Logic.


3. Data Presentation

--The application must present information in a user-friendly format.

Examples:

Displaying employee details
Showing policy information
Returning API responses
Rendering web pages

--The logic responsible for interacting with users or client applications is called Presentation Logic.


Technically, all the above logic can be written in a single class.

However, this approach creates several problems:

--All responsibilities get mixed together.

--Code becomes difficult to understand and maintain.

--A change in one part may affect other parts.

--Parallel development becomes difficult.

--Unit testing becomes complex.

--Code reusability is reduced.

--Application becomes tightly coupled.




Solution: Layered Architecture


--To overcome these problems, a business application is divided into multiple logical layers.

Each layer is responsible for a specific task.

In Spring Boot applications, we generally follow a 3-Layer Architecture:


 Presentation Layer (Controller) <----------> Business Layer( Service) <-------------> Data Access Layer (Repository / DAO) <----------> Database


1. Presentation Layer (Controller Layer):
-----------------------------------------

--The Presentation Layer is responsible for communicating with the external world(Client).

--In Spring Boot, this layer is typically implemented using:

@Controller
@RestController


Responsibilities:

Accept client requests.
Collect input data.
Validate request parameters.
Call service layer methods.
Return responses to clients.
       

Example:


@RestController
public class EmployeeController {

    @Autowired
    private EmployeeService service;

    @GetMapping("/employees")
    public List<Employee> getEmployees() {
        return service.getAllEmployees();
    }
}


Key Point:

--The controller should contain minimal business logic.

--Its primary responsibility is request handling and response generation.


2. Business Layer (Service Layer):
---------------------------------

--The Service Layer contains the business rules of the application.

--In Spring Boot, this layer is implemented using:

@Service


Responsibilities:

Implement business rules.
Perform validations.
Process data.
Coordinate multiple repository calls.
Manage transactions.


Example:


@Service
public class EmployeeService {

    @Autowired
    private EmployeeRepository repository;

    public List<Employee> getAllEmployees() {

        // Business logic can be written here

        return repository.findAll();
    }
}



Key Point:

--This layer acts as a bridge between the Controller Layer and Repository Layer.



3. Data Access Layer (Repository Layer):
----------------------------------------

--The Data Access Layer is responsible for communicating with the database.

--In Spring Boot, this layer is generally implemented using:

@Repository

Responsibilities:

Insert data.
Update data.
Delete data.
Retrieve data.
Execute database queries.


Example:

@Repository
public interface EmployeeRepository extends JpaRepository<Employee, Integer> {

}


Key Point:

--This layer should focus only on database operations and should not contain business logic.




HTTP protocol:
=============

--Before understanding HTTP, we must understand the term Protocol.

--A Protocol is a set of rules that define how two systems communicate with each other.


Real-Life Analogy:
------------------

--Suppose two people are talking on the phone.

Both must follow certain rules:

--One person speaks at a time.
--Both understand the same language.
--Communication follows a specific format.

Without rules, communication becomes impossible.

Similarly, computers also need rules to communicate.

These rules are called Protocols.


Examples of Protocols:
----------------------

| Protocol | Purpose                  |
| -------- | ------------------------ |
| HTTP     | Web Communication        |
| HTTPS    | Secure Web Communication |
| FTP      | File Transfer            |
| SMTP     | Sending Emails           |
| TCP/IP   | Network Communication    |


What is HTTP?
-------------

HTTP stands for: 

Hyper Text Transfer Protocol

--It is the protocol used for communication between:



		Http Request
Client <--------------------------> Server
		Http Response


--Whenever you access a website or call a REST API, HTTP is used behind the scenes.


Examples:

When you open:

https://www.google.com
https://www.amazon.in
https://www.hdfclife.com



--your browser sends HTTP requests.

--The server sends HTTP responses.


Client-Server Communication:
-----------------------------

--Every web application follows the Request-Response model.


Client:

--The client initiates the communication by sending requests(Http request).


Examples:

Chrome
Firefox
Edge
Mobile App
React Application
Angular Application


Server:

--The server receives requests, processes them, and returns responses.

--Server hosts the backend applications.

Examples:

Spring Boot Application
NodeJS Application
ASP.NET Application
Django Application


HTTP Request:
============

An HTTP Request is sent by the client to the server.

--It contains information such as:

Which resource is required?
Which operation should be performed?
Additional metadata about the request.
Request data (if any).




Structure of HTTP Request:
-------------------------

1. Request Line (HTTP method: Resource URI: HTTP version)

2. Request Headers

3. Request Body



Example Request:

GET /employees HTTP/1.1

Host: localhost:8080
User-Agent: Chrome




Request Line:
--------------

GET /employees HTTP/1.1

Contains:

HTTP Method
Resource URI
HTTP Version



Request Headers:
----------------

--Headers provide additional information about the request.

Common Request Headers:

| Header          | Purpose                        |
| --------------- | ------------------------------ |
| Host            | Target server                  |
| User-Agent      | Client application information |
| Accept          | Expected response format       |
| Content-Type    | Format of request body         |
| Authorization   | Authentication token           |
| Cookie          | Session information            |
| Accept-Language | Preferred language             |




Example:

Host: localhost:8080
User-Agent: Chrome
Accept: application/json
Authorization: Bearer eyJhb...





Request Body:
-------------

--The request body contains data sent from the client to the server. (like form data, files, images, etc).

Mostly used with following HTTP methods:

POST
PUT
PATCH


Example:

{
   "name":"Ratan",
   "salary":50000
}





HTTP Response:
=============

--After processing the request, the server sends an HTTP Response.


The response contains:

Request result
Status information
Response data


Structure:
----------

1. Status Line (Status Code: Status Description: HTTP version)

2. Response Headers

3. Response Body


Example:

200 OK HTTP/1.1

Content-Type: application/json
Content-Length: 45

{
  "id":101,
  "name":"Ratan"
}



Status Line:
-------------

It contains:

Status Code
Status Message
HTTP Version

Example:

200 OK HTTP/1.1

--Indicates request success.



Response Headers:
-----------------

--Response headers provide additional information about the response.

Common Response Headers:


| Header         | Purpose                  |
| -------------- | ------------------------ |
| Content-Type   | Type of response data    |
| Content-Length | Size of response         |
| Date           | Response generation time |
| Server         | Server information       |
| Cache-Control  | Caching instructions     |
| Set-Cookie     | Creates session cookies  |
| Location       | Redirect URL             |




Example:

Content-Type: application/json
Content-Length: 250
Date: Tue, 01 Sep 2026
Server: Apache Tomcat


Response Body:
--------------


--Contains the actual data returned by the server.

Example:


{
   "id":101,
   "name":"Ratan"
}




HTTP Methods:
============

-HTTP provides different methods to perform different operations on resources.


1. GET Method:

--Used to retrieve data from the server.

Example:

GET /employees

Use Cases:

Fetch Employee Details
Search Products
View Customer Information


Characteristics:

--Read Only Operation
--Should not modify data.



2. POST Method:

--Used to create new resource.

Example

POST /employees

Request Body:

{
   "name":"Ratan",
   "salary":50000
}


Banking Example:

--Open New Account

Characteristics:

--Creates New Resource



3. PUT Method:

--Used to completely update an existing resource.


Example:


PUT /employees/101

{
   "name":"Ratan Kumar",
   "salary":70000
}


Banking Example:

--Updating complete customer profile information.



4. PATCH Method:

--Used to partially update a resource.


Example:

Current Employee:

{
   "name":"Ratan",
   "salary":50000
}

--Update only salary:

PATCH /employees/101

{
   "salary":70000
}




5. DELETE Method:

--Used to remove a resource.

Example:

DELETE /employees/101

Examples:

Delete Product
Remove Employee Record
Close Bank Account




GET vs POST vs PUT vs DELETE:
------------------------------

| Method | Purpose                |
| ------ | ---------------------- |
| GET    | Read Data              |
| POST   | Create Data            |
| PUT    | Update Entire Resource |
| PATCH  | Partial Update         |
| DELETE | Remove Data            |



HTTP Status Codes:
=================

--Status codes indicate the result of request processing.


200 Series (Success):
--------------------

--Request processed successfully.


200 OK: Request Successful

Example:

	GET /employees

Returns the Employees data successfully.

201 Created: Resource Created Successfully

Example:

	POST /employees


204 No Content: Success but no response body

Example:

	DELETE /employees/1




400 Series (Client Errors):
--------------------------

--Problem exists in the client request.


400 Bad Request: Invalid request data.

Example:

{
  "salary":"abc"
}


401 Unauthorized: Authentication required.

Example:

--User not logged in


403 Forbidden: User authenticated but not allowed.

Example:

	Employee accessing Admin Page.


404 Not Found: Resource does not exist.

Example:

GET /employees/9999


405 Method Not Allowed


500 Series (Server Errors):
--------------------------

--Problem exists on the server side.


500 Internal Server Error

--Unexpected server-side exception.


502 Bad Gateway

503 Service Unavailable


Example:

Database connection failure
NullPointerException
Unexpected server crash




Evolution of Java Web Application Development:
=============================================

--Over the years, Java web application development has become simpler and more developer-friendly. The journey can be broadly divided into three stages:

1. Traditional Servlet-Based Applications

2. Spring MVC Applications

3. Spring Boot Applications


1. Traditional Servlet-Based Development:
------------------------------------------

--Initially, Java web applications were developed using Servlets and JSP technologies.

--In this approach, developers had to perform many manual configuration tasks.

Responsibilities of the Developer:

--Create Servlet classes. (For each requirement create a separate Servlet class)

--Configure servlet mappings in web.xml.

--Package the application as a WAR file.

--Install and configure a web server such as:

Apache Tomcat
Jetty
WebLogic
JBoss

--Deploy the WAR file into the server.

--Manage libraries and dependencies manually.



Real-Life Analogy:
------------------

--Imagine building a house from scratch.

You must arrange:

Bricks
Cement
Electrical wiring
Plumbing
Furniture

--Everything has to be configured manually before the house becomes usable.

--Similarly, traditional Java web development required a lot of manual setup before writing actual business logic.


2. Spring MVC Development:
--------------------------

--Spring introduced the Spring MVC module to simplify web application development.

--Instead of writing low-level servlet code everywhere, developers could use:

Controllers
Dependency Injection
Annotations
View Resolvers

--This significantly reduced boilerplate code.

Advantages:

Better layered architecture.
Reduced servlet coding.
Easier dependency management.
Improved maintainability.


--Although Spring MVC simplified development, developers still had to:

Configure DispatcherServlet (only one Servlet act as a fron controller).

Configure component scanning.

Configure view resolvers.

Configure datasource settings.

Package as WAR (in many projects).

Deploy to an external Tomcat server.


Real-Life Analogy:

--Instead of building the entire house yourself, you hire a construction company.

--Many difficult tasks are handled for you, but you still need to supervise and provide instructions.

--Spring MVC reduced the complexity, but configuration work still existed.


3. Spring Boot Development:
---------------------------

--Spring Boot further simplified Java web application development by following the principle:

"Convention Over Configuration"

This means:

--If a sensible default configuration exists, Spring Boot automatically applies it so that developers can focus on business logic rather than infrastructure setup.


--Spring Boot is an extension of the Spring-MVC module that simplifies application development.




Real-Life Analogy:
-----------------

--Imagine purchasing a fully furnished apartment.

--The builder already provides:

Electricity
Water connection
Furniture
Security
Internet setup

--You can move in immediately and focus on living rather than setup.

--Similarly, Spring Boot provides sensible defaults and infrastructure configuration automatically, allowing developers to focus on writing business functionality.


--Today, Spring Boot is the most popular framework for developing modern Java web applications, REST APIs, and Microservices.



Official Goal of Spring Boot:

--Make Spring Development Faster and Easier.


Features of Spring Boot:
=======================

--Spring Boot was introduced to simplify Spring application development by reducing configuration effort and providing sensible defaults.

Some of the most important features of Spring Boot are:

1. Auto Configuration

2. Embedded Web Server

3. Starter Dependencies

4. Minimal Configuration

5. Production-Ready Features





Auto Configuration:
-------------------

--Auto Configuration is one of the most powerful features of Spring Boot.

--Spring Boot automatically configures various components based on the dependencies available in the project classpath.

--In traditional Spring applications, developers had to manually configure many components such as:

DispatcherServlet
View Resolver
DataSource
Transaction Manager
Component Scanning

--Spring Boot automatically creates and configures these components whenever possible.

Examples

If Spring Boot detects: "spring-boot-starter-web" dependency

It automatically configures:

Spring MVC
DispatcherServlet
Jackson JSON Converter
Embedded Tomcat Server


If Spring Boot detects: spring-boot-starter-data-jpa dependency

It automatically configures:

JPA
Hibernate
Transaction Management
Repository Support


--Spring Boot automatically creates and configures the DataSource object.


It automatically reads the data from the application.properties file:

like:

server.port=8088

Benefits:

Less XML configuration
Less Java configuration
Faster development
Reduced boilerplate code



2. Embedded Web Server:
-----------------------

--In traditional web applications, developers had to:

Install Tomcat server separately.
Package the application as a WAR file.
Deploy the WAR file into Tomcat.


--Spring Boot eliminates this requirement by providing an Embedded Web Server.

Supported embedded servers include:

Tomcat (Default)
Jetty
Undertow


Simply execute: Spring Boot main class which contains the main method
and the web server starts automatically.

Benefits:

No manual server installation
No WAR deployment required
Easy development and testing
Simplified deployment




3. Starter Dependencies:
------------------------

--Managing project dependencies manually can be difficult.

For example, to develop a web application, we may need:

Spring Core
Spring MVC
Jackson
Validation API
Embedded Tomcat
Logging Libraries

--In normal Spring-MVC based application, developer need to add these dependencies manually

--Managing all these dependencies individually is complex.

--Spring Boot solves this problem using Starter Dependencies.

--A starter is a predefined collection of commonly required libraries for a particular functionality.



Common Starter Dependencies:
-----------------------------

For Web Application:


<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-web</artifactId>
</dependency>


Provides:

Spring MVC
Embedded Tomcat
Jackson
Validation Support


For Data JPA:

<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-data-jpa</artifactId>
</dependency>


Provides:

Spring Data JPA
Hibernate
Transaction Management



For Testing:

<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-test</artifactId>
</dependency>


Provides:

JUnit
Mockito
Spring Test Framework



4. Minimal Configuration:
-------------------------

Spring Boot follows the principle: "Convention Over Configuration"

This means:

--If a sensible default configuration exists, Spring Boot uses it automatically.

--Developers only configure what is different from the default behavior.


Spring Boot Simply provide a main class having the main method

Example:

@SpringBootApplication
public class Application {

    public static void main(String[] args) {
        SpringApplication.run(Application.class,args);
    }
}


--We need to simply run this main method to launch our application.



5. Production Ready Features:
---------------------------

Spring Boot provides production-ready capabilities.

Examples:

Health Monitoring
Metrics
Logging
External Configuration

through:

spring-boot-starter-actuator dependency.

Understanding @SpringBootApplication
=====================================

--This is the most important annotation in Spring Boot.

Internally it combines:

@Configuration
@ComponentScan
@EnableAutoConfiguration


@Configuration

--Allows bean configuration.

@ComponentScan

--Scans components automatically.

@EnableAutoConfiguration

--Enables Spring Boot Auto Configuration.



Inside the main method:

 SpringApplication.run(EmployeeManagementApplication.class, args);


--When,

SpringApplication.run(...)

executes:


Step 1: Spring Container starts.

Step 2: Component Scanning starts.

Spring searches for:

@Component

@Service

@Repository

@Controller

@RestController

@Bean


Step 3: Beans are created and registered with Spring container.

Step 4: Dependency Injection happens.

Step 5: Auto Configuration executes.

Step 6: Embedded Tomcat starts.

Step 7: Application becomes ready.


Note: The SpringApplication.run(..) method returns an object of type:

	ApplicationContext

--which represents the Spring Container.

ApplicationContext ctx=  SpringApplication.run(EmployeeManagementApplication.class, args);
       

--Using the ApplicationContext, we can retrieve(pull) any registered Spring Bean manually.

Example:

ApplicationContext ctx = SpringApplication.run(EmployeeManagementApplication.class,args);

EmployeeController controller = ctx.getBean(EmployeeController.class);

System.out.println(controller.sayHello());



--However, in real-world Spring Boot applications, this approach is generally not recommended.
