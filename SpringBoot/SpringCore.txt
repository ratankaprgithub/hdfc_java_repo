The Problem with Plain Java:
-----------------------------


---Imagine you are building an E-Commerce application using only Core Java technologies. While Java is powerful, developing large-scale enterprise applications without a framework introduces several challenges.


1. Database Connection Management:
---------------------------------

--In plain Java, every database operation requires repetitive code:


Example:


Connection conn = null;

try {
    conn = DriverManager.getConnection(url, username, password);

    PreparedStatement stmt = conn.prepareStatement("SELECT * FROM products");

    ResultSet rs = stmt.executeQuery();

    // Process results

} catch (SQLException e) {
    e.printStackTrace();

} finally {
    if (conn != null) { 
        conn.close();
    }
}



Challenges:

--Repetitive boilerplate code in every DAO class.

--Developers must manually open and close database connections.

--Forgetting to close connections can lead to memory leaks.

--Connection pooling must be configured and managed manually.

--Exception handling becomes repetitive.




2. Object Creation and Dependency Management:
---------------------------------------------

Consider the following example:


class EmailService {

    public void sendEmail() {
        System.out.println("Sending Email...");
    }
}


class UserService {

    private EmailService emailService = new EmailService();

    public void registerUser() {

        System.out.println("User registered successfully");

        emailService.sendEmail();
    }
}



Problems:

--UserService is tightly coupled with EmailService.

--Replacing EmailService with SMSService or WhatsAppService requires code modification.

--Unit testing becomes difficult because dependencies are created internally.

--Object creation and dependency management become the responsibility of the developer.


3. Configuration Management:
-----------------------------

--Configuration values are usually loaded manually:

Properties props = new Properties();

FileInputStream fis = new FileInputStream("config.properties");

props.load(fis);

String dbUrl = props.getProperty("db.url");


Challenges:

--Manual loading of configuration files.

--Repeated code across projects.

--Environment-specific configuration becomes difficult to manage.




4. Building REST APIs:
-----------------------

--Before modern frameworks, developers used Servlets:

public class ProductServlet extends HttpServlet {

    protected void doGet(HttpServletRequest request, HttpServletResponse response) {

        // Parse request parameters

        // Execute business logic

        // Convert objects to JSON

        // Set response headers

        // Handle exceptions
    }
}



Additional Complexity:

--Configure URL mappings in web.xml.

--Manage servlet lifecycle manually.

--Convert Java objects to JSON manually.

--Handle exceptions and HTTP responses explicitly.

--Write a significant amount of infrastructure code.



Core Problems with Plain Java Enterprise Development:
======================================================

1. Excessive Boilerplate Code

--Developers spend more time writing infrastructure code than business logic.

2. Manual Object Management

--Creating and wiring dependencies manually becomes difficult as applications grow.

3. Tight Coupling

--Components become dependent on concrete implementations, reducing flexibility.

4. Configuration Complexity

--Managing XML files, properties, and environment settings becomes cumbersome.

5. Reinventing Common Solutions

--Developers repeatedly implement the same patterns across projects.

Tight Coupling and Loose Coupling Between Objects:
==================================================

What is Coupling?

--When one class uses the functionality of another class, we say that both classes are coupled.

--The class that needs a service is called the Dependent Class.

--The class that provides the service is called the Dependency Class.


Example:

public class EmailService {

    public void sendEmail() {
        System.out.println("Email Sent");
    }
}


public class UserService {

    private EmailService emailService = new EmailService();

    public void registerUser() {

        System.out.println("User Registered");

        emailService.sendEmail();
    }
}




Here:

UserService is the Dependent Class
EmailService is the Dependency Class

--UserService needs EmailService to send an email after user registration.


Tight Coupling:
---------------

--A system is said to be tightly coupled when changes in a dependency force changes in the dependent class.

In the above example:

	private EmailService emailService = new EmailService();

--UserService directly creates the object of EmailService using the new operator.

This means:

UserService knows exactly which implementation it is using.
UserService is responsible for creating the dependency object.
Replacing the dependency becomes difficult.



Problem 1: Method Name Change

--Suppose EmailService is modified as follows:

public class EmailService {

    public void sendNotification() {
        System.out.println("Email Sent");
    }
}


--Now the following code in UserService becomes invalid:

	emailService.sendEmail();

It must be changed to:

	emailService.sendNotification();


--Because a change in the dependency class forces a change in the dependent class, both classes are tightly coupled.


Problem 2: Replacing One Dependency with Another simmilar type of dependency.


--Suppose the business requirement changes.

--Instead of sending emails, we now want to send SMS messages.

public class SmsService {

    public void sendSms() {
        System.out.println("SMS Sent");
    }
}



--Now UserService must be modified:


public class UserService {

    private SmsService smsService = new SmsService();

    public void registerUser() {

        System.out.println("User Registered");

        smsService.sendSms();
    }
}



Again, the dependent class must be changed.

Therefore, the classes remain tightly coupled.



How to Achieve Loose Coupling?
------------------------------

--To achieve loose coupling, follow these two rules:

1. Program to Interfaces

--Create an interface representing the common behavior.

2. Apply Dependency Injection (DI)

--The dependent class should not create its own dependencies.

--Instead, dependencies should be supplied from outside.






Step 1: Create an Interface


public interface NotificationService {

    void sendNotification();
}



Step 2: Create Implementations

Email Implementation:
---------------------

public class EmailService implements NotificationService {

    @Override
    public void sendNotification() {
        System.out.println("Email Sent");
    }
}



SMS Implementation:
--------------------

public class SmsService implements NotificationService {

    @Override
    public void sendNotification() {
        System.out.println("SMS Sent");
    }
}


Step 3: Inject Dependency into Dependent Class:


public class UserService {

    private NotificationService notificationService;

    public void setNotificationService(NotificationService notificationService) {

        this.notificationService = notificationService;
    }

    public void registerUser() {

        System.out.println("User Registered");

        notificationService.sendNotification();
    }
}





Here:

UserService no longer creates objects using new.
Dependency is supplied from outside.
UserService only knows about the interface.
UserService does not care whether the implementation is Email or SMS.

--This is called Dependency Injection (Setter Injection).




Client Code
------------
Using Email Service:


UserService userService = new UserService();

userService.setNotificationService(new EmailService());

userService.registerUser();


Output:

User Registered
Email Sent



Using SMS Service:

UserService userService = new UserService();

userService.setNotificationService(new SmsService());

userService.registerUser();

Output:

User Registered
SMS Sent



--Notice that UserService code remains unchanged.

--Only the injected dependency changes.

--This is called Loose Coupling.


Definition of Loose Coupling:
-----------------------------

--If the dependency between two classes is minimal and changes in one class do not force changes in the other class, then those classes are said to be loosely coupled.

Benefits:

Easy maintenance
Easy testing
Better flexibility
Better reusability
Easy replacement of implementations




Inversion of Control (IoC):
===========================

--Traditionally, a dependent class creates its own dependency objects.

Example:

private EmailService emailService = new EmailService();

--Here the control of object creation is with the application code.(Object creation is in main control)

--In IoC (Inversion of Control), object creation responsibility is transferred to an external entity.

--Some external entity creates the object and supplies it to the dependent class.

--This external entity may be:

Factory Class
Registry
Container

--In Spring Framework, the external entity is the Spring IoC Container.

--The responsibility of creating and managing objects is transferred from the application code to the Spring Container.



Dependency Injection (DI)
-------------------------

--Dependency Injection is the practical implementation of IoC.

In DI:

--The dependent object does not create dependency objects.

--Dependency objects are supplied from outside.

--The container pushes the dependency into the dependent object.

Example:


userService.setNotificationService(new EmailService());

--Here EmailService is injected into UserService.


--Instead of creating dependencies inside the class, Spring provides them externally.



IoC vs DI:
----------

| IoC                                          | DI                                       |
| -------------------------------------------- | ---------------------------------------- |
| Design Principle                             | Implementation Technique                 |
| Concept                                      | Practical realization of IoC             |
| Control is transferred to an external entity | External entity injects dependencies     |
| Answers "Who creates objects?"               | Answers "How are dependencies provided?" |




--Dependency Injection (DI) is the process of providing dependency objects to a dependent object from an external source instead of creating them using the new operator.

In Spring Framework, DI can be achieved mainly in two ways:

Setter Injection
Constructor Injection


Setter Injection:
-----------------

--In Setter Injection, the dependency object is injected into the dependent class through a setter method.


Example: Inside the client code:

UserService userService = new UserService();

userService.setNotificationService(new EmailService());

userService.registerUser();



Advantages:

Dependency can be changed at runtime.
Suitable for optional dependencies.
Easy to understand for beginners.


Disadvantages:

Object can be created without dependency.
Possibility of NullPointerException if dependency is not injected.



2. Constructor Injection:
-------------------------

--In Constructor Injection, the dependency object is supplied through the constructor of the dependent class.

Example: Modify the above UserService class to support constuctor injection:


public class UserService {

    private NotificationService notificationService;

    public UserService(NotificationService notificationService) {

        this.notificationService = notificationService;
    }

    public void registerUser() {

        System.out.println("User Registered");

        notificationService.sendNotification();
    }
}



Injecting Dependency:


UserService userService = new UserService(new EmailService());

userService.registerUser();



Advantages:

Dependency is mandatory.
Object cannot be created without required dependencies.
Better for immutable objects.
Easier unit testing.
Recommended by Spring Team.


Disadvantages:

--Constructor becomes lengthy if there are too many dependencies.



Setter Injection vs Constructor Injection:
------------------------------------------

| Setter Injection                                 | Constructor Injection                   |
| ------------------------------------------------ | --------------------------------------- |
| Dependency injected through setter method        | Dependency injected through constructor |
| Suitable for optional dependencies               | Suitable for mandatory dependencies     |
| Dependency can be changed later                  | Dependency generally remains fixed      |
| Object may exist without dependency              | Object always created with dependency   |
| Can lead to NullPointerException if not injected | Safer because dependency is mandatory   |
| Less preferred in modern Spring applications     | Recommended approach in Spring Boot     |




Spring container:
=================

What is a Container?

--In Java, a class that provides runtime support to other classes is called a Container.

Examples:

--In a Console Application, the Main class provides runtime support to other classes.

--In AWT, the Frame class acts as a container for components like Button, Label, and TextField.

--In Servlets, the Servlet Container (Tomcat, Jetty, etc.) provides runtime support to Servlets and JSP pages.

Similarly, in Spring Framework, the Spring Container provides runtime support to Spring beans.


What is Spring Container?

--A Spring Container is a lightweight Java application that creates, configures, manages, and provides Spring bean objects to the application.

--It is the core component of the Spring Framework and implements the IoC (Inversion of Control) principle.

--All core services provided by Spring are available through the Spring Container.


Services Provided by Spring Container:
-------------------------------------

1. Bean Lifecycle Management:

--The Spring Container creates, initializes, manages, and destroys Spring beans automatically.

--Unlike Servlets and EJBs, Spring beans do not need to implement any special container-specific interfaces.


2. Bean Lookup Service:

--The Spring Container acts as a factory of beans.

--Application classes can obtain bean objects directly from the container without using any external registry or naming service.


3. External Configuration

--The state and behavior of beans can be configured using external XML configuration files or using the annotations also.

--This allows modifications without changing the source code of the bean classes.


4. Dependency Resolution:

--The container automatically identifies and injects the required dependency objects into dependent objects.

--This helps achieve loose coupling between application components.


Types of Spring Containers:
----------------------------

--Spring Framework provides two container interfaces:

BeanFactory
     |
ApplicationContext



1. BeanFactory:
----------------

Basic IoC Container.
Provides fundamental bean management features.
Creates bean objects only when requested (lazy loading).
Lightweight and simple container.


2. ApplicationContext:

Advanced IoC Container.
Extends BeanFactory.
Provides additional enterprise features.
Provide Annotation Support
Event Handling
Provide Internationalization support
Most commonly used container in Spring applications.

and much more..


Starting an ApplicationContext Container:
-----------------------------------------

--ApplicationContext provides implementation classes that directly read the configuration file or the cofiguration classes.

Common Implementations:

1. ClassPathXmlApplicationContext

2. FileSystemXmlApplicationContext

3. AnnotationConfigApplicationContext (used for Annotation based configuration classes)





Example:

Using ClassPathXmlApplicationContext:

--When the configuration XML file is available in the classpath:

ApplicationContext context = new ClassPathXmlApplicationContext("spring.xml");


Using FileSystemXmlApplicationContext:

--When the XML file is available at a different location:

ApplicationContext context = new FileSystemXmlApplicationContext("D:\\myapp\\spring.xml");


Using AnnotationConfigApplicationContext:

--When the configuration is done using the annotation approach instead of using xml approach.




Spring Bean:
-----------

--A Spring Bean is an object that is created, configured, managed, and destroyed by the Spring Container.

In other words:

--Any object whose lifecycle is controlled by the Spring Container is called a Spring Bean.

--The Spring Container creates the bean object, injects its dependencies, manages its lifecycle, and provides it to the application whenever required.

--Most Spring Beans are POJOs.


Consider the following class:



public class EmployeeService {

    public void display() {
        System.out.println("Employee Service");
    }
}


--If an object is created using:

EmployeeService service = new EmployeeService();

It is a normal Java object.

--If the same object is created and managed by the Spring Container then it becomes a Spring Bean.


Features of Spring Beans:
-------------------------

--Created by the Spring Container.

--Managed by the Spring Container.

--Dependencies are injected automatically.

--Lifecycle is controlled by the container.

--Can be shared and reused throughout the application.

--Helps achieve loose coupling.





Note: To make a Java class as Spring Bean, we need to register that class with the Spring Container using following approaches:

1. Using XML configurtion files

<bean id="service" class="com.app.EmployeeService"/>

2. Using the help of Annotations:

@Component
@Service
@Controller
@Repository
@Bean

@ComponentScan:
--------------

@ComponentScan enables the component scanning feature of Spring.

--When the Spring Container starts, it scans the specified package and all its sub-packages for Spring-managed components.

Example:

@ComponentScan(basePackages = "com.hdfc")


Spring scans:

com.hdfc

com.hdfc.service

com.hdfc.repository

com.hdfc.controller

com.hdfc.*

--and automatically registers eligible classes as Spring Beans.



--During component scanning, Spring registers a class as a bean only if it finds a stereotype annotation on that class.

Common stereotype annotations are:


@Component
@Service
@Repository
@Controller


These annotations tell Spring:

--"This class should be managed by the Spring Container."

--Component scanning reduces configuration effort because Spring automatically discovers and registers beans.


--By default, Spring creates a bean id using:

Class Name -> First Letter in Lowercase



Example:


package com.hdfc.service;
@Service
public class EmpService
{
--
--
}


package com.hdfc.dao;
@Repository
public class EmpDao
{
--
--
}



--With the above configuration,spring container registers two beans with ids empService and empDao.

Example2: 



package com.hdfc.service;
@Service
public class EmpService1
{
--
--
}


package com.hdfc.dao;
public class EmpDao
{
--
--
}


package org.hdfc;
@Service
public class EmpService2
{
--
--
}



And if we use component scanning like:

@ComponentScan(basePackages = "com.hdfc")


--In the above configuration spring container register only a EmpService1 class as a bean withid 'empService1'

--Second class EmpDao will not registered becoz @Service annotation(streotype annotation) is missing.

--EmpService2 also will not be registered because this class does not belongs to the base package.


--In order to specify more than one base packages we use:

@ComponentScan(basePackages = {"com.hdfc" , "org.hdfc"})




Note: If we want to tell the container that register a bean with given id then we need to pass 'value' element to the stereotype annotaion.


ex:

//@Service(value="em")
@Service("em")
public class EmpService
{

--
--

}


Now the EmpService class will be registered with id "em"

Autowiring Annotaions:
======================

--Autowiring annotations are used to inject dependencies automatically into Spring beans.

Important annotations:

@Autowired

@Qualifier

@Primary




@Autowired:
------------

--Used to to perform Dependency Injection (DI) automatically.

Can be applied on:

Field

Setter Method

Constructor


--Spring container searches for a suitable bean and injects it into the target bean.


1. Setter Injection:
---------------------

--Setter injection is useful when a dependency is optional or when additional logic needs to be executed during injection.


Example:

package com.hdfc.service;

import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.stereotype.Service;

@Service
public class UserService {

    private NotificationService notificationService;

    @Autowired
    public void setNotificationService(NotificationService notificationService) {

	System.out.println("Dependency Injected");
        this.notificationService = notificationService;
    }

    public void registerUser() {

        System.out.println("User Registered Successfully");

        notificationService.sendNotification();
    }


}



Advantages:

--Additional logic can be written inside the setter method.

--Dependency can be changed later if required.


2. Field Injection:
-------------------

--Spring injects the dependency directly into the field using reflection.

--No setter method is required.

Example:


@Service
public class UserService {

    @Autowired
    private NotificationService notificationService;

    public void registerUser() {

        System.out.println("User Registered Successfully");

        notificationService.sendNotification();
    }
}


Note

--Field Injection is simple but generally not recommended because:

Difficult to unit test.
Dependency is hidden.
Cannot create immutable objects.

--Constructor Injection is preferred in real-world applications.


3. Constuctor injection:
------------------------


--Spring officially recommends Constructor Injection because:

Dependencies become mandatory.
Objects can be made immutable (final fields).
Easier unit testing.
Avoids accidental null dependencies.


Example:

package com.hdfc.service;

import org.springframework.stereotype.Service;

@Service
public class UserService {

    private final NotificationService notificationService;


    @Autowired
    public UserService(NotificationService notificationService) {
        this.notificationService = notificationService;
    }

    public void registerUser() {

        System.out.println("User Registered Successfully");

        notificationService.sendNotification();
    }
}


Note: In modern Spring versions (Spring 4.3+), if a class contains only one constructor, @Autowired on the constructor is optional.


 public UserService(NotificationService notificationService) {
        this.notificationService = notificationService;
    }


is sufficient.


How Spring Resolves Dependencies:
---------------------------------

--When Spring encounters @Autowired, it primarily performs dependency resolution by type.


Example:

	@Autowired
	private NotificationService notificationService;


--Spring searches for a bean of type: NotificationService

--and injects it.


Mandatory Dependency:
---------------------

--By default, @Autowired makes a dependency mandatory.

--If no matching bean is found, Spring throws an exception during application startup.

Example:

@Autowired
private NotificationService notificationService;


--If no NotificationService bean exists:

	NoSuchBeanDefinitionException

will be thrown.


Optional Dependency
-------------------

--To make a dependency optional:

@Autowired(required = false)
private NotificationService notificationService;

--If a matching bean is not found, Spring will not throw an exception and the field will remain null.


Problem: Multiple Matching Beans:
--------------------------------

Suppose we have:

public interface NotificationService {
    void sendNotification();
}


@Service
public class EmailService implements NotificationService {

}


@Service
public class SmsService implements NotificationService {

}


--Now Spring finds two beans of type NotificationService.

	@Autowired
	private NotificationService notificationService;

--Spring becomes confused and throws:

	NoUniqueBeanDefinitionException



To resolve this ambiguity we use:

@Qualifier
@Primary



@Qualifier:
-----------

@Qualifier is used to specify exactly which bean should be injected.


	@Autowired
	@Qualifier("smsService")
	private NotificationService notificationService;


--Spring injects the bean whose name is: smsService


@Primary
----------

--@Primary is used to mark a bean as the default choice when multiple beans of the same type are available.

@Service
@Primary
public class EmailService implements NotificationService {

}


--Now whenever Spring finds multiple NotificationService beans, it will inject EmailService by default.


	@Autowired
	private NotificationService notificationService;

Spring injects:

EmailService

--because it is marked with @Primary.


| Annotation   | Purpose                                                           |
| ------------ | ----------------------------------------------------------------- |
| @Autowired   | Automatically injects a dependency                                |
| @Qualifier   | Specifies which bean should be injected when multiple beans exist |
| @Primary     | Marks a bean as the default choice among multiple matching beans  |

--These annotations are commonly used in Spring applications for:

@Value

@Scope

1. @Value:
----------

--@Value is used to inject simple values into Spring beans.

The value can come from:

Hardcoded values
application.properties
Environment variables



Example1: Harcoded value:

@Component
public class Employee {

    @Value("Ratan Kumar")
    private String employeeName;

    @Value("50000")
    private double salary;

    public void display() {

        System.out.println(employeeName);
        System.out.println(salary);
    }
}




Example 2: Reading from application.properties


Step1: create a .properties file inside the "resources" folder, called: 

application.properties: (Name can be anything, but inside the Spring Boot application this properties file name should be application.properties only)




application.properties:
------------------------

employee.name=Ratan Kumar
employee.salary=50000



Step2: Inside the configuration class specify the location of this properties file using:

@PropertySource("classpath:application.properties")


Example:

package com.hdfc.config;

import org.springframework.context.annotation.ComponentScan;
import org.springframework.context.annotation.Configuration;
import org.springframework.context.annotation.PropertySource;

@Configuration
@ComponentScan(basePackages = "com.hdfc")
@PropertySource("classpath:application.properties")
public class AppConfig {


}



Make use the key name of this properties file:


Example:

    @Value("${employee.name}")
    private String employeeName;

    @Value("${employee.salary}")
    private double salary;





@Scope
==========

--@Scope is used to specify the lifecycle and visibility of a bean.

By default every Spring Bean is:

@Scope("singleton")



Common Bean Scopes:
--------------------

| Scope       | Description                               |
| ----------- | ----------------------------------------- |
| singleton   | One object per Spring Container (Default) |
| prototype   | New object every time bean is requested   |
| request     | One object per HTTP Request               |
| session     | One object per HTTP Session               |
| application | One object per ServletContext             |




Note: request, session and application scope is used inside the Spring mvc (webapplication)


Singleton Scope (Default):


@Service
@Scope("singleton")
public class EmployeeService {

}


--Only one object is created and shared throughout the application.


Prototype Scope:


@Service
@Scope("prototype")
public class EmployeeService {

}


--Every request gets a new object.

Example


package com.hdfc;

import com.hdfc.beans.Employee;
import com.hdfc.config.AppConfig;
import org.springframework.context.ApplicationContext;
import org.springframework.context.annotation.AnnotationConfigApplicationContext;

public class App {

    public static void main(String[] args) {

        ApplicationContext ctx= new AnnotationConfigApplicationContext(AppConfig.class);

       Employee emp1=  ctx.getBean(Employee.class);

        Employee emp2=  ctx.getBean(Employee.class);

        System.out.println(emp1 == emp2);

    }
}




Note: Singleton scope doesn't mean that Spring container make the Employee class as Singleton class, It is just maintaining a single object of Employee class thougout the application.







Spring Bean Life Cycle:
=======================


--A Spring Bean passes through multiple stages from creation to destruction.


Bean Life Cycle Steps:
----------------------

1. Spring Container Starts

2. Bean Object Creation

3. Dependency Injection

4. @PostConstruct Method Execution

5. Bean Ready For Use

6. Bean Serves Requests

7. Container Shutdown

8. @PreDestroy Method Execution

9. Bean Destroyed


@PostConstruct:
--------------

--@PostConstruct is used to execute a method immediately after:

Bean creation
Dependency Injection completion

This method is executed only once.



Example:


@Component
public class Employee {

    @Value("Ratan Kumar")
    private String employeeName;

    @Value("50000")
    private double salary;

    @PostConstruct
    public void init() {

        System.out.println("Bean Initialized");
    }

    public void display() {

        System.out.println(employeeName);
        System.out.println(salary);
    }
}


Common Uses:

Loading configuration
Opening resources
Initializing caches
Creating database connections
Reading files


@PreDestroy:
------------

--@PreDestroy is used to execute cleanup code before bean destruction.

--It is executed when the Spring Container is shutting down.


Example:

@Component
public class Employee {

    @Value("Ratan Kumar")
    private String employeeName;

    @Value("50000")
    private double salary;

    @PostConstruct
    public void init() {

        System.out.println("Bean Initialized");
    }


    @PreDestroy
    public void destroy() {

        System.out.println("Cleaning Resources");
    }

    public void display() {

        System.out.println(employeeName);
        System.out.println(salary);
    }
}



Common Uses:

Closing database connections
Releasing resources
Closing files
Stopping background threads
Logging shutdown activities




Important Note About Prototype Scope:
------------------------------------

For Prototype Beans:

@Scope("prototype")

Spring:

Creates the object

Performs Dependency Injection

Calls @PostConstruct

**But Does NOT call @PreDestroy automatically

Reason:

--After creating a prototype bean, Spring hands it over to the application and no longer manages its complete lifecycle.


@Bean:
------

--It is a method level annotation.

--@Bean is used to create and register a bean manually in the Spring Container.


Generally used when:

Source code cannot be modified.
Third-party classes are involved.
Custom object creation logic is required.


--This annotation should be used on the top of a method, which returns an object

--Spring Container will register that returned object as Spring Bean.

--@Bean methods should generally be placed inside a class annotated with @Configuration.


Example: Inside the AppConfig class


@Bean
public List<String> getCities(){


	List<String> cities = new ArrayList<>(List.of("delhi", "mumbai", "kolkata", "chennai"));

	return cities;

}



Note: By default the List object will be registered with the container with id "getCities" (method name only)

--But if we want that container should registered this List as a Spring bean with different id:


@Bean("cities")
public List<String> getCities(){


	List<String> cities = new ArrayList<>(List.of("delhi", "mumbai", "kolkata", "chennai"));

	return cities;

}



Employee.java:
--------------

package com.hdfc.beans;

import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.beans.factory.annotation.Value;
import org.springframework.stereotype.Component;

import java.util.List;

@Component
public class Employee {

    @Value("${employee.name}")
    private String employeeName;

    @Value("${employee.salary}")
    private double salary;

    @Autowired
    private List<String> cities;

    public Employee() {
        System.out.println("Employee Object Created");
    }

    public void display() {

        System.out.println("Welcome to Spring Framework");
        System.out.println(employeeName);
        System.out.println(salary);

        System.out.println(cities);


    }


}




Difference Between @Component and @Bean:
----------------------------------------

| @Component                          | @Bean                                 |
| ----------------------------------- | ------------------------------------- |
| Applied on class                    | Applied on method                     |
| Used for our own classes            | Commonly used for third-party classes |
| Detected through Component Scanning | Registered through Java Configuration |
| Automatic Bean Creation             | Manual Bean Creation                  |
