
Design Pattern:
===============


--A Design Pattern is a proven, reusable solution to a commonly occurring software design problem.

--A design pattern is not a ready-made class or library. Instead, it provides a blueprint for organizing classes and objects to solve recurring design challenges.

--When we use regular technologies like Java, C, C++ to develop an application or a product there may be a chances of getting some problems repeatedly, In this case we need some solutions to resolve those repeated problems for getting better results/performance.

Why Do We Need Design Patterns?

--Software applications often encounter similar design problems, such as:

Creating objects
Managing object relationships
Reusing code
Reducing coupling
Improving maintainability

--Instead of reinventing solutions for these problems, developers use established design patterns that have been tested and refined over time.


Remember,

Design pattern is not:

- A readymade code
- A readmade class
- A framework
- An algorithm

--It is just a standard blueprint(one idea) to solve a problem.

Categogy of Design patterns:
============================

--The Gang of Four (GoF) classified 23 design patterns into three categories:


1. Creational Patterns:
-----------------------

--These patterns deal with object creation i.e How an object can be created.

--These patterns makes object creation easy.

--The basic form of object creation (using "new" keyword) could result in design problems or complexity.

--Creational design patterns solve this problem by somehow controlling this object creation.



Example:

Factory Method
Abstract Factory
Singleton
Builder



2. Structural Patterns:
-----------------------

--These patterns define how classes and objects are composed to form larger structures.

--How to connect objects..

Example:

Adapter
Decorator
Facade
Bridge
Composite


3. Behavioral Patterns:
-----------------------

--These patterns define how objects communicate and interact with each other.

--It defines the common communication patterns between objects and increases the flexibility in communication.


Example:

Strategy
Observer
Command
State
Iterator
Chain Of Resposibility pattern
Mediator pattern
Template pattern





Benefits of Design Patterns:
----------------------------

--Provide proven solutions to recurring design problems.
--Improve code readability and maintainability.
--Encourage code reuse.
--Reduce coupling between classes.
--Improve flexibility and extensibility.
--Establish a common design vocabulary among developers.



--A Design Pattern is a reusable design blueprint—not a ready-made implementation. It helps developers solve recurring software design problems using well-established and maintainable approaches.

Factory Pattern says that:

--Separate the object creation logic from the Client.

--In other word: Client should ask for an object instead of creating it directly.


--So, Here we should think to create a VechileFactory class which can create and return any type of Vechiles based on the Client requirement.


Example:


public class VehicleFactory {

    public  Vehicle getVehicle(String type) {

        if(type.equalsIgnoreCase("CAR")) {

            return new Car();

        }

        else if(type.equalsIgnoreCase("BIKE")) {

            return new Bike();

        }

        else if(type.equalsIgnoreCase("TRUCK")) {

            return new Truck();

        }

        return null;

    }

} 



Now the Client Code:


public class Client {

    public static void main(String[] args) {

        VehicleFactory factory = new VehicleFactory();

	Scanner sc = new Scanner(System.in);

	System.out.println("Which type of vechile you want ?");
	String type= sc.next();

        Vehicle vehicle = factory.getVehicle(type); // CAR

	if(vehicle != null){

        	vehicle.start();
	}else{
		System.out.println("Please pass the proper Vehicle type(CAR, BIKE, TRUCK)");
	}

    }

}


--Here Client has not used "new Car()" or "new Bike()" instead it is asking the getVehicle() method of VehicleFactory class by suppying its requirement.


--Here Factory has created the object.


Now suppose a new requirement comes:

--support the ElectricCar also.


Here we just need to follow following 2 steps:

1. create a new ElectricCar class by implementing the Vehicle interface:


public class ElectricCar implements Vehicle {

    @Override
    public void start() {

    }

2. Change the VechileFactory class:

else if(type.equalsIgnoreCase("ELECTRIC")){

    return new ElectricCar();

}



--But inside the Client, there should be no any changes.



Question: Is it a perfect desing ?

Ans/- Not Yet..


--because here VechileFactory class got modified.

--And it violates OCP of SOLID principle.



--To solve this problem "Factory method design pattern" is introduced.

--To overcome the limitation of "Factory pattern" the "Factory method pattern" is introduced.

To apply the Factory method pattern, first of all we create an interface called : VechileFactory


public interface VehicleFactory {

    Vehicle createVehicle();

}


Now,

CarFactory class:

public class CarFactory implements VehicleFactory {

    @Override
    public Vehicle createVehicle() {

        return new Car();

    }

}


BikeFactory class:

public class BikeFactory implements VehicleFactory {

    @Override
    public Vehicle createVehicle() {

        return new Bike();

    }

}

TruckFactory class:

public class TruckFactory implements VehicleFactory {

    @Override
    public Vehicle createVehicle() {

        return new Truck();

    }

}


Client code:

public class Client {

    public static void main(String[] args) {

        VehicleFactory factory = new CarFactory();

        Vehicle vehicle = factory.createVehicle();

        vehicle.start();

    }

}

Tomorrow, for Bike:


VehicleFactory factory = new BikeFactory();

That's it.

No existing factory modified.

Now

OCP is also satisfied.



Advantages:

Object creation is centralized.
Client is decoupled from concrete classes.
Easier to maintain.
Easier to extend.
Improves readability.
Supports Open-Closed Principle (Factory Method version).


Disadvantages:

More classes.
Slightly more complex for very small applications.
Too many factories if overused.


When Should We Use Factory?
-----------------------------

Use Factory when:

Object creation is complex.
Multiple implementations exist.
Client should not know the concrete class.
You want loose coupling.
New object types may be added in the future.



Difference between Simple Factory and Factory Method:
-----------------------------------------------------

| Simple Factory                              | Factory Method                                          |
| ------------------------------------------- | ------------------------------------------------------- |
| One factory class creates all objects       | Each product has its own factory                        |
| Factory changes when new products are added | New factories are added without modifying existing ones |
| Violates OCP                                | Supports OCP                                            |



Q/- Does Factory eliminate the use of new?

Ans/-  No.

--The new keyword still exists, but it is centralized inside the factory rather than scattered throughout the client code.

Abstract Factory Pattern:
=========================


--Factory Method creates one object (one type of product):


Example:

CarFactory: Car

BikeFactory: Bike

TruckFactory: Truck


--Abstract Factory creates a family of related objects.

Creating Singleton class:
-------------------------

--There are many ways we can create a class as singleton Java class, but at the end they all acheive the same result of a single object.

Eager Singleton:
-----------------

--Simplest implementation:


DatabaseConnection.java:
------------------------

public class DatabaseConnection {

    private static final DatabaseConnection INSTANCE = new DatabaseConnection();

    private DatabaseConnection() {

    }

    public static DatabaseConnection getInstance() {

        return INSTANCE;

    }

}

public class Demo {

--Here As soon as the class will be loaded into the memory the Object of the DatabaseConnection class is created into the memory. and the same object will be returned every time when we call getIntance() method.


Advantages:

--Very simple.
--Thread-safe because the JVM loads classes safely.
--No synchronization required.


Disadvantages:

--Object is created even if it is never used.
--Wastes memory if object creation is expensive.

Lazy Initialization:
--------------------

--Create the object only when it is required.

--And next time onwards return the same object.






DatabaseConnection.java:
------------------------

public class DatabaseConnection {

    private static DatabaseConnection INSTANCE;

    private DatabaseConnection() {

    }

    public static DatabaseConnection getInstance() {


	if(INSTANCE == null){
        	INSTANCE = new DatabaseConnection();
	}

	return INSTANCE;
    }

}


Advantages:

--Object is created only when needed.
--Saves memory.

Problem:

--This implementation is not thread-safe.

--Suppose two threads execute

getInstance(); at exactly the same time.

Both may see instance == null

and both create separate objects.

Singleton breaks due to the Race condition.



Making our Singleton class multithreaded compatible:
----------------------------------------------------


public class DatabaseConnection{

//it is good practice to make this variable as volatile in multi-threaded environment

private static volatile DatabaseConnection INSTANCE;


private DatabaseConnection(){

}


public static DatabaseConnection getInstance(){


synchronized(DatabaseConnection.class){

if(INSTANCE == null)
	instance=new DatabaseConnection();

}


return INSTANCE;

}
}


Advantages:

--Thread-safe.

Disadvantages:

--Every call acquires a lock of the DatabaseConnection class.
--Slower because synchronization happens even after the object has already been created.


--It synchronizes every call. 

Even after the object has already been created.

This causes unnecessary locking.


Double Checked Locking: recommended
-----------------------

--To avoid unnecessary synchronization, check twice.


public class Singleton {

    private static volatile DatabaseConnection INSTANCE;

    private DatabaseConnection() {
    }

    public static DatabaseConnection getInstance() {

        if (INSTANCE == null) {

            synchronized (DatabaseConnection.class) {

                if (INSTANCE == null) {
                    INSTANCE = new DatabaseConnection();
                }
            }
        }

        return INSTANCE;
    }
}
 


--Here if the object is created then next time if a thread in calling getInstance() method, it does not require to accquire a lock. 




Static Inner Class Singleton:
-----------------------------

--This is one of the cleanest implementations.

public class DatabaseConnection {

    private DatabaseConnection() {
    }

    private static class Holder {

        private static final DatabaseConnection INSTANCE = new DatabaseConnection();

    }

    public static DatabaseConnection getInstance() {

        return Holder.INSTANCE;

    }

}


Here:

--The outer class loads first.

--The inner class is not loaded immediately.

--The inner class loads only when getInstance() is called.

--Therefore, the object is created lazily.

--Class loading is thread-safe, so no explicit synchronization is required.


Advantages:

--Lazy initialization.
--Thread-safe.
--No synchronization overhead.


Enum Singleton:
---------------

--The simplest and safest implementation.

public enum DatabaseConnection {

    INSTANCE;

    public void display() {
        System.out.println("Singleton Object");
    }
}



Client code:


public class TestSingleton {

    public static void main(String[] args) {

        // Access the singleton object
        DatabaseConnection singleton1 = DatabaseConnection.INSTANCE;
        DatabaseConnection singleton2 = DatabaseConnection.INSTANCE;

        singleton1.display();
        singleton2.display();

        // Check whether both references point to the same object
        System.out.println(singleton1 == singleton2);      // true
        System.out.println(singleton1.equals(singleton2)); // true

        // Print hashcodes
        System.out.println(singleton1.hashCode());
        System.out.println(singleton2.hashCode());
    }
}



Advantages:

--Thread-safe.
--Prevents reflection attacks.
--Prevents serialization issues.
--Very simple to implement.

--This approach is recommended by Joshua Bloch in Effective Java.

--The most frequent approach is static inner class approach. and enum is also shortcut of creating a singleton object.


Disadvantage:

--You cannot perform custom multi-step lazy initialization using an enum Singleton.

Immutable Object:
-----------------

--An immutable object is an object whose state cannot be changed after it is created.

--Once all the values are assigned during object creation, they remain fixed throughout the lifetime of the object.

Characteristics of an Immutable Class:
---------------------------------------

--The class is declared as final (optional but recommended).
--All instance variables are declared as private and final.
--No setter methods are provided.
--Values are initialized only through the constructor (or Builder).
--If the class contains mutable objects (like List, Date, etc.), defensive copies are used.


Q/- Why Should the Email Class be Immutable in the Builder Pattern?

A/- 

--The Builder Pattern is generally used to construct complex immutable objects.

--After the build() method creates the Email object, its data should never change.

For example, this should not be possible:

email.setSubject("Hacked");   // Not allowed
email.setTo("another@gmail.com"); // Not allowed


Advantages of an Immutable Email Object:
----------------------------------------

1. Prevents Accidental Modification

Once an email is created, nobody can accidentally change the recipient, subject, or body.

Email email = builder.build();

// Subject cannot be changed later.

This guarantees that the email being sent is exactly the one that was created.


2. Thread Safe

Immutable objects are naturally thread-safe because multiple threads can read the same object simultaneously without synchronization.

Thread-1 ---> Reads Email
Thread-2 ---> Reads Email
Thread-3 ---> Reads Email

Since no thread can modify the object, there is no risk of inconsistent data.


3. Maintains Data Integrity:

--Imagine an email has already been validated and approved for sending.

--If someone changes the recipient or subject afterward, the validation becomes invalid.

--Immutability ensures that once an email is validated, it remains unchanged.



4. Easy to Share

--The same immutable email object can safely be passed to different methods or classes.

Email email = builder.build();

emailService.send(email);

emailLogger.log(email);

emailBackup.save(email);

--Since none of these methods can modify the object, sharing it is completely safe.



Note: The Builder class is itself mutable while constructing the object; the object produced by the Builder should be immutable.

public final class Email {

    // Mandatory Fields
    private final String from;
    private final String to;

    // Optional Fields
    private final String subject;
    private final String body;
    private final String cc;
    private final String bcc;
    private final String attachment;
   
    /**
     * Private Constructor
     * Only Builder can create Email objects.
     */
    private Email(Builder builder) {

        this.from = builder.from;
        this.to = builder.to;
        this.subject = builder.subject;
        this.body = builder.body;
        this.cc = builder.cc;
        this.bcc = builder.bcc;
        this.attachment = builder.attachment;    }

    // Getters

    public String getFrom() {
        return from;
    }

    public String getTo() {
        return to;
    }

    public String getSubject() {
        return subject;
    }

    public String getBody() {
        return body;
    }

    public String getCc() {
        return cc;
    }

    public String getBcc() {
        return bcc;
    }

    public String getAttachment() {
        return attachment;
    }


    @Override
    public String toString() {
        return "Email {" +
                "\nFrom='" + from + '\'' +
                ",\nTo='" + to + '\'' +
                ",\nSubject='" + subject + '\'' +
                ",\nBody='" + body + '\'' +
                ",\nCC='" + cc + '\'' +
                ",\nBCC='" + bcc + '\'' +
                ",\nAttachment='" + attachment + '\'' +
                "\n}";
    }

    /**
     * Static Inner Builder Class
     */
    public static class Builder {

        // Mandatory Fields
        private final String from;
        private final String to;

        // Optional Fields
        private String subject;
        private String body;
        private String cc;
        private String bcc;
        private String attachment;
       
        /**
         * Constructor for Mandatory Fields
         */
        public Builder(String from, String to) {

            this.from = from;
            this.to = to;
        }

        public Builder subject(String subject) {
            this.subject = subject;
            return this;
        }

        public Builder body(String body) {
            this.body = body;
            return this;
        }

        public Builder cc(String cc) {
            this.cc = cc;
            return this;
        }

        public Builder bcc(String bcc) {
            this.bcc = bcc;
            return this;
        }

        public Builder attachment(String attachment) {
            this.attachment = attachment;
            return this;
        }

       

        /**
         * Final Object Creation
         */
        public Email build() {

            validate();

            return new Email(this);
        }

        /**
         * Validation
         */
        private void validate() {

            if (from == null || from.isBlank()) {
                throw new IllegalArgumentException("From email cannot be empty.");
            }

            if (to == null || to.isBlank()) {
                throw new IllegalArgumentException("To email cannot be empty.");
            }

            if (!from.contains("@")) {
                throw new IllegalArgumentException("Invalid From email.");
            }

            if (!to.contains("@")) {
                throw new IllegalArgumentException("Invalid To email.");
            }
        }

    }

}

Director Class (Optional):
-------------------------

--In the Builder Pattern, a Director is an optional class that knows how to build a particular object step-by-step using the Builder.

--The Director does not create the object directly. Instead, it instructs the Builder about which construction steps should be executed and in what order.

--The main responsibility of the Director is to encapsulate a predefined object construction process.

Example:

--Suppose an application frequently sends a Welcome Email to every new customer.

--Instead of writing the following code repeatedly:


Email email = new Email.Builder(
        "admin@company.com",
        "customer@gmail.com")
        .subject("Welcome")
        .body("Welcome to our platform.")
        .build();



We can create a Director class:


public class EmailDirector {

    public Email createWelcomeEmail(String customerEmail) {

        return new Email.Builder(
                "admin@company.com",
                  customerEmail)
                .subject("Welcome")
                .body("Welcome to our platform.")
                .build();
    }
}


Client Code:

	EmailDirector director = new EmailDirector();

	Email email = director.createWelcomeEmail("john@gmail.com");



Advantages:

Reuses the same object construction logic.
Keeps client code simple.
Centralizes complex object creation.
Ensures the object is always built in the correct sequence.



Note: The Director class is completely optional. In many real-world Java applications, especially when using a Fluent Builder API, the client directly uses the Builder without a Director. A Director is useful only when the same construction process is reused multiple times or when object creation is complex.

--The Strategy Pattern is a behavioral design pattern that lets you put different ways of doing the same task into separate classes. It allows you to choose or change the required algorithm at runtime without changing the existing code.



In simple:

--The Strategy Pattern allows us to change the behavior of an object at runtime by selecting one of several algorithms stored in separate classes.

--The client  can switch algorithms at runtime without modifying its own code.


--Real companies they uses different strategy based on the different context/situations like:


Amazon: Different pricing strategies

Uber: Different fare calculation strategies

Google Maps: Different routing strategies

Netflix: Different recommendation algorithms

Payment Gateway: Different payment strategies


--The Strategy pattern eliminates large if-else or switch statements used for selecting different behaviors.
--It follows the Open/Closed Principle by allowing new strategies to be added without modifying existing code.



Advantage:

--Removes complex conditional logic.
--Makes code easier to maintain and extend.
--Encourages composition over inheritance.
--Supports runtime behavior changes.
--Improves testability by isolating algorithms.



Implementing the Strategy pattern: For payment
------------------------------------------------

Step1: First of all try to find out the common behaviour for all the payment options.

Like:

UPI
CreditCard
PayPal
Wallet


--The common behaviour among all is: pay the payment.

--So create a strategy interface:



public interface PaymentStrategy {

    void pay(double amount);

}


--So all the payment strategy need to implement this interface, because all of them need to pay the amount. 
--So all of them have to override this pay() method.


Step2:

--Implement the PaymentStrategy interface inside each payment class:
--Create the concrete strategies.


Example:

UPI:

public class UpiPayment implements PaymentStrategy {

    @Override
    public void pay(double amount) {
        System.out.println(amount + " paid using UPI");
    }

}


Card:

public class CardPayment implements PaymentStrategy {

    @Override
    public void pay(double amount) {
        System.out.println(amount + " paid using Credit Card");
    }

}


PayPal:

public class PaypalPayment implements PaymentStrategy {

    @Override
    public void pay(double amount) {
        System.out.println(amount + " paid using PayPal");
    }

}




Step 4: 

--Create a context class:

--The Context class is the class that uses a strategy to perform a task. 

--It holds a reference to the Strategy interface instead of a concrete strategy class and delegates the work to the selected strategy. 

--The Context does not know the implementation details of the algorithm; it simply calls the strategy through the common interface.


public class PaymentService {

    private PaymentStrategy strategy;

}


--So, here PaymentService class will act as a context class, and it says that it can work with any type PaymentStrategy.


Step5: Use the constructor injection to initialize this strategy object.


public class PaymentService {

    private PaymentStrategy strategy;

    public PaymentService(PaymentStrategy strategy) {
        this.strategy = strategy;
    }

}


Step 6: add a setter method also to leter change the strategy:



public class PaymentService {

    private PaymentStrategy strategy;

    public PaymentService(PaymentStrategy strategy) {
        this.strategy = strategy;
    }

    public void setStrategy(PaymentStrategy strategy){
	this.strategy= strategy;
    }


}


Step7: Add the payment processing method:



public class PaymentService {

    private PaymentStrategy strategy;

    public PaymentService(PaymentStrategy strategy) {
        this.strategy = strategy;
    }

    public void setStrategy(PaymentStrategy strategy){
	this.strategy= strategy;
    }

    public void processPayment(double amount) {

    	strategy.pay(amount);
    }


}



--Here context does not know client will use which type of payment strategy..and when he can change its strategy at runtime.



Now the client code creates the strategy object and passes it to the context.

PaymentStrategy strategy = new UpiPayment();
PaymentService service = new PaymentService(strategy);
service.processPayment(1000);



Note: In Spring Boot applications, the IoC Container usually creates and injects the strategy implementation.



Another example:

--Let's create a sorting engine using strategy design pattern:

--Client can choose any of the following types of sorting algorithm

Bubble Sort
Merge Sort
Quick Sort



Step1: first define a common task each algoritm is performing:

Ans/- sort an array.


Based on this create an interface.


public interface SortingStrategy {

    void sort(int[] arr);

}

Step2: create the separate concret classes for each algorithm:

Bubble Sort:

public class BubbleSort
        implements SortingStrategy {

    @Override
    public void sort(int[] arr) {

        System.out.println("Sorting using Bubble Sort");

    }

} 


Merge Sort:

public class MergeSort
        implements SortingStrategy {

    @Override
    public void sort(int[] arr) {

        System.out.println("Sorting using Merge Sort");

    }

}


Quick Sort:

public class QuickSort
        implements SortingStrategy {

    @Override
    public void sort(int[] arr) {

        System.out.println("Sorting using Quick Sort");

    }

}



Step3: Create a context class which uses these strategy to perform the task.


public class Sorter {

    private SortingStrategy strategy;

    public Sorter(SortingStrategy strategy) {
        this.strategy = strategy;
    }


	
    public void setStrategy(SortingStrategy strategy) {
        this.strategy = strategy;
    }



    public void performSorting(int[] arr) {

        strategy.sort(arr);

    }

}




Client code:

Sorter sorter = new Sorter(new MergeSort());

sorter.performSorting(arr); //merger sort

Q/- Which SOLID principle does the Strategy Pattern mainly support?

Answer:

1. Open/Closed Principle (OCP) – Add new strategies without modifying existing classes.
2. Dependency Inversion Principle (DIP) – Context depends on the Strategy abstraction, not concrete implementations.
