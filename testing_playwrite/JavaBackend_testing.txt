Unit Testing:
==============

Recap: What is Testing?

In previous sessions we learned:

--Testing is the process of verifying that a software application behaves as expected
 and produces correct results for different inputs and scenarios.

--Testing means comparing Actual Result with Expected Result.

Example:

2 + 3 = 5

Expected: 5
Actual: 5

Result:
	PASS


Imagine developing a calculator application. If you create an addition method:

public int add(int a, int b) {
    return a + b;
}

How do you know it always works correctly?

What if the inputs are negative?
What if one value is zero?
What if large numbers are passed?

--Instead of manually checking every scenario, 
developers write automated tests to verify the behavior of their code.

--This is where Unit Testing comes into the picture.



Where Does Unit Testing Fit?
-----------------------------

            UI Tests

               │

Unit Tests:
-----------

--Unit Testing is a software testing technique in which individual units or components of an application are tested independently.

--A unit is the smallest testable piece of code, such as:

A method
A function
A class
A component

***The goal is to verify that each unit works correctly in isolation.

For example:

public class Calculator {

    public int add(int a, int b) {
        return a + b;
    }
}

Unit Test:

@Test
void testAddition() {
 
   Calculator calculator = new Calculator();

    assertEquals(5, calculator.add(2, 3));
}

The test automatically verifies that 2 + 3 produces 5.

Fast.
Cheap.
Easy to write.
Most common.



Integration Tests:
-------------------

--Test multiple modules together.

Example:

Service
   ↓
Repository
   ↓
Database

--Testing all together.

Slower.
More setup required.

---------------------

--Suppose HDFC has a feature:

transferMoney()

inside:

Only test AccountService logic.

Database NOT involved.
API NOT involved.
Server NOT involved.



Integration Testing:

AccountService
      ↓
  Repository
      ↓
  Database

--Everything tested together.


Why Unit Testing Matters?
-------------------------

Imagine:

You write:

	calculateInterest()

Today it works.

After 3 months another developer changes code.

Suddenly:

Interest Calculation Wrong

Production bug.
Customer unhappy.


Unit Tests act like:

	Security Guards

Whenever code changes:

	Run Tests

If something breaks:

	Tests Fail

Developer immediately knows.


Real Life Analogy:
------------------

Consider a car manufacturing company.

--Before assembling the entire car, individual parts are tested:

Engine testing
Brake testing
Headlight testing
Battery testing

--If every component works correctly, the chances of the complete car failing are significantly reduced.

Similarly, in software development, we test individual units before integrating them into the complete application.


Then test entire car together.

This is like:

	Integration/System Testing


Characteristics of Good Unit Tests:
-----------------------------------

A good Unit Test should be:

1. Fast

--Tests should execute quickly.

Bad:

Call Database
Call Remote API
Wait 20 Seconds

Good:

	Run in milliseconds


2. Isolated:

--Test only ONE class.

Example:

Testing:

	UserService

Don't test:

Database
Email Service
Kafka

together.

--We'll mock them later using Mockito.



3. Repeatable

Running the same test multiple times should produce the same result.

Bad:

	Depends on internet

Good:

	Runs anywhere

Same Result


4. Independent:

--Test should not depend on another test.

Bad:

	Test B requires Test A

Good:

	Every test runs separately

5. Easy To Read:

--Anyone should understand what the test is verifying.

Bad:

	test1()

Good:

	shouldCalculateInterestForValidInput()
	


Benefits of Unit Testing:
-------------------------

1. Early Bug Detection

--Defects are found during development rather than in production.

2. Better Code Quality

--Developers write cleaner and more maintainable code.

3. Easier Refactoring

--Code can be modified confidently because tests verify correctness.

4. Documentation

--Tests act as executable documentation showing how code should behave.

5. Faster Development Cycle

--Automated tests reduce manual verification efforts.

Unit Testing Workflow:
----------------------

A typical workflow is:

Write application code.
        |
Create test cases.
        |
Execute tests.
        |
Verify results.
        |
Fix failures if any.
        |
Run tests again.
        |
Commit code.

--This cycle continues throughout the software development process.



Note: "The purpose of testing is not to prove that the code works, but to discover situations where it does not work."


Unit Test Structure:
--------------------

Industry follows:

AAA Pattern

	A = Arrange

Prepare data.

	B = Act

Call method.

	C = Assert

--Verify result.


Example:

@Test
void testAdd() {

    // Arrange
    Calculator calculator = new Calculator();

    // Act
    int result = calculator.add(10, 20);

    // Assert
    assertEquals(30, result);
}


--Almost every Unit Test follows this pattern.


JUnit 5 (JUnit Jupiter)
=======================

--JUnit is the most popular testing framework for Java applications. 
It provides a set of annotations, assertions, and utilities that help developers write and execute automated tests.

Before JUnit, developers often tested code manually:

public class Calculator {

    public int add(int a, int b) {
        return a + b;
    }

    public static void main(String[] args) {

        Calculator c = new Calculator();

        if(c.add(2, 3) == 5) {
            System.out.println("Test Passed");
        } else {
            System.out.println("Test Failed");
        }
    }
}


--This approach becomes difficult when hundreds of methods need testing.

--We need a software/framework which can: 

1. Help to create test cases, where we can test the add() method.

2. Run our test cases automatically.

3. Compare actual vs expected value

4. Show the result as PASS / FAIL

5. Generate reports..


--That That software/framework is:

JUnit

--JUnit automates this process.

--JUnit is a Java Testing Framework used to perform Unit Testing of Java applications.

It helps developers:

Write tests
Execute tests
Verify results
Generate reports

Assertions in JUnit-5:
======================

--Assertions are methods used to verify whether the actual result matches the expected result.

--An assertion acts like a checkpoint in a test case.

If the condition is true, the test passes.

If the condition is false, the test fails.


--To validate the result, we use assertions:

Example:

@Test
void testAddition() {
    int result = 2 + 3;
    assertEquals(5, result);
}

--Now JUnit can determine whether the test passed or failed.


Common Assertions in JUnit 5:
-----------------------------

Import:

import static org.junit.jupiter.api.Assertions.*;

--This gives access to all assertion methods.


Business Class:
---------------

public class Calculator {

        return a+b;
    }
}








1. assertEquals()

--Most commonly used assertion.
--Checks whether two values are equal.

Example:

@Test

    Calculator c = new Calculator();

    int actual = c.add(10,20);

    assertEquals(30,actual);
}

--Checks whether two values are different.

    Calculator c = new Calculator();

    int actual = c.add(10,20);

    assertNotEquals(100,actual);
}


Meaning:

100 != 30

PASS




3. assertTrue()

--Checks whether a condition is true.

	
@Test

    int age=25;

    assertTrue(age>=18);
}

Evaluation:

25 >= 18

TRUE

PASS

4. assertFalse()

--Checks whether a condition is false.

	
Example:

--Checks whether an object is null.

@BeforeEach:
-------------

--Runs before every test method.

Example:

}

--JUnit automatically executes it before every test.

----------------

    }

    @Test

    }

@Nested annotation allows grouping related test cases.

--It is a class level annotation.

--The @Nested annotation is used to create inner test classes inside a test class.

It helps organize related test cases into logical groups, making test code more readable and maintainable.

            throw new IllegalArgumentException("Password must contain at least 6 characters");
        }

package com.hdfc.service;

import static org.junit.jupiter.api.Assertions.*;

import org.junit.jupiter.api.DisplayName;
import org.junit.jupiter.api.Nested;
import org.junit.jupiter.api.Test;

public class UserServiceTest {

	UserService service = new UserService();

	@Nested
	@DisplayName("Registration Feature Tests")
	class RegistrationTests {

		@Test
		@DisplayName("Registration should succeed for valid email and password")
		void validRegistration() {

			String result = service.register("ratan@gmail.com", "password123");

			assertEquals("User Registered Successfully", result);
		}

		@Test
		@DisplayName("Registration should fail when email is blank")
		void blankEmail() {

			IllegalArgumentException ex = assertThrows(IllegalArgumentException.class,
					() -> service.register("", "password123"));

			assertEquals("Email is required", ex.getMessage());
		}

		@Test
		@DisplayName("Registration should fail when password length is less than 6")
		void shortPassword() {

			IllegalArgumentException ex = assertThrows(IllegalArgumentException.class,
					() -> service.register("ratan@gmail.com", "123"));

			assertEquals("Password must contain at least 6 characters", ex.getMessage());
		}
	}

	@Nested
	@DisplayName("Login Feature Tests")
	class LoginTests {

		@Test
		@DisplayName("Login should succeed for valid credentials")
		void validLogin() {

			assertTrue(service.login("admin", "admin123"));
		}

		@Test
		@DisplayName("Login should fail for invalid password")
		void invalidPassword() {

			assertFalse(service.login("admin", "wrong123"));
		}
	}
}

eq() method:
-------------

Sometimes we want:

Specific Value

--while using matchers.

Mockito rule:

--If you use a matcher for one argument, then all arguments must be provided using matchers.


Consider:

public interface UserService{

	public boolean login(String username, String role);

}


Here, 

when(userService.login(anyString(), "ADMIN"))
        .thenReturn(true);


This will throw an exception:

Correct Way:

when(userService.login(anyString(), eq("ADMIN")))
        .thenReturn(true);

Here:

anyString()   --> Matcher
eq("ADMIN")   --> Matcher

@SpringBootTest Annotation
--------------------------

@SpringBootTest is one of the most comprehensive testing annotations 
in Spring Boot because it loads the complete Application Context.


--It loads the entire Spring Application Context, just like when we start the application.

@SpringBootTest
class ProductServiceTest {

}

--When Spring Boot sees @SpringBootTest, it starts the Spring Container and creates all required beans.

What Gets Loaded?

When the test starts, Spring Boot creates:

Controllers
Services
Repositories
Configuration Classes
Properties
Security Configuration
DataSource
Application Context

--In short, the test environment becomes very similar to the actual running application.


Spring boot by default create the following test case method:

@Test
void contextLoads() {
}


Purpose:

Verify Application context (Spring container) Starts.

If the Spring Container starts successfully,
the test passes automatically.

If any bean creation, configuration,
or dependency injection fails,
the test fails.




Real-Time Example:
------------------

--Suppose we have a service:

@Service
public class ProductService {

    public String getProduct() {
        return "Laptop";
    }
}


Test Class:


@SpringBootTest
class ProductServiceTest {

    @Autowired
    private ProductService productService;

    @Test
    void testGetProduct() {

        String result = productService.getProduct();

        assertEquals("Laptop", result);
    }
}


Let us understand the complete execution flow:


Step 1: JUnit Starts the Test

JUnit detects and executes:

@Test
void testGetProduct() {
    ...
}

--At this stage, JUnit notices that the class is annotated with:

@SpringBootTest


Step 2: Spring Boot Starts the Container

--Spring Boot creates the Application Context.

--Application Context Started

--The Application Context is the container responsible for managing Spring Beans.


Step 3: Bean Creation

Spring scans the project and creates beans.

For example:

@Service
public class ProductService {

}

Spring creates:

ProductService Bean

--and stores it inside the Spring Container.


Step 4: Dependency Injection

Spring sees:

@Autowired
private ProductService productService;

--It finds the ProductService bean and injects it automatically.


Step 5: Test Method Execution

--Now the test method executes.

String result = productService.getProduct();

--The actual Spring-managed bean is used.



Step 6: Assertion

Finally, JUnit verifies the result.

assertEquals("Laptop", result);

If both values match:

	Test Passed

Otherwise:

	Test Failed


Advantages of @SpringBootTest
-----------------------------

1. Tests Real Spring Beans

--The actual application beans are used.

2. Tests Real Configuration

--Properties, configurations, and dependencies are loaded exactly as they are in production.

3. Useful for Integration Testing

--Ideal for testing interactions between:

Controller
   ↓
Service
   ↓
Repository
   ↓
Database


4. Detects Configuration Problems

It can identify:

Missing Beans
Circular Dependencies
Invalid Configurations
Database Connection Issues

before deployment.



Disadvantages of @SpringBootTest
--------------------------------

1. Slower Execution

--The entire Spring Container must start.

--Application Context Loading takes time.


2. Higher Memory Usage

--Many beans are created even when they are not required for a particular test.

3. Not Suitable for Small Utility Methods

For simple methods:

public int add(int a, int b) {
    return a + b;
}

--using @SpringBootTest is unnecessary.

--A simple JUnit test is sufficient.


When Should We Use @SpringBootTest?
-----------------------------------

Use it when you want to test:

Service + Repository Integration
Database Interaction
Complete Application Flow
Spring Configuration
Dependency Injection

Avoid it for:

Utility Methods
Simple Business Logic
Fast Unit Tests

--For such cases, use JUnit + Mockito instead.


Mocking the repository:
-----------------------

Consider the following method:

public Employee saveEmployee(Employee emp) {

    return empRepository.save(emp);
}

--When we test this method, the Repository will try to connect to the actual database.

This creates several problems:

Database must be running
Test execution becomes slower
Test may fail because of database issues
We are testing the database as well, not only the service logic

--For Unit Testing, we want to test only the Service class.

--Therefore, instead of using a real Repository, we create a fake Repository called a Mock Object.

--Using Mockito, we can define the behavior of dependencies without calling the actual implementation.

Example:

when(repository.findById(100))
.thenReturn(employee);

Meaning:

--"When someone calls findById(100), return this employee object instead of accessing the database."

	}

	@Override
	public Employee saveEmployee(Employee emp) {
		
		return empRepository.save(emp);
	}

		return  empRepository.findAll();

package com.hdfc.controller;

import static org.mockito.Mockito.when;
import static org.springframework.test.web.servlet.request.MockMvcRequestBuilders.get;
import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.jsonPath;
import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.status;

import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.webmvc.test.autoconfigure.WebMvcTest;
import org.springframework.test.context.bean.override.mockito.MockitoBean;
import org.springframework.test.web.servlet.MockMvc;

import com.hdfc.entity.Employee;
import com.hdfc.service.EmployeeService;

@WebMvcTest(EmployeeController.class)
public class EmployeeControllerTest {

    @Autowired
    private MockMvc mockMvc;

    @MockitoBean
    private EmployeeService empService;

    @Test
    void testGetEmployee() throws Exception {

        Employee emp = new Employee();

        emp.setEmpId(1);
        emp.setEmpName("Simran");
        emp.setEmail("simran@gmail.com");
        emp.setSalary(85000.00);

        when(
          empService.getEmployeeByID(1)
        ).thenReturn(emp);

        mockMvc.perform(
                get("/employees/1")
        )
        .andExpect(status().isOk())
        .andExpect(
            jsonPath("$.empId")
            .value(1)
        )
        .andExpect(
            jsonPath("$.empName")
            .value("Simran")
        )
        .andExpect(
            jsonPath("$.email")
            .value("simran@gmail.com")
        );
    }
}
