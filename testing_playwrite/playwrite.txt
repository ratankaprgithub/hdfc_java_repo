5. Automatic Waiting (Auto-Wait)

--One of Playwright's most powerful features is Auto-Waiting.

--Before performing an action, Playwright automatically waits for the target element to become ready.

Example:

await page.click("#loginBtn");

--Before clicking, Playwright automatically checks:

Is the element visible?
Is it attached to the DOM?
Is it enabled?
Is it stable?

--Only then does it perform the action.

Benefit

--This significantly reduces synchronization issues and flaky tests.


Synchronization Problem:
-------------------------

--A synchronization problem occurs when:

Automation Test Script Speed > Application Response Speed

--The automation script executes faster than the application can respond.

In Selenium, we often need to use:

Explicit Wait
Fluent Wait
Implicit Wait

--to handle such situations.

--In Playwright, many of these waits are handled automatically through Auto-Waiting.



Suppose code says:

await page.click("#loginBtn");

Internally:

Playwright
    |
Locate Button
    |
Wait Until Visible
    |
Move Mouse
    |
  Click

Notice:

	Auto Waiting

This is Playwright's superpower.

You don't need lots of explicit waits.


Real Time Analogy

Imagine you order tea.

Selenium behaves like:

"Tea ready or not, I am drinking now."

Sometimes failure.

Playwright behaves like:

"I will wait until tea arrives, then drink."

Much more reliable.

	Request -> Response -> Connection Closed

	Client <-------> Browser

continuously.

--Websocket is a statefull protocol.


Analogy

Speak
Disconnect

Call Again
Speak
Disconnect


WebSocket: 

Call Once
Keep Talking
Keep Listening

--Playwright uses this second approach.

--Therefore communication becomes very fast.

Browser Server vs Real Browser:
===============================

Real Browser:
--------------

--The real browser is the actual application that renders webpages.

Examples:

Chrome
Edge
Firefox
Safari

Its job is:

Render HTML/CSS
Execute JavaScript
Handle user interactions
Load web pages

Think:

Chrome.exe
Firefox.exe
msedge.exe

--These are real browser processes running on your machine.


Browser Server:
--------------

--The Browser Server is a controller/manager process that sits between Playwright and the browser.

Its job is:

Receive commands from Playwright
Create browser contexts
Open tabs/pages
Manage browser resources
Send commands to the browser
Return responses back to Playwright

It does not render webpages.


| Browser Server    | Real Browser         |
| ----------------- | -------------------- |
| Manager           | Worker               |
| Controls browser  | Renders web pages    |
| Creates contexts  | Executes JS          |
| Creates tabs      | Loads HTML/CSS       |
| Manages resources | Handles user actions |



Analogy: Hotel

Browser Server = Hotel Manager

Responsibilities:

Create Room
Allocate Room
Track Guests
Manage Resources


Real Browser = Actual Room

Responsibilities:

Guest Stays Here
Actual Work Happens Here

--Manager manages.

--Room does the real work.



Example:

Suppose your code is:

const browser = await chromium.launch();
const context = await browser.newContext();
const page = await context.newPage();

await page.goto("https://google.com");

Internally:

Browser Server Handles:

Launch Chromium
Create Context
Create Page
Manage Communication

Real Browser Handles:

Render Google Page
Execute Google's JavaScript
Load Images
Handle DOM

Auto-Waiting Superpower:
------------------------

--Suppose login button appears after 3 seconds.

Selenium:

	Thread.sleep(3000);

Often required.

Playwright:

	await page.click('#loginBtn');

--Playwright automatically waits before clicking.

Note: Playwright has different default timeouts for different operations.

1. Test Timeout (Default: 30 seconds)

A complete test can run for a maximum of 30 seconds by default.

test("My Test", async ({ page }) => {
    // Entire test must finish within 30 seconds
});

Error:

Test timeout of 30000ms exceeded

You can change it:

test.setTimeout(60000); // 60 seconds


2. Expect Timeout (Default: 5 seconds)

Assertions such as:

	await expect(page).toHaveTitle("My Title");

or

	await expect(locator).toBeVisible();

--will auto-retry for 5 seconds by default.


You can increase it:

	await expect(page).toHaveTitle("My Title", { timeout: 10000 } );


3. Action Timeout (Default: No Limit)

Disabling the Auto-Generated HTML Report:
----------------------------------------

--By default, when tests fail and the HTML reporter is enabled, 
Playwright may automatically start a local web server and open the HTML report.

Example:

Press Ctrl+C to quit.

--If you do not want the report to open automatically 
and prefer to view it only when needed, 

--modify the reporter configuration in playwright.config.ts.

Change:

reporter: ['html'],

to:

reporter: [['html', { open: 'never' }]],

This will:

--Generate the HTML report after test execution.
--Prevent Playwright from automatically launching the report server.
--Allow you to open the report manually whenever required.

To view the report later, run:

npx playwright show-report



Locators - The Heart of Playwright:
===================================

What is a Locator?

--A Locator is a mechanism used by Playwright to find an element on a webpage at any moment.

Without locators, Playwright cannot:

Click Buttons
Enter Text
Select Dropdowns
Upload Files
Verify Elements

Think of a locator as:

Address of an element inside a webpage.


--A Locator identifies a specific element among hundreds of elements present on a webpage.


Real-Life Analogy:
------------------

Suppose your wife says:

--Bring my red handbag.

You enter a room containing:

10 Bags
5 Suitcases
3 Backpacks

How will you find the correct bag?

Possible identifiers:

Color
Brand
Tag
Location

Similarly, a webpage may contain:

100 Buttons
50 Textboxes
200 Links

--Playwright needs a way to identify the correct element.

--That identification mechanism is called a Locator.


page.locator():
--------------

--The most commonly used API for locating elements.

Syntax:

const element = page.locator("selector");



--It will return te Locator object, Not the promise.
--So, No await is needed because Playwright is not performing any action yet.


Example:

const emailBox = page.locator("#email");

Think:

Page
 ↓
Find Element
 ↓
Store Reference


Advantages:

Auto Waiting
Reusable
Readable
Recommended by Playwright

Example:

const loginBtn = page.locator("#loginBtn");

console.log(loginBtn); 

await loginBtn.click();

Instead of:(Older style)

await page.click("#loginBtn");

Large projects usually prefer locators.

Locator object is reusable.

XPath stands for:

What is an Assertion?
======================


An automation script without verification has little value.

Suppose your script:

await page.fill('#username','admin');
await page.fill('#password','admin123');
await page.click('#loginBtn');

Question:

Did login succeed?

How do we verify it?

Answer:

Assertion

An Assertion compares:

Expected Result vs Actual Result


Assertion Syntax:
-------------------

await expect(actual)
       .matcher(expected);

Example:

await expect(page)
       .toHaveURL(/dashboard/);


Without Assertion:

Script Executes
       ↓
May Contain Bug
       ↓
Still Appears Successful



With Assertion:

Script Executes
       ↓
Verification Happens
       ↓
PASS or FAIL


Web-First Assertions:
---------------------

--Traditional automation tools often verify immediately.

Example:

assertEquals("Dashboard", actualTitle);

Problem:

	Page Still Loading

Result:

	Random Failure


Playwright uses:

Web-First Assertions

Meaning:

--Before verification, Playwright automatically waits for the expected condition.

--This significantly reduces flaky tests.


Example:

await expect(page.getByText("Welcome"))
	    .toBeVisible();

Playwright will wait until:

Element Appears
OR
Timeout Occurs

before failing.

Page Object Model (POM):
========================

--Page Object Model (POM) is a design pattern used in automation frameworks.

The basic idea is:

One Page
      ↓
One Class


Example::

Login Page
      ↓
LoginPage.ts

Dashboard Page
      ↓
DashboardPage.ts

Customer Page
      ↓
CustomerPage.ts



Problem Without POM:
---------------------

Consider a simple login test.

test('Login Test', async ({ page }) => {

    await page.goto(url);

    await page.fill(
      '#username',
      'admin'
    );

    await page.fill(
      '#password',
      'admin123'
    );

    await page.click(
      '#loginBtn'
    );

});

Looks fine.

Now imagine:

100 Tests

Every test contains:

page.fill('#password')

--Repeated everywhere.

Developer changes:

<input id="username">
to
<input id="userName">

Now:

100 Tests Fail

You must update:

100 Locations

--Huge maintenance problem.


POM Solution:

Move locators into one place.

	LoginPage.ts

--Now locator changes only once.


POM Architecture:
-----------------

Without POM:

Tests
   ↓
Directly Access Locators

With POM:

Data Driven Testing (DDT):
==========================

Data Driven Testing means:

Same Test Logic
        +
Different Test Data



Instead of writing:

Login Test For Admin
Login Test For Manager
Login Test For Customer

separately,

we write:

	One Login Test

--and supply multiple users.


Problem Without Data Driven Testing:
-----------------------------------

Example:

test('Admin Login', async ({ page }) => {

   await login('admin','admin123');

});

Another Test:


test('Manager Login', async ({ page }) => {

   await login('manager','manager123');

});

Another Test:


test('Customer Login', async ({ page }) => {

   await login('customer','customer123');

});

Problem:

Duplicate Test Logic
Only data changes.



Solution:

Move data outside.
Keep logic inside test.

Benefits of Data Driven Testing:

Less Code
Easy Maintenance
Reusable Tests
Scalable Framework
Better Coverage

Parameterized Tests:
===================

--In practice, most Data Driven Tests are implemented using parameterized tests. The primary difference is that parameterized tests often store data inside the test file, whereas Data Driven Testing typically retrieves data from external sources.



Parameterized Testing means:

One Test Logic
       +
Multiple Parameters
       =
Multiple Test Executions


Instead of writing:

test('Add Customer A', ()=>{});
test('Add Customer B', ()=>{});
test('Add Customer C', ()=>{});

we can write:

One Test
+
Multiple Parameters



Without parameterization::
--------------------------

test('Login Admin', ()=>{});
test('Login Manager', ()=>{});
test('Login Customer', ()=>{});

Problem:

	Duplicate Logic

Solution:

forEach()
or
for...of


Data Driven Testing vs Parameterized Testing:
---------------------------------------------

Data Driven Testing (DDT):

Data comes from:

JSON
Excel
CSV
Database
API

Example

	import users from '../test-data/users.json';

--Data is external.


Parameterized Testing:

--Data is usually defined inside test code.

Example:

const users = ['admin','manager','customer'];


Comparison:
----------

| Data Driven Testing   | Parameterized Testing  |
| --------------------- | ---------------------- |
| External Data Source  | Data Inside Test       |
| JSON/CSV/Excel        | Arrays/Objects         |
| Large Data Sets       | Small Data Sets        |
| Data Management Focus | Test Reusability Focus |



Most real-world frameworks use:

Parameterized Tests
         +
Data Driven Testing

together.

Tags in Playwright:
====================

--Tags are labels attached to tests.

They help us:

Group Tests
Filter Tests
Execute Specific Tests

--instead of running the entire test suite.


Without tags:

	npx playwright test

runs:

	ALL TESTS

which may take:

	2 Hours

Sometimes we need:

Quick Verification
Only important tests.

--Tags solve this problem.

Example:

Login Tests
Customer Tests
Payment Tests
Policy Tests
Claims Tests

Tag them:

@smoke
@sanity
@regression

--and run only what is required.



Common Industry Tags:
----------------------

Most organizations use:

@smoke
@sanity
@regression
@functional
@api
@ui



Tagging Tests:
--------------

Common practice:

--Add Tags To Test Title

Example:

test('@smoke Login Test',

 async ({ page }) => {

 });

Another Example:

 async ({ page }) => {

 });

Another Example

 async ({ page }) => {

 });



Running Tests Using Tags:
--------------------------

1. Run Smoke Tests:

npx playwright test --grep "@smoke"

Execution

	Only Smoke Tests

run.

2. Run Regression Tests

	npx playwright test --grep "@regression"


3. Run Sanity Tests:

	npx playwright test --grep "@sanity"



grep means:

	Search Matching Pattern

Example

test('@smoke Login');

test('@regression Customer');

test('@sanity Payment');

Command

npx playwright test --grep "@smoke"

Result

	Login Test Only

Dropdown Handling:
==================

--A Dropdown allows users to select one or more values from a list.


<select id="accountType">

   <option>Savings</option>

   <option>Current</option>

   <option>Salary</option>

</select>


Playwright Method:

	selectOption()

--used for HTML <select> elements.



Example:

await page.locator('#accountType')
	.selectOption('Savings');


Select By Value:
----------------

<select id="accountType">

   <option value="sav">
      Savings
   </option>

   <option value="cur">
      Current
   </option>

</select>


Playwright:

await page.locator('#accountType')
		.selectOption('sav');




Verify Selected Value:
-----------------------

await expect(page.locator('#accountType'))
		.toHaveValue('sav');


Multi Select Dropdown:
-----------------------


<select multiple id="skills">

  <option value="java">
     Java
  </option>

  <option value="spring">
     Spring
  </option>

  <option value="playwright">
     Playwright
  </option>

</select>



Select Multiple Values:

await page.locator('#skills')
.selectOption(['java','spring']);




Checkbox Handling:
=================

A Checkbox is a control that supports:

Checked
Unchecked

states.


Example:

<input type="checkbox" id="terms" />


Playwright Method:

	check()
        uncheck()


Example:

await page.locator('#terms')
	.check();

Result
	Checked


Uncheck Checkbox:

await page.locator('#terms')
	.uncheck();

Result:

	Unchecked


Verify Checkbox:
================

1. Checked Assertion

await expect(page.locator('#terms'))
	.toBeChecked();


2. Unchecked Assertion

await expect(page.locator('#terms'))
	.not.toBeChecked();


3. Is Checked?


const status = await page.locator('#terms')
			.isChecked();

console.log(status);

Output:

true
or
false


Multiple Checkboxes:
--------------------

Example

☐ Java
☐ Spring
☐ Playwright


Automation:

await page.locator('#java')
	.check();

await page.locator('#spring')
	.check();



Select All Example:

const checkboxes = await page.locator('input[type=checkbox]')
			.all();

Loop:

for(const checkbox of checkboxes){

   await checkbox.check();

}
