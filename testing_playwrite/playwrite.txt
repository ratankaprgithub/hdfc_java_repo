5. Automatic Waiting (Auto-Wait)

--One of Playwright's most powerful features is Auto-Waiting.

--Before performing an action, Playwright automatically waits for the target element to become ready.

Example:

await page.click("#loginBtn");

--Before clicking, Playwright automatically checks:

Is the element visible?
Is it attached to the DOM?
Is it enabled?
Is it stable?

--Only then does it perform the action.

Benefit

--This significantly reduces synchronization issues and flaky tests.


Synchronization Problem:
-------------------------

--A synchronization problem occurs when:

Automation Test Script Speed > Application Response Speed

--The automation script executes faster than the application can respond.

In Selenium, we often need to use:

Explicit Wait
Fluent Wait
Implicit Wait

--to handle such situations.

--In Playwright, many of these waits are handled automatically through Auto-Waiting.



Suppose code says:

await page.click("#loginBtn");

Internally:

Playwright
    |
Locate Button
    |
Wait Until Visible
    |
Move Mouse
    |
  Click

Notice:

	Auto Waiting

This is Playwright's superpower.

You don't need lots of explicit waits.


Real Time Analogy

Imagine you order tea.

Selenium behaves like:

"Tea ready or not, I am drinking now."

Sometimes failure.

Playwright behaves like:

"I will wait until tea arrives, then drink."

Much more reliable.

	Client <-------> Browser

--Websocket is a statefull protocol.


Analogy

--Therefore communication becomes very fast.

Browser Server vs Real Browser:
===============================

Real Browser:
--------------

--The real browser is the actual application that renders webpages.

Examples:

Chrome
Edge
Firefox
Safari

Its job is:

Render HTML/CSS
Execute JavaScript
Handle user interactions
Load web pages

Think:

Chrome.exe
Firefox.exe
msedge.exe

--These are real browser processes running on your machine.


Browser Server:
--------------

--The Browser Server is a controller/manager process that sits between Playwright and the browser.

Its job is:

Receive commands from Playwright
Create browser contexts
Open tabs/pages
Manage browser resources
Send commands to the browser
Return responses back to Playwright

It does not render webpages.


| Browser Server    | Real Browser         |
| ----------------- | -------------------- |
| Manager           | Worker               |
| Controls browser  | Renders web pages    |
| Creates contexts  | Executes JS          |
| Creates tabs      | Loads HTML/CSS       |
| Manages resources | Handles user actions |



Analogy: Hotel

Browser Server = Hotel Manager

Responsibilities:

Create Room
Allocate Room
Track Guests
Manage Resources


Real Browser = Actual Room

Responsibilities:

Guest Stays Here
Actual Work Happens Here

--Manager manages.

--Room does the real work.



Example:

Suppose your code is:

const browser = await chromium.launch();
const context = await browser.newContext();
const page = await context.newPage();

await page.goto("https://google.com");

Internally:

Browser Server Handles:

Launch Chromium
Create Context
Create Page
Manage Communication

Real Browser Handles:

Render Google Page
Execute Google's JavaScript
Load Images

Auto-Waiting Superpower:
------------------------

--Suppose login button appears after 3 seconds.

Selenium:

	Thread.sleep(3000);

Often required.

Playwright:

	await page.click('#loginBtn');

--Playwright automatically waits before clicking.

Note: Playwright has different default timeouts for different operations.

1. Test Timeout (Default: 30 seconds)

A complete test can run for a maximum of 30 seconds by default.

test("My Test", async ({ page }) => {
    // Entire test must finish within 30 seconds
});

Error:

Test timeout of 30000ms exceeded

You can change it:

test.setTimeout(60000); // 60 seconds


2. Expect Timeout (Default: 5 seconds)

Assertions such as:

	await expect(page).toHaveTitle("My Title");

or

	await expect(locator).toBeVisible();

--will auto-retry for 5 seconds by default.


You can increase it:

	await expect(page).toHaveTitle("My Title", { timeout: 10000 } );


3. Action Timeout (Default: No Limit)

Actions such as:

--However, they are still constrained by the overall test timeout (30 seconds).

Locators - The Heart of Playwright:
===================================

What is a Locator?

--A Locator is a mechanism used by Playwright to find an element on a webpage at any moment.

Without locators, Playwright cannot:

Click Buttons
Enter Text
Select Dropdowns
Upload Files
Verify Elements

Think of a locator as:

Address of an element inside a webpage.


--A Locator identifies a specific element among hundreds of elements present on a webpage.


Real-Life Analogy:
------------------

Suppose your wife says:

--Bring my red handbag.

You enter a room containing:

10 Bags
5 Suitcases
3 Backpacks

How will you find the correct bag?

Possible identifiers:

Color
Brand
Tag
Location

Similarly, a webpage may contain:

100 Buttons
50 Textboxes
200 Links

--Playwright needs a way to identify the correct element.

--That identification mechanism is called a Locator.


page.locator():
--------------

--The most commonly used API for locating elements.

Syntax:

const element = page.locator("selector");



Example:

const emailBox = page.locator("#email");

Think:

Page
 ↓
Find Element
 ↓
Store Reference


Advantages:

Auto Waiting
Reusable
Readable
Recommended by Playwright

Example:

const loginBtn = page.locator("#loginBtn");

await loginBtn.click();

Instead of:

await page.click("#loginBtn");

Large projects usually prefer locators.



Basic Locators:
===============

1. ID Locator

--Most preferred locator whenever available.

HTML:

<input id="email">

Locator:

await page.locator("#email").fill("admin@gmail.com");

or

await page.fill("#email","admin@gmail.com");

2. Name Locator

HTML:

<input name="email">

Locator:

await page.locator('[name="email"]')
	   .fill("admin@gmail.com");


Understanding CSS Attribute Selector:
------------------------------------

Syntax:

[name="value"]

Example:

[name="email"]

Meaning:

Find element
whose name attribute = email
Example

HTML:

Playwright:

3. Tag Name Locator

HTML:

<button>
 Login
</button>

Locator:

Problem with Tag Locators:
--------------------------

Consider:

<button>Save</button>
<button>Delete</button>
<button>Login</button>
<button>Submit</button>

Which button will Playwright click?

Usually the first matching button.

Therefore:

Tag Locator
   ↓
Not Reliable


Playwright expects:

1 Locator = 1 Element


--Avoid using tag locators when multiple matching elements exist.


Even though we can locate different buttons:

await page.locator("button").first().click();

await page.locator("button").last().click();

1. getByRole():
---------------

What is Role?

--Every accessible HTML element has a semantic role.

Example:

<button>Login</button>

Role: button

Common Roles:


| HTML Element    | Role     |
| --------------- | -------- |
| button          | button   |
| input type=text | textbox  |
| a               | link     |
| select          | combobox |
| checkbox        | checkbox |
| radio           | radio    |
| table           | table    |



Playwright recommends:

getByRole()

--because it mimics how assistive technologies (screen readers) interact with webpages.

--It is usually more stable than CSS/XPath.


Example:

<button>Login</button>

Playwright

await page.getByRole('button').click();


Better Version:

await page.getByRole('button', {name: 'Login'})
	 .click();

Why?

Suppose page contains:

<button>Save</button>
<button>Delete</button>
<button>Login</button>

Without name:

page.getByRole('button')

Multiple matches.

With name:

page.getByRole('button', {
    name:'Login'
})

Unique match.


Banking Example:

<button>Submit Proposal</button>

Locator:

await page.getByRole('button', { name:'Submit Proposal' })
	  .click();


Why Industry Likes getByRole()
-----------------------------

Imagine developer changes:

<button class="btn1">Login</button>

to

<button class="btn2">Login</button>

CSS locator may break.

But:

getByRole('button',{name:'Login'})

still works.

XPath:
=======

XPath stands for:

XML Path Language

Originally created for XML navigation.

Today heavily used for HTML element identification.

Absolute XPath:

Example:

/html/body/div/form/input

Avoid it.

Why?

--One UI change breaks everything.


Relative XPath:

Preferred.

Example:

//input

Meaning:

--Find all input elements


Locate by Attribute:
-------------------

<input id="username">

XPath:

//input[@id='username']

Playwright:

await page.locator('//input[@id="username"]');


Locate by Text:
---------------

HTML:

<button>Login</button>

XPath:

//button[text()='Login']

Playwright:

await page.locator('//button[text()="Login"]').click();



contains():
-----------

Most commonly used XPath function.

<button>Login Now</button>

XPath:

//button[contains(text(),'Login')]

Matches:

Login
Login Now
Login Here


starts-with():
--------------

<input id="user123">

XPath:

//input[starts-with(@id,'user')]

Matches:

user123
userABC
userXYZ



CSS vs XPath:
-------------

| CSS         | XPath                |
| ----------- | -------------------- |
| Faster      | Slightly slower      |
| Easy        | More powerful        |
| Recommended | Use only when needed |
| Readable    | Complex sometimes    |

Locator chaining:
-----------------

--Locator Chaining is a technique where we first locate a parent element and then search for child elements inside it.

--Instead of searching the entire webpage, Playwright restricts the search to a specific section of the page.

Why Use Locator Chaining?

Improves readability.
Reduces ambiguity when multiple matching elements exist.
Makes tests more stable and maintainable.
Useful for forms, tables, cards, dialogs, and complex UI components.

<form class="login-form">
    <input placeholder="Username">
    <input placeholder="Password">
    <button>Login</button>
</form>

await form.getByPlaceholder('Username').fill('admin');
await form.getByPlaceholder('Password').fill('admin123');
await form.getByRole('button', { name: 'Login' }).click();


Example 2: Direct Chaining


await page.locator('.login-form')
    	  .getByRole('button', { name: 'Login' })
           .click();



Example 3: Table Row

<tr>
    <td>Ratan</td>
    <td>Trainer</td>
    <td><button>Edit</button></td>
</tr>

What is an Assertion?
======================


An automation script without verification has little value.

Suppose your script:

await page.fill('#username','admin');
await page.fill('#password','admin123');
await page.click('#loginBtn');

Question:

Did login succeed?

How do we verify it?

Answer:

Assertion

An Assertion compares:

Expected Result vs Actual Result


Assertion Syntax:
-------------------

await expect(actual)
       .matcher(expected);

Example:

await expect(page)
       .toHaveURL(/dashboard/);


Without Assertion:

Script Executes
       ↓
May Contain Bug
       ↓
Still Appears Successful



With Assertion:

Script Executes
       ↓
Verification Happens
       ↓
PASS or FAIL


Web-First Assertions:
---------------------

--Traditional automation tools often verify immediately.

Example:

assertEquals("Dashboard", actualTitle);

Problem:

	Page Still Loading

Result:

	Random Failure


Playwright uses:

Web-First Assertions

Meaning:

--Before verification, Playwright automatically waits for the expected condition.

--This significantly reduces flaky tests.


Example:

await expect(page.getByText("Welcome"))
	    .toBeVisible();

Playwright will wait until:

Element Appears
OR
Timeout Occurs

before failing.
