Testing Fundamentals & QA Concepts:
==================================

Why do companies spend so much money on testing?

The answer is:

Because software quality matters.


What Is Software Quality?

--Imagine you order food using Swiggy or Zomato.

You order:

Paneer Butter Masala
Butter Naan
Cold Drink

You pay online.

After 30 minutes, the order arrives.

But:

Paneer is missing
Wrong drink delivered
Payment deducted twice

Would you call this a quality service?

No.


The application technically worked.

You were able to:

Open the app
Select food
Make payment
Place order

Everything worked.

--Yet the overall experience was poor.


Software quality is not just about:

	"Does the application run?"

It is also about:

	Does it satisfy the customer's expectations?


Software Quality means:

--The degree to which software meets customer expectations and business requirements.

A quality application should:

Work correctly
Meet business requirements
Be reliable
Be secure
Be easy to use
Provide a good user experience


Real World Example: UPI Payment
-------------------

Suppose you transfer:

10,000 from Account A to Account B

Expected:

Account A = -10000

Account B = +10000

--Everything is correct.


Now imagine this happens:

Account A = -10000

Account B = No Credit

Money disappears.


Technically:

Button worked
API worked
Database updated partially

But would you trust such a banking application?

Obviously not.

--This is a software quality problem.


What Is A Bug?
==============

--The biggest enemy of software quality is:

Bug


A bug is:

--A difference between expected behavior and actual behavior.

Example 1:

Requirement: Password must contain at least 8 characters.

User enters: 123

Application accepts it.

Expected: Validation Error

Actual: Password Accepted

Since:

Expected != Actual

--This is a bug.


Example 2: 

Requirement: User should be redirected to Dashboard after login.

Actual: Blank Page Appears

Again:

Expected != Actual

Therefore: Bug Found



Q/- Why Bugs Happen?
---------------------

Many beginners assume:

	Good developers don't write bugs.

This is impossible.

--Every developer writes bugs.

--Even Google, Amazon, Microsoft and OpenAI release bugs.

Reasons:

1. Requirement Misunderstanding:

Business says:

	Minimum age should be 18.

Developer misunderstands requirement.

Application behaves incorrectly.


2. Human Mistakes:

Developer writes:

	if(age > 18)

instead of

	if(age >= 18)

--One small symbol creates a defect.


3. Integration Issues:

Suppose:

Payment Service works
Order Service works

--Individually both are correct.

But when they communicate:

Payment Success
Order Not Created

System fails.



4. Last-Minute Changes:

Business changes requirements near release.

New code is written.
New defects are introduced.




Cost of Fixing Bugs:
====================


Scenario 1:

Architect is preparing blueprint.

You notice: Bathroom is missing.

Easy fix.

	Just update drawing.

Cost: Very Low


Scenario 2:

House construction has started.

Walls already built.

Now you realize bathroom is missing.

Need:

	Break wall
	Rebuild wall
	Redo plumbing

Cost increases.


Scenario 3:

House completed.

Family moved in.

Now bathroom problem discovered.

	Need major reconstruction.

Cost becomes huge.

Software Works Exactly The Same Way

--The later a bug is discovered, the more expensive it becomes.


1. Bug Found During Development:

--Developer fixes immediately.

Example:

if(age > 18)

changed to

if(age >= 18)

Time: 5 minutes


2. Bug Found During Testing


Now:

Tester finds bug
Tester raises defect
Developer investigates
Developer fixes
Build deployed
Tester retests


Time: Several hours


2. Bug Found In Production

Now, imagine customers discover the issue.


Suddenly:

Customers impacted
Customers complain
Support tickets created
Management gets involved
Emergency release required

Possible consequences:

Revenue loss
Customer dissatisfaction
Brand damage
Business loss

--Cost becomes very high.


Real Example:
-------------

Suppose Amazon has a bug.

For one hour:

	Buy Now button stops working.

Result:

	Millions of dollars lost.

One small bug.

	Huge business impact.



Important Principle:

Remember this statement:

--The cost of fixing a bug increases dramatically as it moves from Development -> Testing -> Production.



Why Testing is required ?
==========================

--At this point, we know:

Software should be high quality
Bugs reduce quality
Bugs are unavoidable

So a question naturally arises:

--How do we find bugs before customers find them to improve the software quality?

The answer is: Software Testing


Software Testing:
-----------------

--Software Testing is the process of verifying and validating software to ensure it behaves as expected.

The primary purpose of testing is:

--Find defects before customers find them.


Simple Analogy:

Imagine a school examination.

Teacher asks: 2 + 2 = ?

Expected: 4

Student writes: 5

Difference found.

Error detected.

--Testing works exactly the same way.

Tester compares:

Expected Result
vs
Actual Result

If they differ: Bug Found

Quality Assurance (QA):
========================

--Now that we understand why bugs are expensive, let's understand how companies try to prevent them.

The answer is: Quality Assurance (QA)


Quality Assurance (QA) is the overall process of ensuring that software meets expected quality standards before it reaches customers.

QA is much broader than testing.

QA focuses on:

Preventing defects
Improving processes
Maintaining standards
Reducing risks


Simple Analogy:
--------------

Imagine a restaurant.

Customers expect:

Good food
Clean environment
Safe ingredients


A restaurant owner can improve quality by:

Training chefs
Using fresh ingredients
Maintaining hygiene
Following cooking standards

--These activities help prevent bad food from being served.

This entire system represents:

Quality Assurance


--QA Is Not Just Testing

Many beginners think:

QA = Testing

--This is not completely correct.

--Testing is only one part of QA.



QA also includes:

Requirement Reviews
Design Reviews
Code Reviews
Coding Standards
Security Reviews
Testing

--All of these contribute to quality.


What Is A QA Engineer?
-----------------------

Now let's talk about the person.

--A QA Engineer is responsible for verifying that the software behaves correctly under different conditions.

Think of a QA Engineer as:

Customer Representative

--The QA Engineer tries to think like a customer.

--A QA Engineer asks questions such as:

What if the user enters invalid data?
What if the internet connection is lost?
What if the server is unavailable?
What if payment fails?
What if the user clicks the button multiple times?

--The objective is to identify defects before customers experience them.


Developer vs QA Engineer Mindset:
---------------------------------

--Both developers and QA Engineers want the same thing:

High-quality software

But they often think differently.

Developer Mindset:
------------------

A developer generally focuses on:

	How should the feature work?

Example:

Requirement: User should login successfully.

Developer verifies:

Valid Username
Valid Password
Login Success

Feature works.

Developer is satisfied.


QA Engineer Mindset:
---------------------

A QA Engineer focuses on:

	How can this feature fail?

The QA Engineer verifies:

Wrong Password
Blank Username
Blank Password
Special Characters
Locked Account
Expired Account
Network Failure
Session Timeout

--The QA Engineer explores failure scenarios and edge cases.


Q/- Why Both Roles Are Important ?
----------------------------------

Imagine an airplane.

Engineers design and build the aircraft.

But before passengers fly:

Safety inspections happen
System checks happen
Failure scenarios are tested

Both activities are necessary.

Software works exactly the same way.

Developer builds
QA validates

--Together they improve quality



Quality Assurance vs Testing:
==============================

| Process-oriented             | Product-oriented                     |

SDLC (Software Development Life Cycle):
========================================

Before learning STLC (Software Testing Life Cycle), we must first understand the bigger picture.

A very common beginner question is:

"Where does testing actually fit in software development?"

To answer this, we need to understand SDLC.

SDLC stands for: Software Development Life Cycle

--It is a structured process used to build software from an idea to a working product.

--Think of SDLC as a roadmap that guides a software project from start to finish.


Real-Life Analogy: Building a House
------------------

Imagine you want to build a house.

Would you immediately start laying bricks?

No.

First:

Understand requirements
Create blueprint
Estimate budget
Build structure
Inspect quality
Hand over house

--Software development follows a similar process.


Why Do We Need SDLC?
---------------------

--Without a process, software projects become chaotic.

Imagine a team where:

Requirements are unclear
Developers start coding immediately
No testing is done
No deployment plan exists

Result:

Missed deadlines
Poor quality
Customer dissatisfaction
Increased costs

--SDLC helps avoid these problems.



Main Phases of SDLC:
---------------------

--Most software projects follow these stages:

1. Requirement Gathering
2. Analysis
3. Design
4. Development
5. Testing
6. Deployment
7. Maintenance

Let's understand each phase.


Phase 1: Requirement Gathering:
-------------------------------

--This is the most important phase.

--If requirements are wrong, the entire project can fail.

What Happens Here?

Business stakeholders explain:

What problem needs to be solved?
Who will use the application?
What features are required?



Example

Suppose a bank wants: Online Loan Management System

Business may provide requirements such as:

Customer Registration
Loan Application
Loan Approval
EMI Calculation
Payment Tracking


Analogy:

Imagine ordering a custom-built house.

Before construction starts, you discuss:

Number of rooms
Parking space
Kitchen size
Budget

--This is similar to requirement gathering.


Phase 2: Analysis:
-------------------

--After gathering requirements, the team analyzes them.

Questions include:

Are requirements feasible?
What technologies are needed?
What are the risks?
How much effort is required?

Example

Requirement: System should support 1 million users.

Team analyzes:

Database capacity
Server requirements
Scaling strategy




Phase 3: Design
----------------

Now the solution is planned.

--Architects and senior developers create the system design.

Design Includes:

1. High-Level Design (HLD)

Big-picture architecture.

Example:

Frontend
Backend
Database
External Services



2. Low-Level Design (LLD)

Detailed implementation plan.

Example:

Classes
Tables
APIs
Relationships


House Analogy:

--This phase is similar to creating a blueprint before constructing a house.

--Without a blueprint, construction becomes risky.



Phase 4: Development
--------------------

--Now developers start writing code.

--This is where requirements and designs are converted into a working application.


Example:

Spring Boot developers may create:

Controllers
Services
Repositories
Security Configuration
REST APIs

Frontend developers create:

Screens
Forms
Components
Validations



Important Point:

	Many beginners think software is mostly coding.

In reality:

	Coding is only one phase of SDLC.


Phase 5: Testing
-----------------

--Once development is completed, the application is tested.

--This is where QA Engineers become heavily involved.


Objective:

Verify:

Does the application work correctly?
Does it meet requirements?
Can defects be identified before release?


Example

For a Login Feature:

QA verifies:

Valid Login
Invalid Login
Blank Fields
Locked User
Session Timeout


Important:

--Testing is not performed because developers are bad.

Testing is performed because:

Software is complex
Humans make mistakes
Requirements change




Phase 6: Deployment
-------------------

--After successful testing, the application is released to users.

Examples

Deployment to:

Production Server
AWS
Azure
Google Cloud


Example

After testing a Spring Boot application:

Docker Image Created
Application Deployed
Users Start Using It



Phase 7: Maintenance
---------------------

--Deployment is not the end.

Software continues to evolve.

Activities:

Bug Fixes
Performance Improvements
Security Updates
New Features



Real Example:

WhatsApp launched years ago.

Yet today it still receives:

Bug Fixes
Security Updates
Feature Enhancements
This is maintenance.



Complete SDLC Flow:
-------------------

Requirement Gathering
          ↓
      Analysis
          ↓
        Design
          ↓
    Development
          ↓
      Testing
          ↓
     Deployment
          ↓
    Maintenance

==================

--Many beginners think QA participates only during Testing.

In reality, QA can contribute throughout SDLC.

	Review requirements.

	Identify potential risks.

	Review testability.

	Verify fixes.

STLC (Software Testing Life Cycle):
==================================

SDLC describes:

How software is developed
from idea to deployment.

Now let's learn something more specific.

A common question is:

"What does a QA Engineer actually do after requirements are received?"

The answer is:

STLC
(Software Testing Life Cycle)


--It is a structured process followed by QA Engineers to plan, design, execute, and complete testing activities.


Simple Definition

STLC is:

A sequence of activities performed by the testing team to ensure software quality.

=============

| SDLC                                             | STLC                        |
| ------------------------------------------------ | --------------------------- |
| Software Development Life Cycle                  | Software Testing Life Cycle |
| Entire software project                          | Only testing activities     |
| Followed by Business, Architects, Developers, QA | Mainly followed by QA Team  |
| Covers development and testing                   | Covers only testing         |

--------------------------

SDLC:

Building the entire house:

Requirement
Design
Construction
Inspection
Handover


STLC:

Only the inspection activities:

Inspection Planning
Inspection Checklist
Inspection Execution

Final Approval


Why Do We Need STLC?
---------------------

--Imagine a tester receives a new application.

Without a process:

Start clicking randomly
Miss important scenarios

--Testing becomes unreliable.

STLC provides a systematic approach.

It ensures:

Better coverage

Higher quality

1. Requirement Analysis

If requirements are misunderstood:

Wrong test cases
Wrong implementation
Missed defects

Functional Testing vs Non-Functional Testing:
==============================================


When QA Engineers test an application, they usually verify two things:

1. Does the application work correctly?
2. How well does the application work?

These two questions give rise to:

Functional Testing
and
Non-Functional Testing


Real-Life Analogy: Buying a Car
------------------

Suppose you buy a new car.

--You want answers to two different questions.

Question 1:

Can the car:

Start properly?
Move forward?
Apply brakes?
Turn left and right?

If the answer is yes:

The functionality is working.


Question 2:

Now you ask:

How fast can it go?
How much fuel does it consume?
Is it comfortable?
Is it safe?

--Now you're evaluating quality attributes.

Software works exactly the same way.

-------------------

Functional Testing verifies whether the application behaves according to business requirements.

Simply put:

Does the system do what it is supposed to do?

Tester verifies:

Valid password
Successful login

Error message displayed

Here we are checking:

Correct behavior

This is Functional Testing.

Functional Testing focuses on:

Features

Validations
Workflows
User Actions

Tester checks:

Tester verifies:

Wrong PIN
Access denied

These are Functional Tests.

Smoke Testing, Sanity Testing & Regression Testing:
===================================================

--These are three of the most commonly used testing terms in real software projects.

As a trainer, you'll hear statements like:

Please do a smoke test after deployment.
Can someone perform sanity testing on the fix?
We need full regression before release.


Let's understand them is through a real-life example.



Real-Life Analogy: Buying a New Car
--------------------

--Suppose you purchase a new car from a showroom.

--Before driving it for hundreds of kilometers, what do you check first?

Does the engine start?
Do the brakes work?
Do the headlights turn on?
Can the car move?


You are not testing every feature.

You are simply checking:

--Is the car basically usable?

--This is the idea behind Smoke Testing.


Smoke Testing:
--------------

--Smoke Testing is a quick verification performed to ensure that the application's most critical functionalities are working.

Purpose:

Determine whether the build is stable enough for further testing.


Why the Name "Smoke"?

--The term comes from hardware engineering.

--When engineers powered on a newly assembled circuit board:

If smoke came out,
something was seriously wrong.

If no smoke appeared:

Basic verification passed.

--The software industry adopted the same concept.




Example: E-Commerce Application

After a new deployment, QA may verify:

Application launches
Login works
Products load
Cart opens
Payment page opens

If any of these fail:

Build rejected.

--No detailed testing begins.


Example: Banking Application

Smoke Testing may verify:

Login
Balance Inquiry
Fund Transfer Screen
Logout

--Only core functionality.



Characteristics of Smoke Testing:
--------------------------------

Quick
Shallow
Critical Features Only
Performed on Every New Build



--Smoke Testing is a preliminary test performed to verify that 
the critical functionalities of a build are working 
and the build is stable for further testing.



Sanity Testing:
---------------

Now imagine a different situation.

A bug is reported:

	Password Reset is not working.

Developer fixes the issue and sends a new build.

Do we test the entire application again?

No.

First we verify:

Did this specific fix actually work?

--This is called Sanity Testing.


--Sanity Testing is focused testing performed after a bug fix or small change to verify that the particular functionality works correctly.

Purpose:

	Validate the specific change.



Example

Bug:

	User cannot reset password.

Developer fixes the issue.

QA verifies:

Reset password
Email link
New password creation
Login with new password

QA is not checking:

Shopping cart
Product search
Order history

--Those areas were unrelated to the fix.


Real-Life Analogy:
-----------------

--Imagine your mobile phone speaker stops working.

Technician repairs it.

When you receive the phone back, what do you check first?

	Does the speaker work now?

You don't immediately test:

Camera
Bluetooth
WiFi
Fingerprint Sensor

--You first verify the repaired part.

This is Sanity Testing.



Characteristics of Sanity Testing:
----------------------------------

Narrow Scope
Focused Testing
After Bug Fix
After Small Changes


--Sanity Testing verifies that a specific bug fix or small change works correctly before detailed testing continues.


Regression Test:
=================

Now let's look at another scenario.

Suppose developers add a new feature:

	UPI Payment

The feature works perfectly.

But a new question arises:

--Did this new change accidentally break existing features?

--This is where Regression Testing comes in.


--Regression Testing ensures that existing functionality continues to work after changes are introduced.

Purpose:

	Verify that new changes have not broken previously working features.


Example:

Application already supports:

	Credit Card Payment
	Net Banking

Now developers add:

	UPI Payment

QA must verify:

UPI works
Credit Card still works
Net Banking still works


Another Example

Developer modifies Login Module.

QA may verify:

Login
Registration
Forgot Password
Session Management

--Because these features may be affected.


Real-Life Analogy:

--Suppose a mechanic repairs your car's steering system.

Before returning the car:

Check steering
Check brakes
Check suspension
Check wheel alignment

Why?

--Because changes in one area can affect others.

This is Regression Testing.



Characteristics of Regression Testing:
-------------------------------------

Broad Scope
Time Consuming
Repeated Frequently
Excellent Candidate For Automation


Why Automation is Important for Regression?
-------------------------------------------

Imagine:

500 Test Cases

--Running them manually after every release is expensive.

Automation tools like:

Playwright
Selenium
Cypress

--help execute regression suites quickly.

--This is one of the primary reasons organizations adopt automation testing.



Smoke vs Sanity vs Regression:
------------------------------


| Smoke Testing            | Sanity Testing                 | Regression Testing               |
| ------------------------ | ------------------------------ | -------------------------------- |
| Verifies build stability | Verifies a specific fix/change | Verifies old features still work |
| Broad but shallow        | Narrow and focused             | Broad and detailed               |
| Before detailed testing  | After bug fix                  | After code changes               |
| Critical features only   | Specific feature               | Entire impacted application      |
| Fast                     | Very Fast                      | Usually Time Consuming           |



Easy Way to Remember:
---------------------

Smoke Testing:

	Can we start testing?

Sanity Testing:
	
	Did this specific fix work?

Regression Testing:
	
	Did we accidentally break anything?



Real Project Flow:
-------------------

Suppose developers deliver Build v2.0.

Step 1

	Perform: Smoke Testing

	Result: Build Stable

Step 2

	Execute detailed testing.

Equivalence Partitioning (EP):
===============================

--This is one of the most important test case design techniques in software testing.

In real projects, testers face a common problem:

How can we test thoroughly
without writing thousands of test cases?

Imagine a requirement:

	Age must be between 18 and 60.


Possible inputs:

18
19
20
21
22
...
59
60

Should we test every value?

No

That would be time-consuming and inefficient.

This is where:

Equivalence Partitioning (EP)

helps.


What Is Equivalence Partitioning?
---------------------------------

--Equivalence Partitioning is a test case design technique in which input data is divided into groups (partitions), 
and one representative value is selected from each group for testing.

The idea is:

--If one value from a group works correctly, the remaining values in the same group are expected to behave similarly.


Real-Life Analogy:
-----------------

Suppose a teacher has 100 answer sheets.

Do they weigh every sheet individually to check paper quality?

No.

	They may randomly inspect a few sheets.

Why?

	Because all sheets come from the same batch.

	One sheet represents the group.

Equivalence Partitioning follows the same principle.



Why Use EP?
-----------

Without EP:

More Test Cases
More Time
More Effort

With EP:

Fewer Test Cases
Good Coverage
Less Effort



Example 1: Age Validation

Requirement: Age must be between 18 and 60.

Possible partitions:

Invalid Partition 1

Age < 18

Examples:

1
10
15
17

All should be rejected.


Valid Partition

18 ≤ Age ≤ 60

Examples:

18
25
40
55
60

All should be accepted.


Invalid Partition 2

Age > 60

Examples:

61
70
80
90

All should be rejected.



How Many Test Cases?

Without EP:

	Possibly hundreds

With EP:

	Choose one value from each partition.

Example:

10
25
70

	Only 3 test cases.


Why Does This Work?

Because we assume:

All values inside a partition
behave similarly.

If: 25

is accepted,

then:

30
35
40

--should also be accepted.

Example2: Password Length

Requirement: Password length must be between 8 and 20 characters.

Partitions:

Invalid:

	Length < 8

Representative:

	abc


Valid:

	Length 8–20

Representative:

	password123


Invalid

	Length > 20

Representative:

	abcdefghijklmnopqrstuvwxy


Positive And Negative Partitions:
---------------------------------

EP usually creates:

1. Valid Partition

Input should be accepted.

Example:

35


2. Invalid Partition

Input should be rejected.

Example:

15

Good testers always test both.




Another Example: Username Length

Requirement:

Username length:
5–15 characters.



Partitions:


| Partition | Example             | Expected |
| --------- | ------------------- | -------- |
| < 5       | abc                 | Reject   |
| 5–15      | john123             | Accept   |
| > 15      | verylongusername123 | Reject   |

---------------------

   "quantity": ?
}

Instead of testing:

2

4

Boundary Value Analysis (BVA):
-------------------------------

Equivalence Partitioning (EP)

--where we divide inputs into groups and test one representative value from each group.

But there is a problem.

Many real-world defects do not occur in the middle of a range.

They occur at the edges.

For example:

Requirement: Age must be between 18 and 60.

Most bugs are found around:

17
18
19

59
60
61

rather than:

25
35
45

--This leads us to one of the most powerful testing techniques:

Boundary Value Analysis (BVA)

--Boundary Value Analysis is a test design technique that focuses on testing values at the boundaries of valid and invalid partitions.

Simple meaning:

	Most bugs occur at the edges, so test the edges carefully.


Real-Life Analogy:


Suppose a bridge is designed to support:

Maximum Weight = 10 Tons

Would engineers test:

1 Ton
2 Tons
3 Tons

only?

No.

They would test around:

9.9 Tons
10 Tons
10.1 Tons

--because that's where failures are most likely.

Software behaves similarly.



Why BVA Exists?
----------------


Developer accidentally writes:

	if(age > 18 && age < 60)

instead of:

	if(age >= 18 && age <= 60)


What happens?

18 rejected
60 rejected

Bug found.


This type of bug is extremely common.

That's why testers focus on boundaries.


Relationship Between EP and BVA:
--------------------------------

Suppose requirement:

	Age must be between 18 and 60.

EP gives:

<18
18–60
>60

BVA says:

Test around the boundaries
of these partitions.

General BVA Rule:

For a range:

Min = 18
Max = 60

Test:

Min - 1

Min

Min + 1

Max - 1

Max

Max + 1

--This is the most important formula in BVA.




Example 1: Age Validation

Requirement:

	Age must be between 18 and 60.

Boundaries:

18
60


Test Cases:

| Input | Expected |
| ----- | -------- |
| 17    | Reject   |
| 18    | Accept   |
| 19    | Accept   |
| 59    | Accept   |
| 60    | Accept   |
| 61    | Reject   |


Notice:

We are testing around the boundaries.


EP vs BVA
----------

Equivalence Partitioning

Focus: Partitions

Example:

10
25
70

Boundary Value Analysis:

Focus: Edges

Example:

17
18
19
59
60
61


Best Practice

In real projects:

EP + BVA

are almost always used together.

Example:

Requirement:

Age = 18–60

EP Test Cases:

10
30
70



BVA Test Cases:

17
18
19
59
60
61

--Together they provide excellent coverage.


Decision Table Testing:
-----------------------

Equivalence Partitioning (EP)

Boundary Value Analysis (BVA)

These techniques work very well when a single input field has rules like:

Age = 18 to 60
Marks = 0 to 100
Password Length = 8 to 20

--But what happens when multiple conditions together determine the result?


For example:

Loan Approval depends on:

Age
Salary
Credit Score

--Now the output depends on combinations of inputs.

--EP and BVA alone are not sufficient.

This is where:

Decision Table Testing

becomes useful.


Decision Table Testing is a test design technique used when the application's behavior depends on multiple conditions and business rules.

It helps us verify all important combinations of conditions.



Real-Life Analogy:

Suppose a restaurant offers a discount.

Rules:

Member Customer?
YES / NO

Order Above 1000?
YES / NO

Discount Policy:

Member + Order > 1000
20% Discount

Member + Order <= 1000
10% Discount

Non-Member + Order > 1000
5% Discount

Non-Member + Order <= 1000
No Discount

--Would you manually think through every combination?

Possible.

--But as conditions increase, complexity grows rapidly.

--Decision Tables organize these combinations clearly.


Structure Of A Decision Table:
-------------------------------

A decision table usually contains:

Conditions
Actions


General Format:


| Conditions  | Rule1 | Rule2 | Rule3 | Rule4 |
| ----------- | ----- | ----- | ----- | ----- |
| Condition A | Y     | Y     | N     | N     |
| Condition B | Y     | N     | Y     | N     |
| Action      | A1    | A2    | A3    | A4    |





Example 1: Loan Approval

Requirement:

Loan Approved only if:

Salary >= 50,000

Credit Score >= 700

Conditions:

Salary >= 50k ?
Credit Score >= 700 ?


Decision Table:

| Salary >= 50k | Credit Score >= 700 | Result  |
| ------------- | ------------------- | ------- |
| Yes           | Yes                 | Approve |
| Yes           | No                  | Reject  |
| No            | Yes                 | Reject  |
| No            | No                  | Reject  |



Test Cases:

| TC | Salary | Credit Score | Expected |
| -- | ------ | ------------ | -------- |
| 1  | 60000  | 750          | Approve  |
| 2  | 60000  | 650          | Reject   |
| 3  | 40000  | 750          | Reject   |
| 4  | 40000  | 650          | Reject   |



Notice:

We are testing all possible combinations.



Banking Example:

--Suppose HDFC Credit Card Approval Rule:

Age >= 21
Salary >= 40,000
Credit Score >= 700

How many combinations?

	Three conditions.

Each condition has:

Yes
No

Total combinations:

2³ = 8


Decision Table:


| Age | Salary | Score | Result  |
| --- | ------ | ----- | ------- |
| Y   | Y      | Y     | Approve |
| Y   | Y      | N     | Reject  |

State Transition Testing:
-------------------------

Now let's look at another type of system where the output depends on:

Current State

of the application.

This leads us to:

State Transition Testing


What Is A State?
----------------

--A State is simply the current condition or status of a system.


Real-Life Examples:

1. Traffic Signal

Possible states:

Red
Yellow
Green


2. ATM Card

Possible states:

Card Inserted
PIN Verified
Transaction In Progress
Transaction Completed


3. User Account

Possible states:

Active
Locked
Disabled

--At any moment, the system is in one state.



State Transition:
-----------------

A State Transition means:

Moving from one state
to another state.


Example:

Traffic Signal

Red
 ↓
Green
 ↓
Yellow
 ↓
Red

Each movement is a transition.



State Transition Testing:
-------------------------

State Transition Testing verifies that a system behaves correctly when moving from one state to another.

Simple meaning:

	Verify that the correct action occurs when the system changes state.


Why Do We Need It?

--Many applications behave differently depending on their current state.

For example:

Requirement:

User gets 3 login attempts.

After 3 failures,
account should be locked.

Question:

If we test only one login attempt, will we find bugs?

No

--Because the important behavior occurs after multiple state changes.


Real-Life Analogy: ATM Machine
-------------------

Consider ATM usage.

Initial State:

	Card Not Inserted

Action:

	Insert Card

New State:

	Card Inserted

Action:

	Enter Correct PIN

New State:

	Authenticated

Action:

	Withdraw Cash

New State:

	Transaction Complete

--System changes state continuously.

--State Transition Testing verifies these movements.



Example 1: Login Account Locking
-------------------------------

Requirement:

After 3 consecutive failed logins,
account should be locked.

States:

Active
Locked



Transitions:

Active
 ↓
Wrong Password (1)

Active
 ↓
Wrong Password (2)

Active
 ↓
Wrong Password (3)

Locked

---------------

   |
Wrong Password
   |
Active
   |
Wrong Password
   |
Active
   |

   |

Test Cases:
-----------

Case 1:

Wrong Password
Wrong Password
Correct Password

	Login Success

Account still active.


Case 2:

Wrong Password
Wrong Password
Wrong Password

	Account Locked


Case 3:

	Correct Password

Expected:

	Access Denied


This is classic State Transition Testing.

Mountebank:
===========

Mountebank is an open-source software tool used for service virtualization and API mocking.

Think of it as a fake server that can simulate APIs, databases, or external services during testing.

https://www.mbtest.dev/

Suppose:

Frontend Team Ready

Backend Team Not Ready

Should testing stop?

No.

Create a fake backend using Mountebank.

Frontend
   ↓
Mountebank
   ↓
Mock Response

Example:

GET /products

returns:

[
  {
    "id": 1,
    "name": "Laptop"
  }
]

even though actual backend is not available.



Installation:

Since it is a Node.js-based tool:

npm install -g mountebank

Start server:

mb

Default port:

2525

How It Works

You define an imposter (fake service).

Example:

{
  "port": 3000,
  "protocol": "http",
  "stubs": [
    {
      "responses": [
        {
          "is": {
            "statusCode": 200,
            "body": {
              "message": "Hello"
            }
          }
        }
      ]
    }
  ]
}

Now:

GET http://localhost:3000

returns:

{
  "message": "Hello"
}

Testing Pyramid:
================

Imagine a hospital.

No

They start with:

 ↓

 ↓

 ↓

--The same idea applies to software testing.

We should perform:

Many Small Tests
Few Medium Tests
Very Few End-to-End Tests


What Is The Testing Pyramid?

The Testing Pyramid is a guideline that tells us:

How many tests should exist
at each testing level.

Visualization:


            --------
            UI Tests 
           (Few Tests)
        ------------------
     API Tests/integration Test 
         (Some More Tests)
    ----------------------------
           Unit Tests
        (Most Of The Tests)


Why A Pyramid Shape?

Because:

Unit Tests
↓
Fast
Cheap
Easy

UI Tests
↓
Slow
Expensive
Fragile

Therefore:

Many Unit Tests

Some API Tests

Few UI Tests
