Microservices:
==============

Introduction to Software Architecture and Monolithic Applications:
-------------------------------------------------------------------


Software Architecture:
----------------------

--Before writing a single line of code, every successful software system begins with a design.

--Just as a civil engineer creates a blueprint before constructing a building, 
software engineers create an architectural design before building an application.


Real Life Analogy: Building a House:
------------------------------------

Imagine a person wants to build a house.

Before construction starts, several questions need answers:

- How many rooms are required?
- Where should the kitchen be located?
- Where should electrical wiring be placed?
- How should water pipelines be connected?
- How many floors will the building have?

--A blueprint is created before any construction work begins.

Without a blueprint:

Construction becomes confusing.
Resources get wasted.
Future modifications become difficult.

--Software development follows exactly the same principle.
Before building an application, we need a plan that defines:

Components
Responsibilities
Communication
Data Flow
Deployment Strategy

This plan is called:
Software Architecture




Software Architecture is the high-level structure of a software system that defines:

- The major components of the system.
- The responsibilities of each component.
- How components communicate.
- How data flows through the system.
- How the application is deployed and scaled.


Example:

--Consider an Online Shopping Application.

Features:

User Registration
Product Management
Order Management
Payment Processing
Inventory Tracking

--If we immediately start coding without planning:

Different developers may build similar functionality.
Responsibilities may overlap.
The application may become difficult to maintain.

--Architecture helps avoid these problems.



Good architecture helps achieve:

1. Maintainability:

--The application becomes easier to modify.

Example:

Adding a new feature
Fixing a bug
Changing business rules

--becomes easier when responsibilities are clearly separated.


2. Scalability:

--The application can handle increasing traffic.

Example:

100 Users
1000 Users
10000 Users

--A good architecture should support growth.


3. Reliability:

--The application should continue working even when problems occur.

Example:

Temporary Network Issue
Database Delay
High Traffic

--Architecture plays a major role in handling such situations.



4. Security:

--Sensitive information must be protected.

Example:

Passwords
Bank Details
Personal Information

--A good architecture makes it easier to enforce security rules.


5. Team Collaboration:

--As the number of developers increases:

5 Developers
20 Developers
100 Developers

--the architecture helps define ownership and responsibilities.



Monolithic Architecture:
------------------------

The word Monolith comes from:

Mono  = One
Lith  = Stone

Meaning:

One Large Unit

--In software development, a Monolithic Application is an application where all business functionality exists inside a single deployable unit.


--A Monolithic Application is a software application in which all modules are developed, deployed, and executed as one application.

Example:

E-Commerce Example

--Suppose we are building an Online Shopping Platform.

Features:

User Management
Product Management
Order Management
Payment Processing
Inventory Management
Notifications

--In a Monolithic Architecture, all these modules exist inside a single application.



Diagram:

+------------------------------------------------+
|                                                |
|            E-Commerce Application              |
|                                                |
|  Users                                         |
|  Products                                      |
|  Orders                                        |
|  Payments                                      |
|  Inventory                                     |
|  Notifications                                 |
|                                                |
+------------------------------------------------+

--Everything is packaged together and deployed together.

Monolith = Bad

--The real issue is not whether an architecture is good or bad.

The real question is:

--For many years, Monolithic Architecture was the default choice for software development.
Because it solved the problems businesses had at that time.

Most companies:

Small Teams
Limited Budget
Simple Requirements

--did not need distributed systems.

--A Monolith was usually the simplest and most effective solution.

--Monolithic Architecture is often a good choice when:

--Business requirements are still changing frequently.

3. MVP Development:

4. Limited Budget:

--Microservices introduce additional operational costs.

--A Monolith is usually cheaper initially.


Common Misconception:
----------------------

Many developers believe:

--not based on trends.



Problems with Monolithic Architecture:
======================================


Monoliths work extremely well
until the application becomes very large.

Most architectural problems do not appear when:

100 Users
5 Developers
20 Features

The problems start appearing when:

Millions of Users
Hundreds of Developers
Thousands of Features

--Let's understand these problems one by one.



Problem 1: Large Codebase

--As the business grows, the application grows.

Initially:

E-Commerce Application

Users
Products
Orders

After a few years:

Users
Products
Orders
Payments
Inventory
Notifications
Coupons
Reviews
Recommendations
Analytics
Shipping
Returns

--The application becomes huge.


Example:

Suppose an application initially contains:

	50 Classes

After several years:

	5000+ Classes

Developers now face challenges:

Understanding Existing Code
Finding Bugs
Adding New Features
Refactoring Old Features

Real Life Analogy:
------------------

Imagine a small library.

Initially:
500 Books

Finding a book is easy.

--Finding the correct book becomes much harder.

Impact on Developers:

--A new developer joins the organization.

Questions arise:

Where is the code?
Which service handles this?

What will break if I change this?

--The learning curve becomes very steep.



Problem 2: Tight Coupling

--One of the biggest challenges of Monolithic Applications is:

	Tight Coupling

What is Coupling?

--Coupling refers to the level of dependency between components.

Example

Suppose:

OrderService

directly depends on:

PaymentService

and:
PaymentService

depends on:
InventoryService

and:
InventoryService

depends on:
NotificationService

Diagram:

OrderService
      ↓
PaymentService
      ↓
InventoryService
      ↓
NotificationService

--Now changing one component may impact many other components.


Real Life Analogy:

Imagine electrical wiring in a house.

Suppose every room shares the same wiring.

If one wire is damaged:

Kitchen
Bedroom
Living Room
Bathroom

--may all be affected.

This is similar to tightly coupled software.

Why is Tight Coupling Dangerous?

--Because changes become risky.

A developer changes:
	
	PaymentService

and unexpectedly breaks:

	OrderService

--Even though they seem unrelated.



Problem 3: Scaling Challenges:

--This is one of the most important reasons Microservices became popular.

Understanding Scaling

Scaling means:

Increasing system capacity
to handle more users.

Example:

Suppose an application receives:

	100 Requests Per Minute

Later:

	10000 Requests Per Minute

--The application struggles.
--We need to scale.

Imagine an E-Commerce Application.

Traffic Distribution:

	100000 Requests / Minute

Orders Module
	
	2000 Requests / Minute

Payments Module

	500 Requests / Minute

--Only Product Search is heavily used.

	Scale Products Module Only

What Actually Happens?

In a Monolith:

	Scale Entire Application

Diagram:
+--------------------------------+
| Users                          |
| Products                       |
| Orders                         |
| Payments                       |
| Inventory                      |
+--------------------------------+

	Products Need More Resources

Infrastructure Cost

Memory Usage

Real Life Analogy

Microservices Architecture:
===========================

Micro = Small
Service = A business capability

--A Microservice is not simply a small application.

This is one of the most common misunderstandings among beginners.

A Microservice is:

--A small, independently deployable application responsible for a specific business capability.

Notice the phrase:

	Specific Business Capability

--This is extremely important.

Official Definition:
--------------------

According to the Spring ecosystem:

--A Microservice is a small, autonomous service that works together with other services to form a complete system.

Official Reference:

	https://spring.io/microservices

==================================

Let's consider an E-Commerce Platform.

Features:

Inventory Management
Notifications

In a Monolith:

Everything
Inside
One Application

In Microservices:

User Service
Product Service
Order Service

Inventory Service
Notification Service

--Each service becomes responsible for one business capability.

--Each store specializes in a specific business function.

**Microservices did not appear because developers wanted something new.

The Core Philosophy of Microservices:
=====================================

Do One Thing Well

--Each Microservice should focus on one business responsibility.


Good Example:

User Service

Responsibilities:
- Registration
- Login
- Profile Management

Product Service

Responsibilities:
- Product Creation
- Product Updates
- Product Search

Order Service

Responsibilities:
- Place Orders
- View Orders
- Cancel Orders

--Each service has a clear purpose.

Bad Example:

Imagine:

Product Service

contains:

Create Product
Delete Product
Register User
Login User
Generate Invoice
Process Payment

This service is doing too many things.
This is not a good Microservice.



Characteristics of a Microservice:
==================================


1. Single Responsibility

--A Microservice should focus on one business capability.

Example:

User Service

--Only User Related Functionality


2. Independent Deployment

--A service should be deployable independently.

Example:

Product Service Updated

Ideally:

	Deploy Product Service Only

without redeploying:

User Service
Order Service
Payment Service


3. Independent Development

--Different teams can work on different services.

Example:

Team A
	User Service

Team B
	Product Service

Team C
	Order Service

--This reduces coordination overhead.


4, Independent Scaling:

Suppose:

Product Search

receives:
	10000 Requests/Minute

while:

Payments

receive:
	500 Requests/Minute

--Only Product Service needs additional resources.



5. Fault Isolation

If:
Notification Service

fails,

--other services may continue functioning.

Example:

Products OK
Users OK
Orders OK
Notifications DOWN

--This is much better than an entire application outage.

Service Boundaries and Bounded Context:
======================================

Many beginners believe Microservices are simply:

	Many Small Applications

This is only partially correct.

The real challenge is not creating multiple applications.

The real challenge is deciding:

Where should one service end
and another service begin?

This decision is called:

	Defining Service Boundaries


Why Service Boundaries Matter?
------------------------------

Let's imagine a company decides:

We will build 20 Microservices.

Sounds impressive.

But if the services are designed incorrectly:

Communication increases
Dependencies increase
Complexity increases
Deployment becomes harder

--The company may end up with a system that is worse than the original Monolith.


Real Life Analogy: Apartment Building
-------------------------------------

Imagine an apartment building.

Question:

	Where should walls be placed?

A good design creates:

Living Room
Bedroom
Kitchen
Bathroom

--Each area has a clear purpose.

Bad Design:

Half Kitchen
Half Bedroom
Half Bathroom
Half Living Room

--Everything overlaps.

The apartment becomes difficult to use.
Microservices face the same challenge.


What is a Service Boundary?
---------------------------

A Service Boundary defines:

	What a Service Owns

	What a Service Does Not Own

--Every service must have clear responsibilities.


Example: E-Commerce System:
---------------------------


Business Features:

Users
Products
Orders
Payments
Inventory

Question:

--Should everything belong to one service?

No.

--We need ownership boundaries.

User Service Boundary:
---------------------

User Service owns:

User Registration
Login
User Profile
Roles
Permissions

User Service database:

	users

Product Service Boundary:
-------------------------

Product Service owns:

Product Creation
Product Updates
Pricing
Categories
Inventory Quantity

Product Service database:

	products

Very Important Rule:
--------------------

--The Product Service should NOT own:

User Passwords
User Login
User Roles

--Those belong to User Service.

Likewise:

User Service should NOT own:

Product Prices
Product Categories
Inventory

--Those belong to Product Service.


The Ownership Principle:
-----------------------

--Every piece of business data should have one owner.

Example:


User Data
      ↓
User Service

Product Data
       ↓
Product Service

--This principle prevents confusion.


Common Beginner Mistake: 1
--------------------------

--Splitting Services by Technical Layer

Some developers create:

Controller Service
Repository Service
Database Service

This is incorrect.

Microservices should be split by:

	Business Capability

	not by technical layer.


Incorrect Design:

UserController Service
UserService Service
UserRepository Service

--This creates unnecessary network communication.

Correct Design:

User Service

Contains:

Controller
Service
Repository
Database

--Everything related to users remains together.


Common Beginner Mistake 2
--------------------------

--Creating Too Many Microservices

Some teams create:

Login Service
Register Service
Forgot Password Service
Profile Service

--for user functionality.


Result:

Excessive Communication
Excessive Complexity
More Deployments

Better Design:

	User Service

--owns all user-related functionality.


Common Beginner Mistake 3
--------------------------

--Sharing the Same Database


Many beginners create:

User Service
Product Service

but both services access:

	ecommerce_db

directly.

This seems convenient.

Suppose:

	Product Service

directly updates:

users table.

	Who Owns User Data?

Nobody knows.

--Ownership becomes unclear.

Good Practice

--Each service owns its own data.

      ↓
   user_db

      ↓
product_db

--Even if both databases run on the same PostgreSQL server.

Domain Driven Design was introduced by Eric Evans.

Official Reference:

	https://www.domainlanguage.com/ddd/reference/

A central concept of DDD is:

	Bounded Context


Definition:

A Bounded Context defines:
The specific business area
for which a service is responsible.



Example:

Contains:

User Information:

--For every user we need:

Database Name: userdb;

Table: users

CREATE TABLE users
(
    id BIGSERIAL PRIMARY KEY,

    name VARCHAR(100) NOT NULL,

    email VARCHAR(100) UNIQUE NOT NULL,

    password VARCHAR(100) NOT NULL,

    role VARCHAR(20) NOT NULL
);



--Why VARCHAR(100) For Password?

We never store actual passwords.

Example:
	admin123

--should never be stored directly.

Instead we store:
$2a$10$Kc3K9uP8......

--which is the BCrypt encrypted password.
--Therefore the column length must be larger.

AuthenticationManager & UserDetailsService: Inside our application
===========================================

--You may notice that our User Service does not use:

- AuthenticationManager
- UserDetailsService
- UserDetails
- DAOAuthenticationProvider

Reason:
--------

--In this project, we are performing authentication manually inside the service layer.

Current Login Flow:

Client
   |
Email + Password
   |
UserRepository
   |
Database
   |
PasswordEncoder.matches()
   |
JWT Generation
   |
Return Token

Example:

User user = userRepository.findByEmail(dto.getEmail())
        .orElseThrow(...);

boolean valid = passwordEncoder.matches(
        			dto.getPassword(),
        			user.getPassword());

Since we are not using:

	authenticationManager.authenticate(...)

there is no need for:

UserDetailsService
UserDetails
DAOAuthenticationProvider

--In enterprise applications, these components are commonly used by Spring Security to authenticate users.

--For this microservices course, we kept the login process simple so that the focus remains on:

- Microservices Architecture
- JWT
- API Gateway
- Routing & Filters
- Load Balancing
- Circuit Breaker
