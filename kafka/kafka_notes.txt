Event-Driven Architecture with Kafka:
=====================================

Before learning Kafka, we must first understand what problem Kafka is trying to solve.

--Kafka was created to solve common problems that arise
 when multiple services need to communicate with each other in a distributed system.


A Real-World Example:
--------------------

Imagine an e-commerce application like Amazon.

A customer clicks:

	Buy Now
for:
	iPhone 17 Pro Max

--At first glance, it looks like a simple operation.

But internally, many business processes must be executed.

Create Order
Process Payment
Reserve Inventory
Send Email
Send SMS
Generate Invoice
Update Analytics
Detect Fraud

--All these operations are handled by different services.


Traditional Microservice Communication:
---------------------------------------

--Suppose our system contains the following microservices:

Order Service
Payment Service
Inventory Service

Analytics Service
Fraud Service

--When a customer places an order, the Order Service directly calls all other services.

	inventoryClient.reserveStock(order);

	notificationClient.sendEmail(order);

	analyticsClient.recordOrder(order);

	fraudClient.checkFraud(order);

--This approach works initially, but as the system grows, several serious problems appear.



Problem 1: Tight Coupling
-------------------------

What is Coupling?

--Coupling represents the level of dependency between two services.

--When one service has detailed knowledge about another service, they become tightly coupled.


Example

Order Service knows:

Payment Service API
Inventory Service API
Notification Service API
Analytics Service API

--Suppose Notification Service changes its endpoint:

Before:

	/send-email
After:
	/send-notification

--Now Order Service must also change its code.

Notification Service Changed
            |
            v
Order Service Must Change

--This dependency creates a maintenance nightmare.


Why Tight Coupling Is Bad:

- Difficult to modify services independently
- More deployments required
- High maintenance cost
- Small changes affect multiple teams
- Reduced flexibility



Problem 2: Temporal Coupling
----------------------------

What is Temporal Coupling?

Temporal coupling means:

--Two services must be available at the same time for communication to succeed.

--In synchronous communication, the caller waits for the receiver to respond immediately.

Example

Order Service calls Notification Service.

Order Service
      |
      v
Notification Service

--If Notification Service is down:

Order Service
      |
      v
Notification Service
      |
      X  (DOWN)

Result:

	Order Creation Failed

Even though:

	Payment Successful
	Inventory Available

--the entire request may fail because one dependent service is unavailable.


Why Temporal Coupling Is Bad:

- Services become dependent on each other's uptime.
- Service A works only if Service B is available.

--This reduces system reliability.

Synchronous Communication:
--------------------------

In synchronous communication:

1. Service A sends a request.
2. Service A waits.
3. Service B processes.
4. Service B returns a response.
5. Service A continues execution.


Real Life Example:
------------------

Calling a friend on the phone.

You call
You wait
Friend answers
Conversation starts

--You cannot continue until the other person responds.


Characteristics:

Request-Response Model
Blocking Nature
Immediate Response Expected
Both Services Must Be Running

Examples:

REST API
HTTP Calls
gRPC Calls

------------------------------

--Suppose each service takes some time.

Payment Service       = 2 sec

Total waiting time:

	2 + 2 + 1 = 5 seconds

Flow:

- Reduced throughput

--Businesses continuously evolve.

Management may request:

Now Order Service becomes:

Q/- What Solution Can Eliminate These Problems?

--Instead of directly calling every service:

Order Service
      |
      +--> Payment
      +--> Inventory
      +--> Notification

--What if Order Service simply announces:

	"An order has been created."

--and interested services react to that information independently?

--This idea leads us to Event-Driven Architecture, which is the foundation of Kafka.


Now let's understand how Event-Driven Architecture solves these problems 
and where Kafka fits into the picture.


Event-Driven Architecture:
-------------------------

--Instead of directly calling multiple services, 
a service simply publishes an event whenever something important happens.

--Other interested services listen to that event and perform their own work independently.


Event-Driven Approach:
---------------------

Order Service
      |
      v
ORDER_CREATED Event
      |
      v
   Kafka
      |
      +------> Inventory Service
      |
      +------> Notification Service
      |
      +------> Analytics Service
      |
      +------> Fraud Service

--The Order Service no longer needs to know who will consume the event.


What is an Event?
-----------------

--An Event is a record of something important that has already happened in the system.

Think of an event as:

	"A business fact that occurred."

Examples:

User Registered
Order Created

Invoice Generated
Password Changed


--Events describe the past.

Examples:

	User Registered

means

	A user has already registered.

	iPhone 17 Pro Max

  "quantity": 1,
  "amount": 159999
}

Meaning:

	Order 101 has been created.

--Any interested service can now react.

Asynchronous Communication:
---------------------------

--Kafka uses asynchronous communication.

In asynchronous communication:

1. Service sends a message.
2. Service immediately continues its work.
3. Receiver processes later.
4. Sender does not wait for an immediate response.

Example:


Service A
    |
    | Send Message
    v
Kafka
    |
    | Message Stored
    |
Service A Continues


Receiver processes later:

Kafka
   |
   v
Service B




Real-Life Example:
------------------

Email

--When you send an email:

	Send Email

--Do you wait until the receiver reads it?
No.

The email server stores it.

Receiver may read:

After 5 minutes
After 5 hours
After 5 days

This is asynchronous communication.
Kafka works similarly.

Student A

--Trainer doesn't individually call each student.

--Kafka works in a very similar way.


Synchronous vs Asynchronous Communication:
------------------------------------------

| Synchronous 			    | Asynchronous                         |
|-----------------------------------|--------------------------------------|
| Sender waits 			    | Sender doesn't wait                  |
| Immediate response                | Response can come later              |
| Temporal coupling exists          | Temporal coupling removed            |
| Higher latency                    | Faster response                      |
| Services must be online together  | Services can be temporarily offline  |
| REST APIs                         | Kafka Messaging                      |

Important Question:

Q/- When Consumer reads a message:

	Does Kafka delete it?

Answer:
NO

--This is one of Kafka's most powerful features.

--Kafka does not immediately delete messages after consumption.


Why Doesn't Kafka Delete Messages?


Suppose:

	Inventory Service

--already read message.

Tomorrow:

	Analytics Service

--also wants to process the same order.

If Kafka had deleted the message:

	Analytics Service would miss it.

--Therefore Kafka keeps messages for a configurable retention period.

Example:

7 Days
30 Days
90 Days

--depending on configuration.

Why Does Kafka Need Offsets?
-----------------------------

Kafka must remember:

--Which messages were already processed by the consumer?

Example:

Inventory Service processed:

Offset 0
Offset 1
Offset 2

Current position:

	Offset 3

--Kafka stores the committed offset
for each consumer group.

When a consumer restarts,

--it retrieves the last committed offset

from Kafka and resumes processing
from the next offset.

================

	Order service

- Higher backlog

- Single point of failure


Scaling the Consumer:

Inventory-3

Inventory-2

--Messages distributed.

--Processing becomes faster.

Partition: The Secret Behind Kafka Scalability
===========

We learned that Kafka uses Consumer Groups to distribute work among multiple consumers.

A natural question arises:

--If millions of messages are arriving every day, how can a single topic handle all that traffic efficiently?

Kafka's answer is:
Partitions


--Partitions are one of the most important concepts in Kafka.

Without partitions:

No Parallel Processing
No High Throughput
No Scalability


Why Do We Need Partitions?
-------------------------

Suppose Amazon receives:

	10 Orders Per Day

--A single topic can easily handle that.

Now imagine:

	10 Lakh Orders Per Day
or
	Millions of Orders Per Day

--A single stream of messages becomes difficult to process efficiently.

--Kafka solves this problem by splitting a topic into multiple smaller parts.

These smaller parts are called:

	Partitions

Example:

	order-topic

--can be divided into:

Partition-0
Partition-1
Partition-2


Real-World Analog:
------------------

Imagine a huge library.

--Suppose all books are kept in a single rack.

	Rack-1

--Finding books becomes slow.

A better approach:

Rack-1
Rack-2
Rack-3
Rack-4

--Books are distributed across multiple racks.

Benefits:

Faster Search
Better Organization
More Parallel Access

--Kafka follows the same principle.

--Instead of storing all messages in one place, it distributes them across partitions.


Messages Inside Partitions:
---------------------------

Suppose a producer sends:

Order-101
Order-102
Order-103
Order-104
Order-105
Order-106

Kafka may distribute them like this:


Partition-0

	Order-101
	Order-104

Partition-1

	Order-102
	Order-105

Partition-2

	Order-103
	Order-106


Notice:

Messages are distributed
across partitions.



Offsets are Per Partition:
--------------------------

--Many beginners assume offsets are global.

That is incorrect.

Important Rule:

--Offsets belong to a partition, not to a topic.

--Each partition maintains its own offset sequence.

Example:

Partition-0

	Offset 0 -> Order-101
	Offset 1 -> Order-104

Partition-1

	Offset 0 -> Order-102
	Offset 1 -> Order-105

Partition-2

	Offset 0 -> Order-103
	Offset 1 -> Order-106


Notice:

Offset 0

exists in:

Partition-0
Partition-1
Partition-2

Therefore:

--Offset alone is not unique.

Partition + Offset
forms a unique message location.


Partitions mainly solve two problems:
-------------------------------------

1. Ordering
2. Parallel Processing


Ordering:
--------

--Some business operations must happen in the exact order they were created.

Banking Example:

Account:
	ACC1001

Operations:

Deposit 1000
Withdraw 200
Withdraw 300

--Correct execution order:

Deposit 1000
Withdraw 200
Withdraw 300

Final Balance:

	500

What if Order Changes?

--Suppose messages are processed randomly:

Withdraw 300
Withdraw 200
Deposit 1000

--Business logic may become incorrect.

--The resulting balance may not represent what actually happened.

--Therefore ordering is extremely important.


Kafka's Ordering Guarantee:
----------------------------

Kafka guarantees:

	Ordering Within A Partition

Example:

Partition-0

	Offset 0 -> Order-101

	Offset 1 -> Order-102

	Offset 2 -> Order-103

	Offset 3 -> Order-104

Consumer reads:

Order-101
Order-102
Order-103
Order-104

--Exactly in the same sequence.

--Kafka never changes the order inside a partition.


Kafka guarantees:

	Ordering Within A Partition

--Kafka does NOT guarantee:

	Ordering Across Partitions


Ordering Across Partitions:
---------------------------

Suppose:

Partition-0

	Order-101
	Order-104

Partition-1

	Order-102
	Order-105

Partition-2

	Order-103
	Order-106

--A consumer group may process them in the following sequence:

Order-101
Order-102
Order-103
Order-105
Order-104
Order-106

--This is completely valid.

--Kafka is not concerned about ordering between partitions.

--Its guarantee applies only inside an individual partition.


Golden Rule:

--Kafka guarantees message ordering only within a partition.

or

Same Partition

	Order Guaranteed

Different Partitions

	Order Not Guaranteed

--This ordering guarantee is one of the main reasons why choosing the 
correct partitioning strategy is so important in real-world Kafka applications.



Parallelism:
=============

--This is why Kafka is fast.

Suppose:

10000 Orders

One consumer:

	Consumer-1

Processing:

	10000 messages

--Very slow.


Multiple Consumers


	Consumer-1

	Consumer-2

	Consumer-3

--Now workload is divided.


But How Does Kafka Divide Work?

Answer:

	Using Partitions only


--Each consumer gets partitions.

Example

Topic:

	order-topic

Partitions:

	P0
	P1
	P2

Consumer Group:

	C1
	C2
	C3

Assignment:

	P0 --> C1
	P1 --> C2
	P2 --> C3



Partition 0 --> Consumer 1
Partition 1 --> Consumer 2
Partition 2 --> Consumer 3

--All consumers work simultaneously.


Important Rule:

One Partition
	→ One Consumer

--Inside Same Consumer Group


What If Consumers > Partitions?
-------------------------------

Topic:

	3 Partitions

Consumers:

	5 Consumers

Kafka can assign only:

	P0 -> C1

	P1 -> C2

	P2 -> C3

Remaining:

C4 Idle

C5 Idle

-------------------------------

Partitions:

	6

Consumers:

	3

Assignment:

	Consumer1 -> P0,P1

	Consumer2 -> P2,P3

	Consumer3 -> P4,P5

--Consumers handle multiple partitions.

Kafka Cluster:
==============

--A Kafka Cluster is a collection of one or more Kafka Brokers working together to store, manage, and deliver messages reliably.

--Instead of storing all data on a single Kafka server, 
Kafka distributes data across multiple brokers to 
achieve scalability, fault tolerance, and high availability.



Why Do We Need a Kafka Cluster?

A single broker can become:

- A performance bottleneck
- A single point of failure
- Difficult to scale as message volume grows

--Kafka solves this by using multiple brokers in a cluster.


How It Works:
--------------

Suppose a topic:

	order-topic

has 3 partitions:

	Partition-0
	Partition-1
	Partition-2

--Kafka may distribute them across brokers:

	Broker-1 -> Partition-0
	Broker-2 -> Partition-1
	Broker-3 -> Partition-2

--This allows multiple brokers to share storage and processing responsibilities.


Fault Tolerance:
-----------------

If one broker goes down:

	Broker-2  DOWN

--Kafka can continue serving data from replicas stored on other brokers.

--This ensures that messages are not lost and applications continue to function.

Earlier Kafka Architecture:
---------------------------

--In older versions, Kafka could not run by itself.

It required:

Kafka
   +
ZooKeeper


--ZooKeeper was used to manage Kafka cluster metadata such as:

- Topics
- Partitions
- Broker Information
- Cluster Configuration


Problem with ZooKeeper:

--Running Kafka required managing two separate systems:

Kafka
+
ZooKeeper

--This made setup and maintenance more complex.


Modern Kafka Architecture (KRaft Mode):
---------------------------------------

--Newer versions of Kafka no longer require ZooKeeper.

Kafka now uses:

	KRaft

KRaft = Kafka Raft Metadata Mode

--In KRaft mode, Kafka manages its own metadata internally.


Architecture:

+----------------+
| Kafka Broker   |
|   (KRaft)      |
+----------------+

--No ZooKeeper is required.

group-id:
---------

	spring.kafka.consumer.group-id=inventory-group


--A consumer must belong to a consumer group.

Example:

Inventory Service
        |
        v
inventory-group
        |
        v
order-topic


--Kafka tracks which messages have already been consumed for each group.

auto-offset-reset
-----------------

	spring.kafka.consumer.auto-offset-reset=earliest

Meaning:

--If no previous offset exists, start reading from the beginning of the topic.


Possible values:

earliest: Read all existing messages
latest  : Read only new messages
none	: Throw exception if no offset exists


--For learning and testing:

	earliest

--is usually preferred.

Step 4: Configure JSON Deserialization

--When Kafka receives a message, it arrives as bytes.

--The consumer must convert JSON back into a Java object.

Add the following properties:


spring.kafka.consumer.key-deserializer=org.apache.kafka.common.serialization.StringDeserializer

spring.kafka.consumer.value-deserializer=org.springframework.kafka.support.serializer.JacksonJsonDeserializer

spring.kafka.consumer.properties.spring.json.trusted.packages=*



Here,

spring.kafka.consumer.properties.spring.json.trusted.packages=*

For security reasons,
JacksonJsonDeserializer only trusts specified packages.

* means trust all packages.

For learning purposes this is acceptable.

In production, specify the actual package name.

Example:

	spring.kafka.consumer.properties.spring.json.trusted.packages=com.hdfc.event

package com.hdfc.service;

import org.springframework.kafka.annotation.KafkaListener;
import org.springframework.stereotype.Service;

import com.hdfc.event.OrderCreatedEvent;

@Service
public class InventoryConsumer {

    // @KafkaListener(topics = "order-topic", groupId = "inventory-group")
    @KafkaListener(topics = "order-topic")
    public void consume(OrderCreatedEvent event) {

        System.out.println("Order Received");

        System.out.println("Order Id : " + event.getOrderId());

        System.out.println("Product  : " + event.getProduct());


    }
}
